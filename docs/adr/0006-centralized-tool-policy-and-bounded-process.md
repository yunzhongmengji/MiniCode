# ADR-0006：集中实施工具策略并使用受限 argv 子进程

状态：Accepted
日期：2026-09-07

## 背景

M3 已建立 Tool、Registry、Dispatcher 和 Workspace，但只有读取能力。加入搜索、编辑和运行测试后，模型动作会消耗更多资源或产生文件和进程副作用，需要解决以下问题：

1. 工具各自实施权限会导致默认规则和审批行为不一致。
2. 模型生成的参数不可信，非法参数不应到达 Policy、用户审批或副作用代码。
3. 编辑目标可能不存在或重复，自动猜测会修改错误位置。
4. 拼接 shell 命令会让模型输入中的控制符变成额外命令。
5. 测试进程可能超时并在 Agent 已经停止后继续运行。
6. 应用层约束容易被误认为完整 Sandbox，需要明确剩余风险。

## 决策

1. ToolDispatcher 统一按照 Registry 查找、Schema 验证、Policy、Approval、Tool 执行的顺序处理调用。
2. Policy 使用 Allow、Ask、Deny 三种结果；名称没有显式规则时默认 Deny。
3. Ask 必须通过异步 ToolApprover 对本次 ToolCall 返回严格布尔值；拒绝或缺少 Approver 时不执行工具。
4. SearchTextTool 只提供 literal search，并限制遍历文件数、单文件大小和匹配结果数。
5. EditFileTool 只替换恰好出现一次的精确文本，检查完整更新结果大小，并使用同目录临时文件与 `os.replace()`。
6. RunTestsTool 只接受工作区内测试路径，拒绝 `-` 开头的 pytest 选项，并构造固定 argv。
7. ProcessRunner 使用 `create_subprocess_exec()` 而不是 shell，捕获 stdout/stderr，并在超时时终止和回收直接子进程。
8. 预期文件、进程和工具失败逐层转换为 ToolExecutionError 和错误 ToolResult；意外程序错误继续抛出。
9. 明确记录未实现的环境白名单、输出上限、进程组清理、持久审批事件和 OS Sandbox，不把 M5 宣称为任意命令隔离层。

## 正面后果

1. 所有工具共享一个执行前权限边界，新增工具不会自行决定是否绕过审批。
2. 非法参数、拒绝和未批准调用在副作用前短路，并能通过假 Runner 的零调用断言证明。
3. 模型无法通过 shell 控制符扩展固定 pytest 命令，pytest 选项注入也在 Schema 层拒绝。
4. 搜索和编辑具有明确资源上限，编辑不会在多个候选位置中猜测。
5. 超时进程在错误返回前被终止和回收，工具层仍能向模型提供稳定错误语义。
6. QueryLoop 继续只依赖 ToolRuntime，不需要知道具体 Policy、Approval、Workspace 或 ProcessRunner。

## 负面后果

1. Policy 当前只依据 ToolCall 和工具名称，复杂的路径、参数与上下文策略需要扩展接口。
2. Approval 只是异步协议，没有真实 UI、持久事件、签名令牌或过期机制。
3. 唯一精确替换比补丁或 AST 编辑能力弱，模型需要先读取并提供足够上下文。
4. literal search 不支持正则、忽略规则、二进制探测或索引，大仓库效率有限。
5. `communicate()` 会把全部进程输出保存在内存中，子进程也继承当前环境。
6. `kill()` 只针对直接子进程，无法保证清理 pytest 产生的所有后代进程。
7. Workspace 仍有检查与使用之间的 TOCTOU 窗口，应用层边界不能替代 Sandbox。

## 备选方案

1. 每个工具自行询问审批。
   - 实现局部简单，但容易遗漏、重复或产生不同的默认行为，因此不采用。

2. 先运行工具，再根据结果判断是否允许。
   - 副作用已经发生，审批失去意义，不接受。

3. 直接执行模型生成的 shell 字符串。
   - 灵活但暴露 shell 注入和任意命令能力，M5 不接受。

4. 自动替换全部 old_text 匹配。
   - 使用方便，但会把歧义扩大为多处修改，当前选择拒绝猜测。

5. 只在 QueryLoop 外设置总超时。
   - 能停止等待，但不能确保子进程在返回前被显式终止和回收，因此 ProcessRunner 仍需自己的超时清理。

## 重新评估条件

1. Policy 需要依据规范化路径、验证后的参数、任务来源或历史风险时，扩展决策输入。
2. CLI/UI 接入真实人工审批时，引入一次性批准、过期、精确参数绑定和事件记录。
3. 测试输出可能很大或包含秘密时，引入流式 byte 上限、截断标记和脱敏。
4. pytest 能启动后代进程时，引入进程组或容器级生命周期管理。
5. 开放安装、网络、任意命令或不可信仓库执行前，必须引入 OS Sandbox 并完成 M12 红队验证。
