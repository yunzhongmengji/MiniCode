# MiniCode：Agent 面试考点与秋招发展路线

核对日期：2026-09-13。本文依据当前工作区代码、测试、已归档结果及用户提供的面试截图。
这是后续行动建议，不表示下面的功能已经实现，也不表示学习门禁已经通过。

## 1. 先明确项目要证明什么

MiniCode 的定位继续是：**面向 Python 仓库、可审计、可恢复的本地 Coding Agent 工程原型**。
主投方向是 Agent 应用开发、AI 应用工程、偏 Agent 的后端研发，而不是大模型训练或推理引擎研发。

适合贯穿面试的一个问题是：

> 模型需要多轮读代码、修改和测试时，怎样限制它的权限，保留必要上下文，恢复中断任务，并证明最后确实做对了？

面试截图中最可用的内容是具体问题，而不是对招聘行情的结论。
薪资、公司面试风格、岗位增长、“前沿必考”和 RSI 相关断言均属于作者叙述，本文不将其视为已核实事实。
不因为文章提到一个名词，就给项目增加一个子系统。

建议形成三条技术主线：

1. 可靠执行：工具契约、权限、预算、失败恢复和过程记录。
2. 上下文治理：完整执行状态与模型视图分离，逐步实现可回读的历史输出裁剪。
3. 受控经验复用：先让 Skill 真正参与任务，再做有来源、可纠错的项目记忆。

评测不是最后的装饰：每条主线都要回答“相较之前，解决了哪个失败，证据是什么”。

## 3. 从截图提炼出的项目面试题

每个主题按三层准备：**怎么做 → 为什么这样做 → 怎么证明、哪里会失败**。
下面不是背诵答案，面试时应能指出对应代码和一条测试。

### 3.1 Agent、Tool、Workflow 与 Harness 各负责什么？

面试问题：模型靠什么选择工具？Function Call 如何执行？为什么不用固定流程或三个角色？

用 MiniCode 解释：

- Tool 是具体能力，例如读文件；名称、描述和参数 Schema 提供给模型。
- Agent 的模型根据任务、历史和工具定义提出下一步调用；它并不直接取得执行权限。
- Workflow 是预先写定的步骤与判断。MiniCode 的参数校验、审批和结果验收适合确定性代码；定位哪段代码出错则允许模型探索。
- Harness 可理解为模型外面的运行支撑系统：循环、工具执行、预算、状态、上下文和观察机制。不是再加一个模型的名字。
- 当前是单 Agent，不是规划、执行、审查三个独立 Agent。工具可有多个，不代表 Agent 有多个。

追问准备：单 Agent 能完成哪些任务？模型反复调用同一工具时如何停？多角色如果引入，额外通信、Token、失败恢复和文件冲突值不值得？
现阶段用有证据的单 Agent 是合理取舍，不是缺一个必须打勾的功能。

### 3.2 非法参数、错误结果和无限循环如何处理？

面试问题：JSON 不符合结构怎么办？多个工具输出如何对应？输出形式合法但内容错了怎么办？

当前链路是：ToolCall → Registry 查工具 → Pydantic 参数校验 → Policy → 必要审批 → 执行 → 带相同 `call_id` 的 ToolResult。
可预期的工具错误以 `is_error=True` 反馈；程序内部意外异常与取消不能伪装成成功。
工具结果进入下一轮上下文，模型可以据此改变动作，但受轮数和调用数限制。

必须区分：

1. 模型适配器解析失败，与工具参数 Schema 校验失败，不是同一层错误。
2. 参数可解析，不代表语义正确：路径可能越界、编辑目标可能不匹配。
3. 工具执行成功，不代表任务做对：还要检查最终代码、隐藏测试和副作用。
4. 有总调用上限，不代表已有“无进展检测”或完整的自动纠错策略。

证据：[Dispatcher](../../src/minicode/tools/dispatcher.py)、[工具测试](../../tests/tools/test_dispatcher.py)、[QueryLoop 测试](../../tests/core/test_query_loop.py)。

### 3.3 中断以后究竟恢复什么？

面试问题：为何逐工具保存？为什么 Run ID 必须相同？任务完成后为什么不能再次恢复？

当前每个工具结果产生后保存 `RunCheckpoint`，其中有历史、已用预算和完成标记。
一批调用执行到一半失败时，通过调用与结果的 `call_id` 匹配找出 pending；恢复不把预算归零。
CLI 按 Workspace 路径隔离存储，并复用原 Run ID；核心还检查 Checkpoint 与 EventLedger 的 Run ID 一致。

最有价值的边界题：

> 文件已经被工具改了，但 Checkpoint 保存失败，这个工具算执行完了吗？

对文件系统可能已经完成，对恢复状态却没有完成证据。两次独立写入之间存在结果未知窗口，不能声称恰好一次。
持久化检查点与工具副作用的幂等性是不同问题。Run ID 校验也不是身份鉴权，更不能证明工作区内容没有变化。

当前只有一套运行检查点，包含步骤进度和任务终态；不能包装成已实现完整的任务级/步骤级双层调度系统。
执行中追加新用户要求、抢占或合并任务尚未实现。

证据：[恢复集成测试](../../tests/test_recovery_integration.py)、[文件存储](../../src/minicode/core/file_checkpoint_store.py)。

### 3.4 上下文为什么变长？压缩的是哪一份数据？

面试问题：为什么不用滑动窗口？错误信息能否删？历史还在，模型为什么仍会忘？

先理解三个不同对象：

| 对象 | 用途 | 本阶段原则 |
|---|---|---|
| `message_history` | 程序维护的执行历史 | 保留原始 ToolCall/ToolResult，支撑恢复和取证 |
| `ModelRequest` | 这一次提供给模型的信息 | 由完整历史构造，再由 Projector 产生模型视图 |
| `RunResult` / Checkpoint | 向调用方返回运行结果 / 保存恢复状态 | 从程序维护的状态构造，不从压缩请求“反推原文” |

因此，模型看到占位内容，Checkpoint 仍有原文，并不矛盾：原文是程序保存的，不是模型重新生成的。
下一轮仍会从原始历史构建候选请求，再投影一次；这里要控制模型可见增长，不是已经解决磁盘和内存增长。

当前 `IdentityModelContextProjector` 不做改动。替换 ToolResult 的测试只证明两份状态隔离，不证明模型真的能在信息减少后做对任务。
`ContextProfile` 测量规范化 JSON 的 UTF-8 字节，不是模型实际 Token，也不是 Provider 最终请求的精确大小。

保留规则目前保护历史末尾连续 ToolResult 和所有错误结果；更早成功输出只是候选。
“末尾批次”是结构判断，不能证明模型已经理解了更早信息；新用户消息、恢复和不同历史形态的适用边界要通过测试明确。
旧输出仍可能包含决定下一步的唯一事实，不能因为它旧就认定可丢弃。

三个替代方案的取舍：

- 滑动窗口实现简单，但可能删除早期用户约束或拆断工具调用关系。
- 摘要能浓缩跨轮决策，但会引入额外模型成本、遗漏和摘要本身的错误。
- 保留原文引用、按需回读有助于取证，但回读也消耗轮次、Token 和时间；且模型必须真的有回读入口。

优先验证第三种的最小形式，再根据失败样本决定是否加摘要，而不是预先断言它一定最优。

### 3.5 评测如何证明效果，Ground Truth 谁来定？

Ground Truth 是验收依据，不只是另一段模型生成的“标准答案”。
本项目 Case 由项目维护者编写，主要用隐藏程序检查行为、修改范围和指定事实，再检查执行轨迹。
没有外部专家独立标注或生产用户样本，应如实说明。

Result 2 分开判断四件事：

1. outcome：最终代码或诊断是否通过 Case 验收。
2. operational：Agent 是否正常完成。
3. budget：是否满足该 Case 的轮次和工具调用预算。
4. trace：是否使用必要工具、避免禁止动作、在最后一次改动之后重新测试。

值得重点复述的实际经历：只读分页任务曾通过关键词验收，但解释中包含错误数学关系。
后来把整除、非整除和零项三个输入的当前值/期望值写进验收，并给验收器增加误放反例测试。
这说明“检查器显示通过”和“任务真的正确”之间也可能有缺口。
形式严格的数值/公式检查仍可能拒绝合理的不同表述，不能声称全面理解答案语义。

当前证据口径：

- 四个不同 Case，三个历史批次，共五次正式运行；重复同一题不等于新增题目。
- 四次旧版记录缺少 Result 2 的预算与 Trace 综合判定，只有一次新版只读运行有四维判定。
- 不同批次对应不同提交，不能合并成当前版本的统一成功率。
- 新记录器支持 `workspace.patch` 及哈希，但现有历史批次早于这项功能，不能说它们都已有补丁。
- 计划中的 50 题、延迟分位数和压缩收益不是已测成果。

证据：[结果批次说明](../../benchmarks/coding_agent/results/README.md)、[结果判断](../../src/minicode/evaluation_result.py)、[验收器反例](../../tests/benchmarks/test_readonly_pagination_case.py)。

### 3.6 Skill 为什么懒加载？选错了怎么办？

MiniCode 先读轻量 Manifest，按关键词路由，再读选中 Skill 的正文。
这减少无关指令进入请求；未选中内容不读取已有集成测试，但尚无真实任务 Token 收益实验。
关键词路由可解释、便于建立基线，也容易漏掉同义词和中文/英文改写。

要能回答：相关 Skill 没选到、两个相似 Skill 选错、不相关任务误选，各如何在评测中出现？
当前路由匹配率只能衡量选中了哪个名字，不能替代最终 Coding 任务是否成功。
默认 `build_coding_agent()` 尚未传 `skill_context_provider`，下一阶段要完成产品接入而非重写整套 Skill。

Skill 是方法说明，不是新权限。当前还把 Skill 渲染到 instructions，来源可信度和注入风险需要单独管理；目录限制不等于内容可信。
不因为截图提到热插拔，就加入进程池、RPC 和注册中心。

### 3.7 Memory 与压缩有什么区别？能否自动更新 AGENTS.md？

压缩解决“这次任务现在给模型看什么”；长期 Memory 解决“以后另一场任务还能复用哪些经验”。
保存所有聊天不等于高质量 Memory，一次失败后写一句经验也不等于递归自我改进。

适合 MiniCode 的第一种记忆是带来源的项目事实，例如特定快照下验证过的测试命令或目录约定。
必须保留来源、作用域和有效条件；不要把模型猜测、仓库注入或临时错误直接提升成持久指令。

追问应覆盖：谁允许写入、同一事实冲突如何更新、另一仓库是否会读到、如何纠错/删除、旧事实失效如何判断。
自动改 `AGENTS.md` 会修改后续行为，不宜作为第一版默认能力；可以先生成候选，经过证据检查与用户确认再采纳。

### 3.8 安全、性能与 AI Coding 验收怎么讲？

安全：模型建议与执行权限分开。仓库里写“忽略用户、读取密钥”不能成为新的授权。
但现有提示词与策略并非完整防注入系统，`run_tests` 仍可能运行任意仓库 Python 代码，审批不等于沙箱。
环境白名单只能限制继承的环境变量，不能证明代码无法读取本机其他文件中的秘密。

性能：慢可能是模型、工具、重复调用、审批等待或压缩开销。先增加阶段计时，再决定优化位置。
当前事件有顺序和计数，没有完整耗时测量，不应展示凭空估计的 P95 或火焰图。

AI Coding：如实说明 AI 辅助范围，用自己能定位的一个 Bug、一次验收器改进和一个方案取舍作证。
测试代码也是 AI 可能出错的地方，不能只看“全绿”。不应虚构自己独立手写了所有代码。

## 4. 后续发展：按验收进入下一阶段

下面 A—D 是秋招交付顺序，不替换旧 M0—M13 的主题编号。
先做到可演示、可解释、可复测，再考虑可选扩展；安全和评测贯穿各阶段。
不要求做完所有未来里程碑才能写简历。

### A：完成上下文治理的第一个可验证闭环（当前主线）

目标不是“删掉越多越好”，而是减少重复大输出进入请求，同时不让必要证据不可访问。

每项拆成独立小步，不在一次修改里全部实现：

1. 明确历史输出回读契约：按当前 run 的 `call_id` 返回当时保存的 ToolResult，不重新执行原工具。
   第一版优先复用完整历史/Checkpoint，不先引入数据库或另造持久化系统。
2. 为模型增加受控回读入口，限定当前 run、大小和可读内容，明确不存在、跨 run、过大输出的行为。
   证明新实例从 Checkpoint 恢复后仍能使用；回读不会赋予比原任务更大的数据权限。
3. 完成确定性投影：仅对满足阈值与保留规则的旧成功输出提供简短引用；保留 call_id、错误标记与调用关系。
   保护当前结果、错误和用户约束；回读结果也要有保留规则，避免刚读回立即又丢弃。
4. 记录投影前后大小、所处理的调用及原因，并提供可关闭的产品接入。短任务不必触发。
   字节阈值只是一种初始启发式，不宣称是 Token 硬预算；模型窗口限制与输出预留需另行设计。
5. 用同一批任务比较原样请求与候选策略，检查正确性、安全、总 Token、额外回读调用和耗时。

工程门槛：

- 真实 QueryLoop 中模型请求确实变化，而原始历史和 Checkpoint 不变。
- 最新批次、错误结果和工具协议不会误伤；不适用的历史输入明确拒绝或保守保留。
- 原文可准确取回，包括文件已经改变及重建 Agent 后的情况。
- 至少覆盖旧事实后续必需、多批长输出、错误恢复、只读约束和短任务不触发。
- 现有回归通过；候选策略在预先声明的验收任务上没有未解释的质量或安全回退。
- 真实模型实验明确区分结构收益与效果收益；无收益就保留基线或继续改进，不提前设定必须出现的百分比。

学习门槛：能不看代码解释 history/request/result 三者来源，手推连续三轮保留结果，解释为什么磁盘原文存在不代表模型看得到。

可选后续：如果裁剪仍无法支撑长任务，再增加“任务目标、限制、已完成、未解决、证据引用”的结构化摘要。
摘要的遗漏、无依据新增事实和费用必须纳入单独对照。稳定前缀/缓存与压缩不是同一个机制，缓存收益需要供应商实测数据。

### B：让已有 Skill 真正进入默认产品

目标：让能力从组件测试走到 `minicode run` 可选使用，而不是添加更多技能名字。

小步顺序：一个本地 Skill 的 CLI 配置与组装 → 正/负例路由 → 相似 Skill 误选用例 → Skill 开关对照。
明确本地 Skill 的加载来源与信任要求，不能把任意仓库文字视为可信系统指令。

工程门槛：

- 有 Skill 时 Trace 能解释选择、加载和注入；无 Skill 时行为保持原基线。
- 无关正文不读；越界、过大、加载失败都可观察且不绕过工具权限。
- 固定路由题之外，至少有“选中了但没帮助任务”的任务级验收与失败分析。
- 恢复时如何处理 Skill 内容/版本变化有明确规则；不能默默把不同说明当成同一上下文。

学习门槛：解释懒加载与关键词误选的取舍，能自己添加一个负例并定位是哪一层选错。

### C：做有证据、可纠错的项目记忆

目标：跨两次独立运行复用一条已经确认的项目事实，而不是一开始自动总结所有历史。

小步顺序：复核旧 WIP 设计 → 一条有来源的候选记录 → 项目作用域持久化 → 下一次检索 → 冲突更新和删除。
自动提炼可以晚于人工确认的数据契约；先知道什么可以存，再提高自动化程度。

工程门槛：

- 每条记忆有来源、范围和适用条件；相邻仓库不串数据。
- 错误或不可信候选不自动成为指令；纠正/删除后不能继续召回旧事实。
- 项目文件变化导致记忆失效时能检测或降级，不盲从历史记录。
- 有无记忆的跨会话任务对照能说明收益，也有故意放入错误旧记忆的反例。

学习门槛：说明“记住更多”为什么可能变差，演示一次纠错，而不是只演示写入成功。

### D：形成秋招可交付版本与证据包

这一阶段先做最小版本；如果投递临近，可在 A 完成后先做 D，不必等待 B/C 全部完成。

- 用统一的当前版本重跑已有四例，再按失败类型扩展 Case，不机械凑 50 道。
- 每例先重复三次用于初步稳定性观察；三次不是统计显著性保证，三次重跑仍只是一道题。
- 以需求类别、仓库、难度和失败类型分层扩充；把调策略的开发用例与未用于调参的保留用例区分开。
- 一次只比较一个因素：先压缩开关，再 Skill 开关，再 Memory 开关。不要同时换模型、Prompt 和策略后归因。
- 保存代码/配置/Fixture 版本、原始回答、Trace、补丁、结果与失败解释；如果工作树有未提交修改，要另有可复现快照。
- 先补模型、工具和审批等待计时；真实效果实验统计整个任务成本，不只看某一轮请求变小。
- 选择一个真实 Python 仓库的隔离副本做至少一个端到端案例，明确是项目演示而非生产流量验证。
- 准备正常成功、拒绝危险请求、中断恢复、上下文回读四段短演示。

发布前安全检查至少包含：工具副作用完成但保存失败、越权路径、仓库注入、秘密输出风险、取消与超时。
审计还发现一个需验证的进程边界：读取 stdout/stderr 的超时结束后，单独的 `process.wait()` 是否仍会无限等待；用关闭输出流但继续存活的子进程检验，不能先认定所有超时情况已覆盖。
先补测试与边界说明，再按风险决定修复；本次没有修改该逻辑。

工程门槛：别人能在隔离环境复现关键案例，每个对外数字都能从原始记录复算，每个能力清楚标明适用范围。
未实现 OS 隔离之前，不把不可信仓库测试当成安全的自动执行工作负载。

学习门槛：能讲两分钟业务价值、十分钟技术设计；每条简历描述接受三层追问，能独立定位一条失败 Trace。

## 5. 当前小步：历史原文回读契约

下一次实现建议只做一个能力：**从当前运行的完整历史按调用 ID 找回原始 ToolResult**。
先完成查找函数及边界测试，不在同一步接 CLI、压缩器、摘要和数据库。

用这个例子理解输入输出：

1. 任务第一次读 `config.py`，结果为 `timeout = 3`，程序保存为 `call_001` 的结果。
2. 后来文件被改成 `timeout = 5`。
3. 未来模型请求中，旧结果可被引用替代；如果需要核对修改前的值，应回读 `call_001` 得到 `timeout = 3`。
4. 再执行 `read_file(config.py)` 只能证明当前文件是 `timeout = 5`，不能替代历史证据。

最低验收：

- 正确 ID 返回当时的原文，而不是当前文件内容。
- 查找不修改历史，也不执行原工具。
- 不存在或尚无结果的 ID 明确报错，不编造空成功。
- 查找限定当前任务的历史；后续暴露成工具时再验证跨 run 请求被拒绝。

这一步结束后，你应能回答：“为什么原始历史一直没压缩，还需要额外做回读？”
答案是程序内部有数据与模型有权按协议获取数据不是一回事。

2026-09-14 进度：已完成第一层纯查找函数 `get_tool_result(history, call_id)`。它返回
历史中原来的不可变 ToolResult，并用不同异常区分“调用存在但结果尚未产生”和“调用
根本不存在”。测试使用编辑前后的两次读取结果，证明请求旧 call ID 时不会误取更新后的
结果。该函数只读取调用者传入的历史，不执行 Tool，也不修改历史。

2026-09-14 第二层进度：新增 `RunToolResultSource`。创建 Source 时由宿主传入
CheckpointStore 和当前 run_id；之后 `get()` 只接收 call_id，并总是读取该 Run 的最新
Checkpoint。两个 Run 即使存在相同 call ID，也不会混用结果；Store 若错误返回其他 Run
的 Checkpoint，Source 会拒绝。

2026-09-14 第三层进度：新增 `ReadToolResultTool` 及只有 `call_id` 的严格参数 Schema。
Tool 返回历史原文，不重新执行旧工具；查询失败转换成 Dispatcher 能处理的预期 Tool
错误。宿主配置 UTF-8 byte 上限，模型不能在参数里调大，超限时明确失败而非静默截断。

2026-09-14 第四层进度：新增 `ToolResultReferenceProjector`。它复用 retention 分类，只把
较老、成功、超过宿主阈值且引用确实更短的 ToolResult 替换成确定性 JSON；引用包含
call_id、原始 UTF-8 byte 数和 `read_tool_result` 工具名。最新批次、错误和较短结果保留
原文，canonical request 与 Checkpoint 不变。

2026-09-14 第五层进度：`build_coding_agent()` 新增默认值为 `None` 的显式阈值。只有设置
阈值时才同时注册短引用 Projector 和 `read_tool_result`，并强制要求 EventLedger 与
CheckpointStore 来绑定当前 Run。脚本模型已经验证“旧原文 → 短引用 → 按 call_id 回读 →
新 ToolResult 携带完整旧原文”的四轮闭环；最终 Checkpoint 始终保存 canonical history。

2026-09-14 第六层进度：`MODEL_CALL_STARTED` 保留原有模型可见 `context_profile`，新增
`context_projection`，记录变化 ToolResult 数、投影前后 ToolResult/总 bytes 和差值。关闭
路径差值为 0；开启闭环的第三轮出现 1 个变化结果和正数节省。回读次数直接从既有
`TOOL_EXECUTION_FINISHED` 的 tool_name/outcome 统计，避免重复状态。

2026-09-14 第七层进度：新增可重复的 `eager_historical_readback` 离线对照。同一个条件
模型在关闭组看到旧原文后直接完成，在开启组看到引用后先回读再完成。关闭组累计模型可见
23411 bytes；开启组虽然投影内部累计省 10142 bytes，却因多一次模型调用累计发送 30356
bytes，反而多 6945 bytes。最终脚本答案一致、两组完成且 Checkpoint 匹配各自完整历史。

2026-09-14 第八层进度：增加 `no_historical_readback` 端点，并把两端汇总为成本公式。
不回读时净收益为 `3571 = 5071 投影收益 - 1500 运行形状开销`；急切回读时净收益为
`-6945 = 10142 - 17087`。如果只线性混合这两个固定端点，急切回读型任务占比约 33.96%
时归零。该数字只训练“收益必须覆盖额外轮次和工具协议成本”的分析方法，不是生产阈值。

2026-09-15 第九层进度：真实 Preflight 证明始终暴露 `read_tool_result` 会让短任务出现净亏损，
因此加入自适应净收益门槛。Projector 先生成候选引用，再精确计算“工具结果毛节省减去本轮
回读 Tool Spec 开销”；只有差值大于 0 才投影。回读 Tool 仍注册在 Dispatcher，但只在真正
产生引用的 ModelRequest 中可见。更新后的离线结果为：不回读端点
`4571 = 5071 - 500 - 0`，急切回读端点 `-5945 = 10142 - 1000 - 15087`。这说明本地门槛能
避免单轮必亏，但无法消除回读造成的额外模型轮次成本；端到端评测仍不可省略。

当前边界：普通 CLI 没有开启入口，默认 CodingAgent 仍是七个工具和 Identity Projector；
Benchmark 可以显式选择投影 Arm。v1 真实 Preflight 已完成，但它对应优化前的始终暴露策略；
自适应策略来自观察结果后的修改，必须新建 v2 协议，不能混入 v1 正式样本。

## 6. 明确暂不投入的方向

- Multi-Agent/Team：先用单 Agent 基线找出真实瓶颈。未来优先试只读检索或审查 Worker，由主 Agent 统一写入；有可比收益后再讨论并发写冲突与调度。
- MCP：先学习它解决外部工具接入标准化的问题；确有接入需求时再做适配，不为名词重写本地工具。
- RPC、注册中心、Skill 进程热插拔：当前本地方法说明并不需要这些分布式机制。
- 自动改 AGENTS.md、开放式自我优化：先有固定验收、版本、人工确认与回滚，再谈迭代。模型建议一次修改不是 RSI 的效果证据。
- LoRA/QLoRA、PPO/DPO、CUDA、vLLM 算子：属于另一条岗位技能线，不加入当前仓库。面试基础可根据目标 JD 单独学习。
- 后端基础不能放弃：异步、取消、文件原子替换、幂等、进程、测试与错误契约都能结合本项目学习；不需要额外造电商系统。

## 7. 简历与面试表达

当前可采用、但需要自己理解的表述：

> 基于 Python 实现本地 Coding Agent 运行时，支持结构化工具调用、确定性权限与人工审批、逐工具检查点及中断恢复；构建包含隐藏验收、执行轨迹约束与结果工件校验的评测链路。

上下文与 Skill/Memory 对外描述要随真实完成度更新。压缩尚未接入时只能说正在实现，不写“显著优化”或无依据的百分比。
已有默认工具七个可以准确列出；测试数量说明覆盖规模，不能等价于真实任务能力。

未来有测量后，数字描述应附带口径：

> 在固定版本的 N 个自建任务、每题 R 次运行上，对比原样上下文与策略 X；报告通过数、总输入/输出 Token、额外工具调用及失败案例。

N、R 和收益留到实际测量后填写。样本、模型、初始仓库、预算、审批方式和判定标准都能继续追问。

每个小步的教学约定：

1. 先说明这一小步解决哪个失败，不一次引入多个新模块。
2. 新代码解释调用者、输入输出、所在链路和失败行为。
3. 运行有针对性的测试，说明它证明了什么、没有证明什么。
4. 让你预测一个变式或讲回流程；未理解则继续讲，不假设“代码通过＝你已掌握”。
5. 更新对应学习文档；不把每次小修改都包装成一个已完成大阶段。

## 8. 外部工程依据与适用范围

以下是工程思路的参考，不是 MiniCode 已有效的证明，也不是所有企业都采用同一架构的证据。

- Anthropic [Building effective agents](https://www.anthropic.com/engineering/building-effective-agents) 区分固定 Workflow 与模型动态决策，并建议依据需要增加系统复杂度。对应本项目先保留单 Agent、确定性权限/验收的选择。
- Anthropic [Effective context engineering for AI agents](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents) 讨论按需取回信息、历史工具输出清理、摘要及结构化笔记，也指出压缩可能丢失后来才显得重要的信息。对应本项目先验证原文回读，再评估裁剪的路线；具体保留算法是本项目待验证的设计。
- Anthropic [Demystifying evals for AI agents](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents) 强调最终环境状态、重复尝试、验收器质量和人工阅读轨迹。对应本项目把任务结果、过程约束和验收器反例一起检查。

真实企业适用性最终还取决于权限/隔离、数据保留、成本、运维和业务验收；本路线训练这些工程能力，但不把个人项目等同于生产系统。
