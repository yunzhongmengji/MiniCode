# v3 Preflight 逐轮 Trace 诊断

诊断日期：2026-09-16  
范围：只读取已归档 Trace、Result 和 Case 文件；未修改算法，未调用 Provider。

## 1. 诊断问题

本次只回答两个问题：

1. baseline 与 projection 从哪一轮开始走出不同轨迹？
2. projection 为什么已经修复代码并通过测试，却没有在预算内提交最终答案？

Trace 只记录工具名、结果 Artifact 和上下文度量，不记录所有未执行 ToolCall 的参数，也不记录模型
内部意图。因此本文把可复现事实和解释边界分开。

## 2. Artifact 对应的真实文件

`read_file` 的输出格式是 `File "<path>":\n<content>`。使用同一格式重新计算 Case 文件的
SHA-256 后，可以确定 Trace 中三种读取结果：

| Artifact 前缀 | Bytes | 文件 |
|---|---:|---|
| `aeb7440a...` | 135 | `service_config/timeouts.py` |
| `262a4fe3...` | 1673 | `service_config/client_registry.py` |
| `ea0721f2...` | 389 | `tests/test_timeouts.py` |

两次出现的 `262a4fe3...` 是同一份客户端注册表，不是两个大小相近的未知文件。

## 3. 逐轮对照

“投影变化”是该次 ModelRequest 中被短引用替换的历史 ToolResult 数量，不是新增工具数量。

| Turn | baseline 行为 | projection 行为 | projection 变化/净节省 |
|---:|---|---|---:|
| 1 | `list_files` | `list_files` | 0 / 0 B |
| 2 | `search_text` | `search_text` | 0 / 0 B |
| 3 | 读取 `timeouts.py` | 读取 `timeouts.py` | 0 / 0 B |
| 4 | 返回 1 个未进入运行时的 ToolCall | 同轮读取注册表和测试 | 1 / 2144 B |
| 5 | 修改 `timeouts.py` | 修改 `timeouts.py` | 1 / 2144 B |
| 6 | 运行相关测试 | 运行相关测试 | 2 / 3743 B |
| 7 | 读取注册表 | 再次读取注册表 | 2 / 3743 B |
| 8 | 输出最终答案 | 执行 `git_diff` | 2 / 3743 B |
| 9 | — | 返回 1 个未执行 ToolCall，随后 `max_turns` | 3 / 5342 B |

前三轮的工具、Artifact、Token 和上下文 bytes 完全一致。第 4 轮是第一个分叉点，也是第一个实际
发生投影的请求。

## 4. “证据被挤出”是怎样发生的

`plan_tool_result_retention()` 保护两类结果：错误结果，以及 Conversation 尾部连续的最新一批
ToolResult。已经被模型看过、又不属于尾部最新批次的结果可以进入压缩候选。

这条规则在本次 projection 中形成了下面的生命周期：

1. 第 3 轮模型已经看过完整搜索结果，然后请求读取 `timeouts.py`。
2. 第 4 轮，`timeouts.py` 成为最新结果；较早的 2730-byte 搜索结果首次被替换为引用。
3. 第 4 轮模型没有调用 `read_tool_result`，而是直接读取注册表和测试文件。
4. 第 6 轮，修改结果成为最新批次；较早的大搜索结果和注册表结果都可以被压缩，变化数升到 2。
5. 第 7 轮模型再次读取注册表。第 8 轮请求中，这份新结果仍位于历史尾部，所以保留全文；模型此时
   确实能够看到 25 个客户端及首尾名称。
6. 第 8 轮模型选择执行 `git_diff`，而不是直接回答。第 9 轮中，`git_diff` 成为最新结果，刚刚读取的
   注册表不再属于最新批次，变化数从 2 升到 3，全文再次被替换为引用。
7. 第 9 轮模型又返回一个 ToolCall，但达到 `max_turns` 后没有执行，也没有最终答案。

这说明当前规则保证的是“新结果至少完整展示一次”，不是“完成任务前持续保留重要证据”。对普通
Coding 信息，展示一次后压缩通常合理；对必须在最终答案中复述的证据，模型若在取回证据后又执行
别的工具，就可能再次失去全文。

## 5. 能确认与不能确认的结论

可以确认：

- 第 4 轮首次投影与两组轨迹首次分叉发生在同一轮；
- projection 没有使用 `read_tool_result`，而是直接读取 Workspace 文件；
- 注册表在第 7 轮重新读取后，第 8 轮保留全文，第 9 轮因 `git_diff` 后移而重新变成引用；
- projection 的代码修改、测试和变更范围都正确，失败点是没有在轮次内形成最终回答。

不能确认：

- 不能仅凭时间相邻证明“压缩导致模型选择了哪些工具”；真实模型采样本身也可能产生不同轨迹；
- Trace 没有保存第 9 轮未执行 ToolCall 的名称和参数，不能声称模型当时一定想再次读取注册表；
- 单个 projection 失败样本不能估计任务成功率，也不能证明把轮次从 9 增大就能稳定成功。

## 6. 暴露出的两个独立设计问题

1. **证据保留窗口问题**：只保护最后一批结果，可能让刚恢复的终局证据在一次常规检查工具之后再次
   被压缩。这是 Context Projection 的设计问题。
2. **终止预算问题**：模型在测试成功后仍有读文件、看 diff 等合理行为，但 Harness 没有为最终回答
   预留一轮，也没有在预算临界点限制继续调用工具。这是 Query Loop 的预算/终止问题。

二者不能混成一个修复。直接增加 `max_turns` 只能延后停止，不会解决证据再次被压缩；直接扩大保留
范围也不能保证模型会在预算内结束。

## 7. 下一小步建议

先只处理第一个问题，做一个离线、确定性的“最近两批结果保留”候选实验：

- 不立即替换现有策略；先新增配置化候选并用 Scripted Model 重放“读取证据 → `git_diff` → 最终回答”；
- 验证注册表在 `git_diff` 后仍保持全文，同时计算增加的请求 bytes；
- 保留现有“一批窗口”作为对照；
- 只有候选在信息可用性和成本两方面都通过，才讨论新的真实协议。

终止预算保护单独排在其后，避免一步同时修改两个变量而无法解释效果。
