# MiniCode：Skill 分层组织、二阶段路由与按需加载

资料性质：简历全部完成前提下的模拟面试参考设计；细节采用本文件统一方案，不是当前源码核验结论。

## 问题：原子 Tool、深层 Skill 与 Skill 目录怎样分层？

检索词：Skill 分层、原子 Tool、深层 Skill、能力目录、Skill Catalog。

主回答：原子 Tool 是能实际执行的动作接口；深层 Skill 是某类专业任务的方法包，描述适用条件、步骤、约束和验收；Skill 目录保存轻量能力入口和元数据，帮助先缩小候选范围。它们分别对应动作、方法和组织索引，不是三个独立模型。

例子：read_file/edit_file/run_tests 是动作；跨文件契约修改是一套方法；目录负责把它与只读诊断、单测修复等方法区分。目录不应一开始就包含全部正文。

## 问题：Skill Manifest 需要哪些元数据？

检索词：Manifest、元信息、name、description、tags、示例、适用边界。

主回答：除稳定标识、名称、描述、正文入口和版本外，完成版方案把任务意图、语言/仓库条件、相关标签、适用与不适用边界及简短任务示例作为路由信息。需要的工具可以作为能力约束，但声明依赖不等于授予权限。

验证：字段合法只是第一步，还要验证目录和入口没有越界、同名版本不冲突、示例没有混入验收答案、正文与元数据没有明显矛盾。

## 问题：意图识别如何帮助 Skill 路由？

检索词：意图识别、任务分类、路由、debug、repair、诊断、重构。

主回答：先把任务描述规范化成任务类别、语言、只读/可修改要求等有限特征，再用它们缩小适用范围。这里不强行引入额外模型，清晰场景可以用规则与标签映射；不确定时保留候选或澄清，而不是假装分类必然正确。

边界：只读任务不应因为某个方法相关，就选入要求修改文件的流程。意图识别是路由依据，不决定最终执行权限。

## 问题：二阶段召回与精排具体怎么实现？

检索词：两阶段检索、召回、精排、候选集、排序、适用性。

主回答：完成版先用意图、名称、描述、标签和简短示例做低成本候选召回，排除明确违反硬条件的方法；再对候选检查适用边界、意图覆盖、词项和示例匹配、冲突与正文成本，排序后选择有限数量。先广覆盖，再收紧选择，避免一开始读取所有正文。

统一参考算法：先比较明确适用性和意图匹配，再比较标签/文本及示例匹配程度，最后使用加载成本和稳定 ID 决定同分顺序；不虚构未给出的权重。精排在这里是候选细排序，不自动意味着使用 Cross-Encoder 或 LLM。

验证：分别统计第一阶段漏召回与第二阶段错序；第一阶段漏掉的结果不能由精排凭空找回。

## 问题：为什么不直接用 Embedding 或大模型挑 Skill？

检索词：Embedding、语义检索、关键词、LLM 路由、复杂度。

主回答：方案需要和规模匹配。目录较小时，可解释的元数据和规则便于调试、测试和版本固定；语义检索能改善改写覆盖，但增加索引维护和误召回问题，模型路由还增加延迟与成本。应先用错选、漏选和任务效果证明必要性，再决定替换召回或排序。

不要扩写：本包没有设定已使用向量数据库、BM25、学习排序或模型微调，不为回答专业而堆技术栈。

## 问题：Skill 按需加载发生在哪里？进入 messages 吗？

检索词：懒加载、按需加载、SKILL.md、instructions、system、message_history。

主回答：先发现 Manifest 和路由，选中后才读取 SKILL.md 正文；QueryLoop 把方法文本放入独立 instructions，不伪造用户或工具历史。Provider 适配器再按其协议把 instructions 转成前置指令消息。因此内部不属于 conversation 的正文，发送时仍然会成为模型输入。

未选中正文不读取；加载不是执行 Tool，也不意味着方法中的每一步被程序强制按顺序完成。

## 问题：为什么任务开始时加载一次，而不是每轮切换？

检索词：动态加载、Skill 快照、版本一致性、resume、每轮请求。

主回答：同一个任务先固定方法版本，避免磁盘正文变化或工具输出中的偶然词改变指导，也减少重复路由与读取。后续请求仍携带该指令，恢复使用保存的快照。

代价：中途发现新领域时不会自动换方法；动态切换需要额外定义版本、去重、冲突、预算和恢复。本简历能力完成不自动包含热插拔。加载一次也不等于只产生一次输入 Token。

## 问题：怎样减少 Skill 噪声、重叠和 Token 成本？

检索词：检索噪声、功能重叠、召回空间、Top-K、上下文成本。

主回答：先按目录和适用边界缩小范围，再限制正文数量及总大小；同一能力的版本建立替换关系，不同时注入新旧正文。相关不等于必须选中，过小收益或明显冲突可以不加载。

成本来源不仅是加载耗时，还有正文每轮重发和方法引导增加的调用。不能只用路由命中率或单轮正文减少证明整任务变便宜。

## 问题：Skill 怎样随着经验增长？怎么避免不断堆积？

检索词：Skill 生长、版本、去重、经验提升、回滚、方法发布。

主回答：完成版只允许经过来源核对和验证的经验成为候选方法。先判断已有 Skill 是否能修订，再考虑新增；更新明确适用范围、版本和替换关系，用独立任务检查收益与回归，经受控发布后才进入目录，保留回滚路径。

边界：不是每次成功都自动新增 Skill，也不允许模型直接改权限或删除审计。经验候选、已发布方法和用户偏好必须分开。

## 问题：怎样验证 Skill 路由和任务效果？

检索词：Skill evaluation、漏选、多选、排序、负例、任务对照。

主回答：离线评测检查预期 Skill、候选覆盖、漏选、多选和顺序，包含相似方法、无关任务、同义改写、正文损坏和越权指令。任务级再固定模型、任务、预算和版本，比较开关两组的验收结果、实际调用和完整用量。

关键区别：路由对了不等于任务成功，任务成功也不证明是 Skill 带来的提升；没有对照或原始记录，就不报提升数字。
