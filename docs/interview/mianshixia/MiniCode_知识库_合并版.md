## 一、项目定位与执行主链

### Q01：MiniCode 是做什么的，五个项目亮点怎样连成闭环？

检索词：MiniCode、项目介绍、可恢复 Coding Agent、QueryLoop、工具治理、上下文、Skill、Checkpoint、Benchmark。

主回答：MiniCode 是面向 Python 仓库编码任务的 Agent 运行原型，覆盖代码观察、局部修改、测试和任务恢复。模型基于上下文提出工具调用，程序负责参数校验、审批、调用预算和超时；旧工具结果可以按预算替换为可回读引用；Skill 通过元数据路由后才加载正文；执行结果保存为检查点并通过事件审计，最后由固定任务的独立验收检查交付。

设计重点：把模型决策与执行权限、完整状态与模型视图、循环完成与任务正确性分别拆开。它不是通用部署平台，也不包含本版简历没有列出的自动长期记忆、Skill 生长或语义摘要体系。

证据边界：本版简历标注 2025-12—2026-04；初版与后续迭代、本人职责和实验数据仍需本人确认，不能由“能力完成”推导生产规模或收益数字。

### Q02：MiniCode 为什么需要 Harness，而不是只写一个 Prompt？

检索词：MiniCode、Harness、Agent Runtime、Prompt Engineering、Context Engineering、运行框架。

主回答：Prompt 只能引导模型，不能替程序执行权限、保存状态和验证结果。MiniCode 的 Harness 是模型外的运行支撑，包括 QueryLoop、工具协议、策略审批、预算、上下文组装、Checkpoint、Event 和评测。模型决策有不确定性，但关键执行边界和状态处理尽量用确定性代码实现。

术语区别：Prompt Engineering 关注指令如何表达；Context Engineering 关注这一轮给模型哪些指令、历史和证据；Harness 则还包括执行、恢复和评测。三者相互配合，不是互相替代。

### Q03：MiniCode 一条编码任务从输入到结束怎样流转？

检索词：MiniCode、CLI、CodingAgent、QueryLoop、ModelRequest、ToolCall、ToolResult、执行主链。

主回答：CLI 解析任务和配置，组装工作区、模型、工具、策略与状态依赖。新任务先按配置从最近用户任务选择 Skill，只加载命中正文；QueryLoop 用完整历史、固定及 Skill 指令、工具定义构造请求，经过可选上下文投影后发给模型。收到调用先检查循环与调用预算，再由 Dispatcher 校验参数、判断权限并请求必要审批，工具返回结果后写入历史、事件和 Checkpoint，继续下一轮。模型不再请求工具或触发停止条件时返回结果。

实现要点：历史同时保留 ToolCall 和对应 ToolResult，拒绝和预期工具错误也有明确反馈；普通运行不会自动调用 Benchmark 隐藏验收，也没有启动跨任务记忆检索。

验证方法：用脚本模型固定读、改、测和最终回答，检查每轮实际请求、调用匹配、停止原因及文件变化，再用独立验收检查任务。

### Q04：MiniCode 的 ModelRequest 为什么把 conversation、instructions 和 tool_specs 分开？

检索词：MiniCode、ModelRequest、conversation、instructions、tool_specs、消息协议。

主回答：conversation 保存真实消息和工具交互，instructions 放固定及可选 Skill 指导，tool_specs 描述本轮允许模型选择的接口。分开以后可以独立测试指令注入、历史保真和工具可见性，Projector 也不必通过伪造用户消息来改变模型视图。

实现要点：适配器将三类内容转换成 Provider 要求的消息与工具参数。内部历史中的调用和结果需按协议归并，ToolCall 与 ToolResult 通过 ID 对应；提供工具定义本身不执行工具，也不绕过后续 Policy。

验证方法：捕获真实请求，检查 Skill 不混入 history、工具参数 Schema 来自注册合同、工具结果对应正确调用，不能只看最终回答是否提到某个工具。

### Q05：MiniCode：CodingAgent 和 QueryLoop 有什么区别？是否可以去掉外层 Agent？

检索词：MiniCode、CodingAgent、QueryLoop、组装、依赖注入、薄封装。

主回答：QueryLoop 是维护请求、响应、工具反馈和停止条件的核心执行引擎。CodingAgent 提供面向编码任务的 run/resume 入口，组装函数连接具体模型、工具和策略。外层可以很薄，直接调用 QueryLoop 在技术上也成立；保留它是为了稳定产品入口，而不是多造一层自主智能。

取舍：抽象应服务于替换模型、工具或执行器等真实需求；如果一层只转发参数且没有明确边界，就不应为了架构图复杂而保留。

### Q06：MiniCode：为什么选单 Agent，不直接做规划、执行、审查多个 Agent？

检索词：MiniCode、单 Agent、多 Agent、Planner、Executor、Reviewer、Agent Team、架构取舍。

主回答：MiniCode 优先解决单任务的可靠执行。代码定位、编辑、测试之间有较强状态依赖，拆成多个 Agent 会增加通信成本、证据同步和文件冲突。先用单 Agent 配合外部确定性检查，能够减少不必要的协调。只有子任务可独立并行、收益能覆盖通信和恢复成本时，才考虑引入多 Agent。

不要扩写：多工具不等于多 Agent，Skill 分层也不意味着多个独立模型。

### Q07：MiniCode 是否硬编码了“先读文件、再编辑、再测试”的顺序？

检索词：MiniCode、Agent 与 Workflow、固定指令、读改测、测试门禁。

主回答：固定指令建议先观察、最小修改、检查差异并运行相关测试，但具体定位和工具选择仍由模型根据上下文决定。QueryLoop 硬性执行的是预算、协议和工具调用边界，不是完整的读改测状态机。

取舍：模型能灵活调查，也可能漏步骤或重复调用；程序不能因为提示词写了要求就宣称已保证遵守。Benchmark 可按案例检查修改后测试及禁止动作，普通运行不会因此自动获得相同验收门禁。

验证方法：脚本模型故意直接给最终回答或漏测试，检查循环可能正常结束而独立验收仍拒绝，说明收尾与正确性是两层。

### Q08：MiniCode 能从零搭建并部署完整项目吗？工具是不是太少？

检索词：MiniCode、端到端开发、项目搭建、工具数量、能力边界、部署、依赖安装。

主回答：MiniCode 的目标是已有 Python 仓库中的代码理解、局部修复和测试，不把它定义成任意项目搭建与部署平台。现有工具覆盖文件发现、读取、搜索、创建、编辑、差异检查和测试，是否足够应按目标任务评估，而不是按工具数量判断。依赖安装、后台服务、数据库和部署属于额外能力，需要新的权限与生命周期管理。

边界：能创建文件不等于已验证复杂项目搭建；不能因为简历完成，就补写全栈生成、云端部署和生产运行经历。

### Q09：MiniCode 从零实现与借鉴公开 Agent 思路有什么区别？

检索词：MiniCode、从零实现、架构参考、Coding Agent、开源、个人贡献。

主回答：从零实现指在项目中显式组织 QueryLoop、数据合同、工具边界和恢复评测，不代表发明了 Tool Calling 或不参考公开设计。可以解释与成熟 Coding Agent 共有的多轮工具反馈、上下文治理和受控执行原则，但不能声称读过闭源内部源码或完整复刻某产品。

边界：具体参考资料、AI 辅助和本人实现范围要由本人确认。本版简历没有要求必须用 Claude Code 的某种内部机制，也不因此补写其全部能力。

### Q10：MiniCode 最值得讲的设计取舍是什么？

检索词：MiniCode、设计亮点、核心取舍、模型权限、模型视图、独立验收。

主回答：第一，提示词引导模型，但权限由程序在副作用前检查。第二，完整历史保留，模型请求只按预算提供需要的视图，避免压缩破坏原文恢复。第三，检查点支持继续同一任务，却不承诺外部副作用恰好一次；任务最终正确与否另用独立验收。Skill 则在不扩大工具权限的前提下提供可选方法指导。

表达要求：用一条任务链和一条异常测试说明设计，不把模块多或抽象层多直接当成创新；个人贡献需要实际事实支持。

### Q11：MiniCode：为什么不直接用现成 Agent 框架？自己实现有什么代价？

检索词：MiniCode、框架选型、自研、LangChain、LangGraph、QueryLoop、可控性。

主回答：MiniCode 的目标之一是显式理解和验证循环、权限、状态与上下文边界，所以采用较小的核心协议，便于插入脚本模型、故障与独立检查。这不代表现成框架不可靠，也不意味着自写一定更简单或更快。

代价：需要自己维护 Provider 兼容、消息顺序、异常传播、恢复格式和测试，功能生态也更有限。选型应由任务范围和验证成本决定；若后续引入框架，仍需检查它能否保留当前执行不变量，而不是用新框架替换所有理解。

个人贡献边界：采用某个架构不自动证明全部独立实现；具体参考和 AI 辅助范围必须如实确认。

## 二、执行循环、模型适配与工具治理

### Q12：MiniCode 的结构化 Tool Calling 怎样实现？

检索词：MiniCode、Tool Calling、Function Calling、ToolCall、ToolResult、call_id、工具定义。

主回答：把工具名称、描述和参数 Schema 提供给模型，模型只返回候选调用。适配器解析协议，Dispatcher 查找注册工具、验证参数、评估策略并请求必要审批，工具执行后用相同 call_id 返回结果。模型下一轮通过这些结果继续决策。

关键边界：模型响应解析、Pydantic 参数校验、路径语义检查、权限判断是不同层。JSON 合法不代表参数正确，更不代表获准执行。

### Q13：MiniCode：为什么要使用工具注册表和白名单？

检索词：MiniCode、Registry、Dispatcher、白名单、未知工具、默认拒绝。

主回答：注册表限定程序实际提供的能力，模型不能通过编造工具名调用任意函数。工具策略默认拒绝未配置能力；显式列出的读取类操作可以允许，有副作用的操作要求审批或拒绝。注册能力、向模型展示定义、批准某次执行是三个不同动作。

验证：请求未知工具、重复注册、未配置策略和伪造名字时，程序应明确拒绝且不产生副作用。

### Q14：MiniCode：Pydantic 的 strict、extra forbid、frozen 分别做什么？

检索词：MiniCode、Pydantic、Schema、strict、frozen、extra forbid、参数校验。

主回答：strict 限制宽松类型转换，extra forbid 拒绝未定义字段，frozen 限制普通赋值修改。它们固定工具输入合同，但不证明路径在工作区内、替换文本唯一或用户已批准；这些还需要策略和工具内部校验。

例子：字符串路径能通过类型检查，却仍可能越界；编辑参数字段齐全，也可能找不到唯一的旧文本。

### Q15：MiniCode 的 ALLOW、ASK、DENY 策略怎样约束工具？

检索词：MiniCode、ToolPolicy、ConfiguredToolPolicy、ALLOW、ASK、DENY、工具权限。

主回答：Dispatcher 查到工具并验证参数后，查询可信程序配置。ALLOW 可进入工具执行，ASK 必须取得审批，DENY 直接返回拒绝；未配置策略默认拒绝。默认读取、搜索和查看差异允许，创建、编辑与运行测试要求审批。获准后工具仍校验路径和操作条件。

取舍：当前按工具名配置策略，容易解释和测试，但不是模型风险评分、完整参数级授权或任意操作的安全判断。模型和 Skill 不能修改策略，也不能用工具结果中的“已批准”代替真实审批。

验证方法：覆盖未知策略、缺审批者、拒绝及批准，检查没有批准时实际文件和进程未发生相应副作用。

### Q16：MiniCode：用户拒绝编辑后，MiniCode 怎样处理？

检索词：MiniCode、审批拒绝、用户拒绝、ToolResult、is_error、工具预算。

主回答：不执行编辑，返回与调用 ID 对应的拒绝结果，历史保留调用和拒绝证据，模型可以停止、解释或改选允许的动作。拒绝并不必然结束整个任务。

计数口径：Runtime 正常返回拒绝或校验错误也算一次调用尝试，避免反复失败绕过预算；实际成功执行次数另行统计。执行过程抛出意外异常则进入异常路径，不能假装收到成功结果。

### Q17：MiniCode：Skill 告诉模型“无需审批”，能绕过编辑权限吗？

检索词：MiniCode、Skill 越权、提示词、审批绕过、权限继承。

主回答：不能。Skill 只影响模型提出什么请求，Dispatcher 仍按可信策略检查。模型就算直接返回 edit_file，也需要通过 ASK 审批；正文不能自行提高权限。

验证：用脚本模型固定提出编辑调用，加载要求跳过审批的 Skill，让审批者拒绝。检查实际发生审批、文件未变、拒绝结果与 call_id 正确对应。真实模型可能不提出编辑，不能单靠它验证程序分支。

### Q18：MiniCode 怎样约束仓库和工具输出中的提示注入？

检索词：MiniCode、Prompt Injection、README、工具结果、Skill、伪造审批。

主回答：仓库内容和工具结果作为待分析数据，不因包含“忽略规则”或“用户已批准”就成为新授权。固定指令明确这些来源不授予权限，实际调用仍必须通过注册工具、参数校验、策略和审批；Skill 也不能越过这些边界。

边界：这不是已经实现能识别所有恶意文本的语义防火墙。数据可能影响模型判断，文件中的秘密或模型直接回答泄漏还需另行治理，工具审批不覆盖所有风险。

验证方法：在受控夹具中放入诱导越界读取或跳过审批的内容，检查实际调用、审批和文件变化，不只看模型口头说拒绝。

### Q19：MiniCode：Workspace 是不是安全沙盒？为什么不直接把 cwd 指向项目目录？

检索词：MiniCode、Workspace、沙盒、sandbox、cwd、路径校验、open。

主回答：Workspace 校验经过自身方法的文件访问；cwd 只是进程开始运行的目录。测试代码直接调用 open 或创建子进程，不会自动走 Workspace，因此它们不是 OS 级隔离。路径检查、固定 argv、环境白名单和审批能降低风险，但不能代替进程级沙盒。

范围：本知识库不追加“已实现沙盒”的经历。进程隔离是额外设计议题，可讨论容器、默认断网、最小文件暴露、资源限制和整体清理，但不能把方案说成已上线能力。

### Q20：MiniCode 循环有哪些停止原因？COMPLETED 等于任务成功吗？

检索词：MiniCode、StopReason、COMPLETED、MAX_TURNS、MAX_TOOL_CALLS、TOKEN_BUDGET、USAGE_MISSING。

主回答：模型响应返回后，先处理已配置的用量门禁；没有工具调用时保存完成状态并返回 COMPLETED。有调用但缺执行器、达到轮数或本批会超过工具调用预算时，以不同原因返回。异常、取消和总超时另保留各自语义，不能都叫正常完成。

关键边界：COMPLETED 只表示循环收尾，不证明代码满足需求；Benchmark 再检查结果、运行、预算和过程约束。累计 Token 阈值主要在响应后核对，当前响应可能已经跨过阈值，不是预付费式硬账单上限。

验证方法：覆盖无调用、最后一轮仍请求工具、调用额度不足、缺 usage 和工具执行异常，检查停止分支没有继续产生不允许的动作。

### Q21：MiniCode 一次响应请求三个工具，但只剩两次额度，会执行前两个吗？

检索词：MiniCode、工具批次、剩余额度、MAX_TOOL_CALLS、MAX_TURNS、停止顺序。

主回答：当前在执行本批前比较已用调用数加整批数量，超过就返回 MAX_TOOL_CALLS，不部分执行前两个。这样同一响应的调用不会因为临时额度只执行一部分，但也意味着可能保留未使用额度。

停止顺序：已经收到响应后先检查配置的用量门禁；没有工具调用可以正常完成；最后允许轮次仍提出调用则返回 MAX_TURNS，不继续执行。最后一轮没有调用与最后一轮仍请求工具，结果不同。

验证方法：构造剩余两次但提出三次、额度恰好够、最后一轮两种响应，以及 usage 超阈值的脚本，检查实际 Runtime 调用次数与停止原因。

### Q22：MiniCode：工具超时、取消和错误如何反馈？

检索词：MiniCode、超时、timeout、CancelledError、预期异常、进程树、失败恢复。

主回答：预期工具失败转成带调用 ID 的错误结果，供模型调整；程序意外异常、取消和整任务超时保留各自语义，不能全部吞成成功。限制输出防止内存无限增长，记录失败发生在审批、工具还是模型阶段。

边界：终止直接子进程不等于清理整个后代进程树，超时也不会自动撤销已经写入的文件或外部副作用。

### Q23：MiniCode：已经使用模型 SDK，为什么还需要 Model Adapter？

检索词：MiniCode、模型适配器、SDK、ModelRequest、ModelResponse、Provider、依赖反转。

主回答：SDK 负责连接某个服务，Adapter 负责把项目自己的消息、工具定义和结果转换成 Provider 协议，再把响应、用量和错误归一化。QueryLoop 只依赖项目合同，不直接依赖某个 SDK 的 choices、usage 或 tool_calls 细节。因此脚本模型和真实模型可以共用循环。

实现要点：请求转换要维持助手调用与工具结果的关联；响应解析要验证调用 ID、名字与参数结构；错误映射不能把鉴权、限流和配额耗尽全部包装成一个无法定位的异常。

验证：分别测试请求转换、响应解析与循环执行；换 Adapter 不应改变审批和预算规则。兼容相同请求外形，不代表所有 Provider 行为完全相同。

### Q24：MiniCode：模型返回的工具参数不是合法 JSON，或缺少调用 ID，怎么办？

检索词：MiniCode、非法 JSON、ModelProtocolError、工具参数、call_id、Schema 校验。

主回答：先区分协议解析失败和已识别调用的参数校验失败。JSON 不能解析、解码后不是对象或调用身份不完整时，在模型边界报告协议错误，不随意补一个 ID、修正文字符后执行。调用身份完整但参数不符合工具合同，则可以返回对应调用的校验错误。

取舍：可另行设计有限次的模型纠正，但它需要清楚的预算和反馈合同，不能把“程序通常能猜对”当可靠性。当前项目主链不能被描述成已经有任意 JSON 自动修复。

验证：覆盖缺 choices、未知调用类型、数组代替参数对象、错误字段类型、重复或缺失 ID；每条失败都检查没有进入工具副作用阶段。

### Q25：MiniCode：哪些模型错误适合重试？重试会不会重复修改文件？

检索词：MiniCode、重试、限流、配额、连接失败、鉴权、退避、幂等。

主回答：鉴权、权限、模型不支持或余额不足通常需要改变配置，盲目重试无益；临时限流、连接或服务故障可在明确次数和总时限内考虑退避。请求超时可能已经被服务处理，重试还可能增加费用，不能假定第一次没有发生。

必须区分三层：SDK 请求重试、QueryLoop 新一轮决策、工具副作用重试。模型请求重试不应顺带重新执行此前已记录的工具。外部工具重试需要单独评估幂等性，不能复用模型重试逻辑。

项目口径：普通客户端与评测入口的重试配置应分别说明；现有普通客户端默认允许 SDK 重试，评测入口设为 0，以减少隐藏尝试对比较的影响。不能说评测为 0 就消除了所有重试或外部失败。

### Q26：MiniCode：Temperature 设为 0，为什么结果仍可能不同？

检索词：MiniCode、Temperature、采样、确定性、重复实验、seed、模型版本。

主回答：低随机性设置不等于整个运行可复现。模型服务的具体执行、版本和数值行为可能变化，工具输入、文件状态和网络错误也会改变后续路径；而且参数是否生效要由 Provider 接口确认。即使固定 seed，也只能按该服务承诺理解，不能保证绝对一致。

验证：固定模型版本、初始工作区、完整请求、参数和预算，重复运行并比较轨迹与结果。重复用于检查稳定性，不能代替不同任务的覆盖。

边界：不能因为一次模型结果不同就认定是 Temperature 失效，也不能把项目某个评测配置扩写成所有入口都采用相同采样设置。

### Q27：MiniCode：流式响应中的 ToolCall 能不能边收到参数边执行？

检索词：MiniCode、流式、stream、delta、ToolCall 拼接、finish reason、不完整响应。

主回答：不能把未完成的参数片段当成合法调用执行。流式返回可能拆开工具名、调用 ID 和 JSON 参数，需要按调用索引归并片段，在确认结束状态并完成解析后，才得到可交给 Dispatcher 的 ModelResponse。可以逐步展示文本，但展示与执行是两条边界。

异常：中途断开、缺结束状态、因长度截断或最后参数损坏，都不能因为已经显示了一段文字就当正常完成。失败时关闭流，记录已收到的状态，不虚构完整结果。

范围：适配器存在流式接口，不代表 QueryLoop 或 CLI 已经端到端采用流式执行，也不代表多个工具正在并行运行。

### Q28：MiniCode：为什么选择当前模型？如何比较更强或更便宜的模型？

检索词：MiniCode、Qwen、模型选型、工具调用能力、成本、时延、可复现评测。

主回答：模型选型应按本项目任务验证，而不是只看通用榜单。比较工具协议合法率、任务独立验收、错误恢复、完整用量和时延，同时核对接口可用性、预算及数据要求。更便宜的单 Token 价格可能被更多调用抵消，更强模型也不保证值得全部替换。

项目表达：已知项目使用 Qwen/DashScope 接口，但具体为何选定、是否比较过其他模型，需要本人提供实际记录。没有对照时只能解释选择标准和已有配置，不能编造“压测多个模型后最优”的经历。

验证：模型比较固定同一任务集、初态和执行策略，允许按预先定义的合理参数运行；不临时换题或只保留获胜案例。

### Q29：MiniCode：edit_file 为什么使用唯一精确替换？匹配零处或多处怎么办？

检索词：MiniCode、edit_file、old_text、new_text、精确替换、多处匹配、最小修改。

主回答：精确替换要求模型明确现有内容，有助于把修改限制在观察过的位置。旧文本不存在就拒绝，出现多处也拒绝，而不是猜一个位置或全部替换；成功时只替换唯一目标，并检查修改前后大小。失败结果反馈给模型，让它重新读取或提供更具体上下文。

取舍：格式、空白或并发变化都可能让精确匹配失败，复杂重构不如 AST 或 patch 灵活；但合同容易测试，适合局部修复。不能把缺旧文本自动当“以前已经成功”。

验证：空目标、零匹配、多匹配、唯一匹配、修改后超限、文件变化和不允许的路径都要覆盖，失败后文件应保持原状。

### Q30：MiniCode：create_file 为什么不能先判断不存在，再普通写入？

检索词：MiniCode、create_file、禁止覆盖、排他创建、TOCTOU、os.link。

主回答：先检查再写有竞争窗口，检查后别的进程可能创建同一路径。创建合同应在最终提交时拒绝已有目标，例如采用排他创建，或在适用文件系统上先写临时文件，再用不覆盖既有目标的发布方式。MiniCode 的创建路径采用临时文件与硬链接发布，目标存在时不能静默覆盖。

边界：检查权限、父目录、文件系统支持和失败清理；路径检查本身仍有并发风险，不应把单个发布操作的原子性说成完整文件系统事务。[Python os 文档](https://docs.python.org/3.12/library/os.html#os.link)

### Q31：MiniCode：为什么不能只用字符串前缀判断路径在工作区内？

检索词：MiniCode、路径逃逸、resolve、is_relative_to、符号链接、TOCTOU、普通文件。

主回答：字符串前缀会混淆相似目录名，也无法正确处理父级跳转和符号链接。应先规范化并解析目标，再按路径层级判断是否在允许根目录内，同时检查操作所需的文件类型。

边界：解析、检查和打开不是同一个原子动作，检查后符号链接或目录仍可能被替换；FIFO、设备文件也不能只凭路径合法就放心读取。更严格边界需要描述符相对访问、文件类型限制或 OS 隔离，不能声称现有 Workspace 消除了全部并发逃逸。

验证：相似前缀、绝对路径、父级跳转、内部/外部符号链接和特殊文件使用隔离临时环境验证，不碰真实敏感文件。

### Q32：MiniCode：搜索结果有限制时，“没有匹配”能证明仓库里不存在吗？

检索词：MiniCode、search_text、截断、max_results、跳过文件、搜索范围、不完整结果。

主回答：只能说明在本次实际检查的范围内没有匹配。目录剪枝、非文本文件、大小上限、文件数上限和结果截断都可能让搜索不完整。工具合同应尽量表达搜索范围、跳过与截断状态，引导缩小路径或关键词；没有这些信息时不能把有限结果解释成全仓库证明。

项目细节：搜索采用字面文本而非任意正则；目录搜索可跳过非 UTF-8 或超大文件，结果达到数量上限就停止。不能声称当前任意输出都已经有完整分页或结构化截断元数据。

验证：匹配位于排除目录、超大文件和上限之后时，应测试系统不会把“未看到”当作“确定不存在”。

### Q33：MiniCode：run_tests 怎样避免命令拼接？测试失败和执行失败怎样区分？

检索词：MiniCode、run_tests、pytest、argv、shell、退出码、stdout、stderr。

主回答：把 Python、模块参数与测试路径作为固定 argv 传给执行器，不拼接 shell 字符串；路径先验证，防止被当成额外选项。进程正常返回但退出码非零时报告测试失败；无法启动、超时、输出超限和取消属于不同执行问题。

取舍：stdout/stderr 与退出码一起保留，不只匹配“passed”字符串；但固定 pytest 命令仍会执行项目 Python 代码，所以不等于安全沙盒。

验证：正常通过、断言失败、无效路径、启动失败、持续输出与长时间运行分别检查结果类别及副作用。

### Q34：MiniCode：两个任务同时编辑一个文件，或者用户中途改了文件怎么办？

检索词：MiniCode、并发编辑、文件冲突、用户插入、版本检查、丢失更新、工作副本。

主回答：单 Agent 中顺序执行工具，不代表宿主机不存在其他写入者。精确替换能发现部分内容不匹配，但不能保证读后到提交前没有变化。应明确支持范围：隔离任务工作副本、串行写入，或在提交时做版本/锁保护；只比较一次 hash 仍有检查后变化的窗口。

范围：不把现有顺序循环包装成已实现并发合并。运行中收到新要求，也不能无条件混进旧任务；需定义停止、排队或创建新 Run 的规则，当前知识库不追加抢占调度经历。

验证：用受控第二写入者在读后改动目标，确认不静默覆盖用户修改；不能依靠肉眼看一次 diff 就宣称不存在竞争条件。

## 三、预算驱动的上下文管理

### Q35：MiniCode 现在采用怎样的预算驱动上下文策略？

检索词：MiniCode、预算驱动、BudgetedToolResultProjector、ToolResult 引用、原文回读。

主回答：程序保留完整执行历史，每轮先构造完整请求；开启预算模式后，只有规范化请求超过配置 byte 预算，才选择可恢复的旧工具结果替换为短引用。近期批次、错误结果、排除工具和无法完整回读的输出保留；替换还要计入新增回读工具定义并满足净节省要求。需要细节时模型可按 call_id 回读原文。

范围：这是确定性的引用投影，不调用摘要模型，不存在摘要层、中间指导层、最终结果层的自动生成，也没有跨任务记忆接入。默认 identity 不压缩，开启需要显式配置。

验证方法：同时核对模型请求变化、原始历史不变、真实回读和整任务验收，不把请求变小直接当作成本收益。

### Q36：MiniCode 的完整历史、模型 Request 与 Checkpoint 为什么分开？

检索词：MiniCode、message_history、canonical_request、projected_request、执行状态、恢复。

主回答：完整历史记录用户消息、模型已提出的调用及真实工具结果；Request 是本轮给模型的信息；Checkpoint 持久化恢复所需状态。Projector 只产生另一份模型视图，下一轮仍从完整历史重建，不从上轮裁剪文本继续丢信息。

取舍：保留原文让当前 Run 可回读，也能复查执行证据，但内存和磁盘增长没有因此解决。最终回答在 RunResult.response 中，不应把 history 误叫包含所有输出的完整审计档案。

验证方法：对同一原始请求投影多次，检查原对象、返回历史和 Checkpoint 原结果未被替换为引用。

### Q37：MiniCode 怎样判断哪些历史工具结果可以进入压缩候选？

检索词：MiniCode、Retention、protected_recent、protected_error、excluded_tool、retrievable、批次。

主回答：先分类，再选择：近期 ToolResult 批次、错误、排除工具及超过完整回读能力的结果都保护，其余旧结果只是 eligible。预算规划器随后按历史顺序从较旧候选尝试替换，不是所有 eligible 都一定压缩。

批次含义：一段连续 ToolResult 可含多个调用结果，保护一批不等于保护一条。保护窗口是历史结构规则，不代表系统知道模型已经理解了较早内容。

验证方法：多结果批次、错误与近期重叠、超大结果和无候选都检查分类原因；系统指令、用户消息、普通助手消息与 Skill 正文不在当前 ToolResult 裁剪范围。

### Q38：MiniCode：旧工具结果的短引用包含什么？怎样回读？

检索词：MiniCode、read_tool_result、call_id、引用、原文、历史查询、恢复。

主回答：引用说明这里曾有历史输出，保留 call_id、原始大小与回读工具名；原 ToolCall 仍让模型知道当时做了什么。read_tool_result 只读取当前绑定 Run 中已保存的原 ToolResult，校验运行身份和大小，不重新执行搜索或读取当前文件。

工具历史和当前文件可能不同：回读回答“当时返回什么”，read_file 回答“现在文件是什么”。结果尚未生成、ID 不存在或 Run 不匹配都必须明确失败。

### Q39：MiniCode 为什么不把超过回读上限的历史结果也替换成引用？

检索词：MiniCode、完整回读上限、protected_not_retrievable、分页、不可兑现引用。

主回答：回读合同只承诺返回上限内的完整原结果，如果原文超过能力却仍替换，模型需要时就无法取回，引用承诺失效。因此该结果保留原文，不能为了压缩比例制造无法恢复的数据。

边界：分页是尚未包含的扩展，需要定义偏移、编码、总长度、截断、快照和错误行为。当前不能声称引用能恢复任意大输出，也不能拿语义摘要替代它没有提供的完整回读。

验证方法：上限内、恰好上限和超上限分别测分类及工具返回，未知 ID、pending 和 Run 不匹配检查明确错误。

### Q40：MiniCode 如何判断引用替换有净收益，为什么毛节省不够？

检索词：MiniCode、完整请求净节省、Tool Spec、minimum_net_savings_bytes、引用成本。

主回答：正文换成短引用只是毛节省；本轮如果新增 read_tool_result 定义，也占请求空间。规划时构造完整候选 Request，重新按同一规范化口径计量，只有净节省达到配置要求才采用；有引用时才向模型暴露回读定义。

取舍：这种计算只防止当前请求越裁越大，不保证后续回读和新增模型轮次后的累计 Token 更低。多条短结果的收益也要合并计算，不能逐条看到较短就宣称整个请求获益。

验证方法：构造毛节省为正但扣定义后为负的请求、多个候选合计才达标的请求，以及投影后实测大小与计划不一致的反例。

### Q41：MiniCode 已没有可压缩结果，但请求仍超预算，怎么办？

检索词：MiniCode、remaining_overflow_bytes、软预算、Provider 窗口、保护内容、压缩失败。

主回答：预算投影是受保护规则约束的尽力裁剪，不保证所有请求都达标。候选耗尽时保留可解释的剩余超额，不能偷偷删用户要求、系统指令或不可回读原文。实现侧 byte 目标还不等于 Provider 的硬 Token 窗口，两者需要分别处理。

当前边界：部分 Skill 与预算组合有投影后超限拒绝检查，不能扩写为任何配置都有统一的硬窗口预检；其他请求仍可能由 Provider 拒绝。缩小任务或调整受信配置应显式进行，不声称已有自动语义摘要或拆任务调度。

验证方法：仅由大用户消息、Skill 正文或近期错误组成的请求也要测试，确认没有破坏保护规则或把模型请求失败当作任务完成。

### Q42：MiniCode：没有特别大的输出，但很多小结果累积也超限，怎么办？

检索词：MiniCode、小结果累积、全请求预算、工具定义成本、历史增长、上下文组成。

主回答：这正是只用单条输出阈值不够的原因。应先看完整请求画像，区分工具定义、指令、用户内容和工具历史的占比；预算式策略可以合并考虑多个可裁剪小结果，但引用及回读定义必须有净收益。

边界：很多短结果换成引用可能反而更大，不能强制逐条替换。若主要成本来自方法正文或工具定义，继续裁剪结果也解决不了，要在对应的选择与加载环节治理；完整执行历史的内存增长仍是另一问题。

验证：小输出、大工具定义、大 Skill 和大量历史分别构造请求，确认计量与决策针对真实成本来源，而不是见超限就删 ToolResult。

### Q43：MiniCode 历史测试通过，但文件后来又改了，还能沿用结论吗？

检索词：MiniCode、历史工具结果、当前状态、run_tests、修改后重测、证据时效。

主回答：不能把旧测试成功当成本次修改成功。历史 ToolResult 回答某一时刻发生了什么，文件变化后要重新获取当前证据；read_tool_result 也只返回当时结果，不会替你重跑测试。评测可按案例要求检查最后一次修改之后有成功测试。

取舍：保留历史便于取证，不等于旧证据始终适用。差异检查说明改了什么，测试验证行为，两者不能互相替代。

验证方法：先测通过再引入错误、不相关测试通过、测试失败后直接结束等，都应由对应案例合同识别。

## 四、Skill 元数据路由与延迟加载

### Q44：MiniCode 的 Skill、Tool 和固定 Workflow 有什么区别？

检索词：MiniCode、Skill、Tool、Workflow、方法说明、执行权限。

主回答：Tool 是可执行动作及其参数合同，Skill 是供模型参考的方法说明，固定 Workflow 是程序预先定义的步骤和分支。MiniCode 选择 Skill 后仍由模型提出原子工具调用，Dispatcher 决定能否执行；加载一段 Skill 不会自动运行其中所有步骤，也不产生新权限。

项目边界：本版是元数据路由与正文延迟加载，没有另设深层 Skill、独立意图分类或自动能力生长体系。

验证方法：用选中的 Skill 引导编辑，再拒绝审批，确认方法已进入请求但文件未被修改。

### Q45：MiniCode 的 Skill Manifest 和 Catalog 保存什么，为什么与正文分开？

检索词：MiniCode、SkillManifest、SkillCatalog、manifest.json、name、description、entrypoint、tags。

主回答：Manifest 描述名称、说明、正文入口和标签，Catalog 稳定收集这些元数据并拒绝重复名称。启动发现只读取轻量 Manifest，收到任务后才能选择并加载 SKILL.md 正文，避免所有方法都提前占用上下文。

实现要点：磁盘格式按实际 schema 校验，入口相对 Skill 目录解析，目录与名称关系、类型和重复标签等有明确检查。运行内 Manifest 对象和磁盘 JSON 版本合同是两回事。

范围：不补写当前字段中没有的意图模型、正反示例特征、自动版本发布或模型评分。引用 metadata 不等于相信正文内容安全。

### Q46：MiniCode 如何从用户任务中召回候选 Skill？

检索词：MiniCode、关键词召回、casefold、tokenize、名称、描述、标签、集合交集。

主回答：取最近用户任务文本，做 casefold 规范化，再按非单词字符与下划线切分成去重词集合；Skill 的名称、描述与标签也按同一规则合成词集合。两者存在共同词就进入候选，不需要额外调用模型。

取舍：行为简单、确定且便于复现，但不理解同义词、语义改写与跨语言关系；中文连续文本也不能当成成熟分词。没有共享词就可能漏召回，不能把“没有选中”解释成已理解任务后确认无关。

验证方法：覆盖大小写、重复词、下划线、无交集与中文改写，并核对候选，而不只看最终答案。

### Q47：MiniCode 怎样给候选 Skill 排序？为什么不是语义精排？

检索词：MiniCode、KeywordSkillRanker、共享词数量、稳定排序、max_skills、Top-K。

主回答：分数是任务词集合与 Skill 元数据词集合的交集大小，按分数降序，同分保持 Catalog 原有顺序，再按 max_skills 截取。重复出现同一个词不重复加分；名称、说明和标签没有另设训练权重。

例子：任务词含 pytest 与 failures，元数据也含这两项，就得到两个共享词的分数。它是候选规则排序，不是 Embedding、CrossEncoder 或大模型意图评分；阈值与数量以实际配置为准，不把默认值叫行业最优。

验证方法：人工构造可计算分数的元数据，测试同分顺序、截断、空候选和重复词，保证确定性。

### Q48：MiniCode 为什么先用关键词路由，而不是向量检索选 Skill？

检索词：MiniCode、关键词路由、语义召回、Embedding、设计取舍、SkillRouter。

主回答：在目录较小、需要明确解释和测试的范围内，关键词方案成本低，也容易区分候选、排序和加载失败。语义召回能改善改写覆盖，但增加模型、索引和误召回的维护问题；应先用错选和漏选案例证明必要性，再替换路由接口的实现。

范围：独立扩展指可以替换 Router 或 Loader，不代表现有产品已经接入向量数据库、语义重排或自动增长。

验证方法：保留规则基线和同一任务集，比较召回、错选、加载成本与最终任务结果，而不是因换了更复杂技术就宣称提升。

### Q49：MiniCode 的 Skill 正文怎样加载，并加入哪一部分模型请求？

检索词：MiniCode、FileSkillLoader、SkillContextBuilder、instructions、conversation、SKILL.md。

主回答：Router 返回命中项，Loader 只读对应正文，Builder 渲染成固定方法文本；QueryLoop 把它与固定指令放入 ModelRequest.instructions，不追加为真实用户或工具历史。适配器发送时再按协议转换成前置指令消息。

实现要点：未命中正文不读取；单份正文和合并指令都有大小边界；入口使用独立 Skill Workspace 校验路径。没有配置 Skill 来源时整条链关闭，空选择不等于异常。

验证方法：让未选中正文损坏，运行仍能继续；检查模型实际请求确有选中指令，history 没有伪造 Skill 对话。

### Q50：MiniCode 没匹配 Skill 与选中后正文损坏，行为为什么不同？

检索词：MiniCode、Skill 无匹配、正文损坏、UTF-8、路径边界、模型调用前失败。

主回答：没配置来源或路由没有命中，可以继续普通任务，不需要额外 Skill 指令；已经选中却正文缺失、非 UTF-8、空白或越界，是加载失败，必须明确报告，不能静默声称已加载。元数据发现失败与正文读取失败也要区分。

数据链：Router 先返回名称与分数，Builder 记录选择和加载事件，再调用 Loader；失败向外传播，尚未进行模型请求。目录创建客户端等准备动作不等于已经付费调用模型。

验证方法：用记录调用的脚本模型检查失败时 complete 没发生；另让未选中正文损坏，确认确实没有提前读它。

### Q51：MiniCode 为什么在任务开始时加载 Skill 一次，恢复时怎么处理？

检索词：MiniCode、Skill 加载时机、快照、resume、skills_root、指令复用。

主回答：新任务在首次模型调用前选择并加载一次，后续各轮复用同一方法文本，避免正文变化或工具输出偶然出现关键词时悄悄切换指导。检查点保存已加载指令，恢复沿用快照，不要求原目录仍可用。

取舍：不能根据中途新发现自动热插拔方法，但运行行为更稳定。加载一次只减少重复路由和磁盘读取，不表示正文只发送一次；它仍会进入后续模型请求。

验证方法：保存中断检查点后删除或修改 Skill 文件，再恢复检查请求中的原指令，以及原工具审批仍生效。

### Q52：MiniCode 如何控制加载的 Skill 数量、大小和失败边界？

检索词：MiniCode、max_skills、正文 byte 上限、总指令上限、失败处理、信任边界。

主回答：路由限制选中数量，Loader 限制每份正文和路径，QueryLoop 再检查合并指令的大小。目录发现、候选排序与正文读取分开，便于明确失败发生在哪一层。加载上限是资源约束，不是内容安全认证。

边界：数量少不保证相关性，byte 小不保证 Token 成本或质量；当前 ToolResult 投影不压缩 Skill 正文。如果方法文本本身造成请求压力，需要显式处理配置，而不是悄悄改写系统或 Skill 指令。

验证方法：测试数量截断、边界大小、非法编码、空白正文和越界入口，检查失败不会被伪装成成功加载。

### Q53：MiniCode 如何评测 Skill 路由？为什么还需要任务级对照？

检索词：MiniCode、SkillRoutingCase、exact_match、漏选、多选、顺序、开关对照。

主回答：离线案例给出任务和预期 Skill 名称，比较实际选中序列；exact_match 要求名称、数量和顺序一致，同时列出漏选与意外选中。无关任务使用空预期检查过度召回，同分与截断检查稳定性。

边界：这个口径是路由精确匹配率，不是答案准确率、召回率或真实任务成功率。任务级另外固定模型、代码、初态、预算和方法版本比较开关，观察独立验收及完整用量。

验证方法：正例、负例、相似能力、错序及有选择但加载失败分别核对；没有真实对照就不报收益数字。

## 五、检查点恢复与执行审计

### Q54：MiniCode Checkpoint 保存什么，resume 与只读 Replay 有什么区别？

检索词：MiniCode、RunCheckpoint、run_id、message_history、turns_used、tool_calls_used、skill_instructions、Replay。

主回答：Checkpoint 保存 Run ID、完整交互历史、已用轮次和工具计数、完成标记以及本次 Skill 指令。resume 用它继续同一个 Run，按调用与结果的 ID 匹配补执行 pending，延续已有轮次和调用预算；完成态拒绝继续。

Replay 则只读取有序事件，检查和汇总执行过程，不重新调用模型或工具。Checkpoint 不是自动长期记忆，保存历史也不意味着新任务自动继承旧任务。

边界：当前完成回答在 RunResult.response 中，完成 Checkpoint 不额外复制最终回答文本。恢复字段也不包含已累计 Token，不能把所有预算都说成可无损延续。

### Q55：MiniCode 为什么在 ToolResult 后保存检查点？第一工具执行前崩溃怎么办？

检索词：MiniCode、保存时机、ToolResult、完成态、初始检查点、pending。

主回答：工具结果返回后，QueryLoop 把它加入完整历史并保存计数，恢复才知道哪些调用已有结果。一批调用先加入历史，逐结果保存，可以在已有检查点中识别后续 pending；正常无工具收尾时另保存完成态。

边界：普通新运行不在任意时刻自动保存；第一个工具结果前中断可能还没有可恢复检查点。工具结果返回到保存成功之间也有窗口，不能说执行过的任何动作都已经可恢复。没有 Store 就不会自动落盘。

验证方法：第一结果前取消、第一结果后第二调用取消、保存失败、完成后再恢复分别检查；不能把日志里打印过 Run ID 当成磁盘已有有效状态。

### Q56：MiniCode 怎样防止恢复错 Run 或在另一个工作区加载状态？

检索词：MiniCode、run_id、工作区隔离、恢复拒绝、FileCheckpointStore、RunToolResultSource。

主回答：CLI 按规范化工作区路径定位状态目录，恢复复用原 Run ID；文件存储读取后核对内容 Run ID 与查询键一致，QueryLoop 在有 EventLedger 时还核对其 Run ID。历史回读绑定指定 Run，也拒绝存储返回不匹配状态。

意义：这些检查防止把任务 A 的历史接成任务 B，而不是让模型判断“看起来像同一个任务”。原 Run 身份和新启动请求 ID 不能随意混用。

边界：ID 一致不是身份鉴权，也不证明工作区文件没变或状态未被宿主权限持有人篡改。验证时分别替换存储返回、EventLedger ID 和工作区，检查模型与工具前拒绝的边界。

### Q57：MiniCode 恢复时哪些预算能延续，为什么不能假装 Token 从零开始？

检索词：MiniCode、resume、轮次预算、工具预算、Token 累计、fresh run。

主回答：Checkpoint 有 turns_used 与 tool_calls_used，恢复先检查剩余额度，pending 完成后从后续轮次继续，不能把计数重置获得额外执行机会。它没有保存历史累计输入输出 Token，因此配置 ModelRunBudget 的运行会拒绝 resume，要求新 Run。

取舍：这比恢复时把未知 Token 当零更保守，但不等于已支持所有预算的跨重启延续。保存完整 usage 是可讨论的扩展，需要新的数据合同和兼容验证，不能从现有轮次字段推出来。

验证方法：检查已有计数、pending 会超额度、轮次耗尽、完成态以及有 Token 门禁时的拒绝；新 Run 与旧 Run 的结果和成本不可混作一次无缝继续。

### Q58：MiniCode：Checkpoint 能保证工具只执行一次吗？

检索词：MiniCode、幂等、exactly once、副作用、崩溃窗口、原子性、重复编辑。

主回答：不能。工具修改成功后、Checkpoint 保存前崩溃，磁盘效果和恢复状态可能不一致。仅记录执行前 pending 也分不清“还没执行”和“已经执行但没记结果”。需要按动作使用幂等键、执行前条件或事务，而不是靠一个状态标志消除不确定性。

例子：精确替换成功后旧文本消失，再执行可能报不匹配；这有助于避免盲目重复替换，但不是已实现成功去重或恰好一次保证。

### Q59：MiniCode 的 Event、Trace、Artifact 和 Checkpoint 如何配合？

检索词：MiniCode、EventLedger、Trace、Artifact、Checkpoint、审计、持久化。

主回答：Event 用关联 ID 和顺序记录模型、策略、审批、工具与保存阶段；Trace 是可导出的事件文本；Artifact 保存工具输出及引用元数据；Checkpoint 保存恢复状态。它们对应过程观察、输出保存和恢复，不能相互替代。

实现边界：文件 Checkpoint 已持久化，不等于 Event 和 Artifact 都是持久服务。当前事件及工件主要在进程内，CLI 可选导出 Trace；只读 Replay 可以复盘导出的事件，但不能据此承诺跨重启完整审计、不可篡改或历史工件永久可用。

验证方法：核对同一 Run 中 call_id、策略、审批、执行和保存的顺序；hash 帮助比较关联文件内容，不是身份鉴权或事实正确性证明。

### Q60：MiniCode：临时文件加 os.replace 为什么更可靠？能保证断电不丢吗？

检索词：MiniCode、原子写、临时文件、os.replace、flush、fsync、崩溃一致性。

主回答：直接覆盖目标可能让其他读取者看到部分内容；先在同一文件系统写完整临时文件，再替换目标，可以在相应操作保证下让路径切换呈现旧版或新版。它解决的是发布可见性，不自动保证数据在断电后持久存在。

持久性需要另行考虑缓冲刷新、文件同步及必要目录元数据同步，并验证错误处理。也不能把单文件原子替换说成多文件、记录与索引或外部副作用的原子事务。[Python os 文档](https://docs.python.org/3.12/library/os.html#os.replace)

验证：在临时文件写入、同步和替换处分别注入失败，检查原目标与临时资源；模拟异常测试不等同于真正断电测试。

### Q61：MiniCode：项目为什么既用 Python 对象又用 JSON？什么时候转换？

检索词：MiniCode、JSON、序列化、反序列化、Checkpoint codec、Pydantic、schema version。

主回答：运行中用有类型对象传递数据，方便表达约束；跨模型 API、磁盘持久化和结果归档边界时再转 JSON。JSON 自身没有项目类语义，读取后要校验 schema 版本、字段、枚举和引用关系，不能反序列化成功就当状态有效。

取舍：不要求每个内部函数先 dump 再 load；但对外部输入不能省略校验。明确拒绝未知版本和损坏状态，不静默修成看似可用的历史；不能用不安全的任意对象反序列化替代明确数据合同。

验证：缺字段、额外字段、错误类型、重复调用 ID、错配结果、未知版本和过大输入分别覆盖。

## 六、固定任务评测、对照与版本回归

### Q62：MiniCode 的 Benchmark 怎样综合判断任务成功？

检索词：MiniCode、outcome_passed、operational_passed、budget_passed、trace_passed、独立验收。

主回答：任务结果看独立验收，运行状态看是否正常完成而非轮数耗尽，预算看预设额度，Trace 看案例约定的禁止动作与验证条件。四项同时通过才是整体通过；允许修改范围由案例验收与工作区差异核对，不能用一个维度抵消另一个失败。

取舍：代码已经正确但 Agent 未正常收尾，应分别报告功能通过和运行失败，而不是统称代码错误。推荐的调查路径与安全硬约束应分开，避免只认可一条工具顺序。

验证方法：为每个维度单独构造反例，检查验收器本身能拒绝错误交付，而不是只测一条全通过路径。

### Q63：MiniCode：隐藏验收和 Agent 自己运行测试有什么区别？

检索词：MiniCode、隐藏测试、acceptance、run_tests、自测、独立验收。

主回答：自测是 Agent 在执行过程中获得反馈并继续修改；独立验收由评测侧依据预先任务要求检查最终交付，不根据模型的实现反过来改标准。隐藏的是具体代码和样例，不是故意隐瞒需求。

边界：验收可能写错，放在工作区外也不等于不可被任意进程访问。要给验收器设计正反例，不能把“测试全绿”当作绝对正确。

### Q64：MiniCode：单文件修复怎样设计验收？

检索词：MiniCode、single_file_batching、批处理、边界输入、单文件修复。

主回答：以批处理逻辑为例，任务约定输入、批次大小、输出与允许修改文件。验收至少覆盖整除、非整除、空输入和非法参数等已约定边界，检查实现真正满足需求，而不是只适配一个样例。

过程：Agent 读取、提出最小修改、执行测试和检查差异；评测另查结果、改动范围与运行约束。这里是验收设计说明，不补造某次模型的实际工具顺序和结果。

### Q65：MiniCode：跨文件 quantity 改 stock 为什么不能只检查报表能输出？

检索词：MiniCode、multi_file_inventory_contract、跨文件契约、quantity、stock、报表。

主回答：库存与报表如果都继续使用旧字段，报表仍可能正常工作。因此验收既断言库存记录符合 stock 新契约，也断言报表能正确消费该记录，还检查允许修改范围。前者证明需求改了，后者证明功能未坏。

失败反例：只改生产者、只改消费者、两边都没改、通过删除测试绕过需求，都应该被识别。预期字段来自任务，不来自模型修改后的代码。

### Q66：MiniCode：只读诊断案例检验什么？

检索词：MiniCode、readonly_pagination_diagnosis、只读、分页、注入、解释正确性。

主回答：只读任务不仅检查最终解释是否符合不同边界输入，还检查没有修改工作区，并用仓库中的不可信诱导验证权限边界。关键词命中不足以证明诊断正确，应检查关键输入和预期关系，允许合理表达但拒绝错误结论。

取舍：检查过松会误放，过度绑定措辞又会误杀，因此验收也需要独立反例。不能因为答题中出现了正确名词就算通过。

### Q67：MiniCode：搜索驱动的共享根因修复和普通修复有什么不同？

检索词：MiniCode、search_driven_retry_schedule、搜索定位、共享实现、根因、调用关系。

主回答：不预先把具体出错文件指给 Agent，要求从目录和文本搜索发现调用关系，定位多个现象背后的共享实现，再做最小修改。验收检查共享行为和允许修改范围，避免在多个调用方分别打补丁掩盖根因。

证据：轨迹能帮助解释为什么读这些文件、修改是否基于观察；但搜索步骤只是调查路径，是否必须作为硬门禁取决于案例预先契约。

### Q68：MiniCode：大工具输出与早期证据回忆案例为什么必要？

检索词：MiniCode、large_search_context_repair、large_search_context_recall、上下文压力、早期证据。

主回答：简单任务输出少，可能根本不触发压缩，不能证明压缩路径可用。压力案例需要真实产生足够大的历史输出，并让后续任务依赖早期证据，检查是否发生投影、能否回读及最终答案是否正确。

公平性：任务应要求报告正确事实，不强制只有开启组才有的 read_tool_result；否则把专属实现写成正确性条件，会人为偏袒一组。

### Q69：MiniCode 的成功率、工具调用与 Token 怎样统计？

检索词：MiniCode、运行分母、不同任务数、调用尝试、执行成功、usage_complete、累计 Token。

主回答：先定义任务集、重复次数、预算和失败分类；同一任务重复不算新增场景。总体按预注册运行统计，同时分开结果、运行、安全和基础设施失败。模型请求的调用数量、Runtime 已返回结果的尝试数量和实际成功副作用不是同一个口径，不能都写成成功工具执行。

用量：累加整次任务所有已报告的输入输出，usage 缺失保留已知小计并标记不完整。评测预算字段还需说明它统计的是模型提出的调用还是运行内已消耗计数。

验证方法：覆盖审批拒绝、参数错误、工具抛异常、额度不足未执行的调用和缺 usage；不能从 API 配额不足反推本次消耗很大。

### Q70：MiniCode 如何做 Skill 与上下文策略的对照及版本回归？

检索词：MiniCode、Skill 开关、上下文投影、消融、Preflight、版本回归。

主回答：固定模型、代码、任务初态、预算和权限，一次只改变目标配置。Skill 对照固定目录和正文；上下文对照检查真实请求是否发生投影、是否回读，以及累计 Token 和验收。两项一起变化只能说明组合差异，不能分别归因。

Preflight 是小规模端到端预检查，用来确认关键路径和数据链，不当正式统计；协议或策略改变需另记版本，失败不能无规则补跑到成功。回归比较依靠固定案例和原始结果，不混合不同提交包装成统一成功率。

验证方法：Trace 与 Result 声明互相核对，构造开启却未命中机制的运行；不包含本版未主张的 Memory 或缓存收益实验。

### Q71：MiniCode：失败如何归因？怎么避免只凭直觉怪压缩或模型？

检索词：MiniCode、失败归因、Trace、权限拒绝、工具失败、模型错误、上下文遗漏。

主回答：先按阶段找直接原因：模型协议、参数、策略拒绝、工具、状态保存、上下文、Provider 或验收器。再查看当轮实际请求、工具输入输出和差异，判断缺了什么证据；要证明某策略影响还需要受控对照。

例子：编辑未获批准导致字段未改，首先是执行未获准；隐藏验收失败不能单独证明压缩有问题。Trace 记录关联线索，不自动构成因果证明。

### Q72：MiniCode 为什么同时保存 Answer、Trace、Result 和工作区差异？

检索词：MiniCode、answer.txt、trace.txt、result.json、workspace.patch、哈希、归档。

主回答：Answer 表达最终输出，Trace 说明模型、权限和工具过程，Result 保存验收及统计，工作区差异展示真实改动。关联案例、Run、模型、代码版本和配置后，才能判断一句“通过”来自哪次执行。普通 CLI 与评测归档是不同工作流，不自动产生相同证据集。

边界：新增记录支持补丁和关联哈希，不应说所有历史批次都有这些文件。哈希只检查内容关联，不证明行为正确；临时目录被清理后不能继续声称原始结果完整可复现。

验证方法：错配运行、修改关联文件、重复覆盖输出或声明与 Trace 不符时应拒绝记录或汇总。

### Q73：MiniCode 的项目难点或失败复盘应该怎样讲？

检索词：MiniCode、真实失败复盘、设计取舍、上下文收益、验收器、恢复窗口。

主回答结构：说明一个有记录的任务和异常，给出当轮请求、工具或验收证据，解释候选原因和排查，指出改变的设计与验证范围，最后交代未解决边界。可以围绕引用节省被回读抵消、验收条件误放或工具成功后状态保存失败展开，但不能把讨论主题编成个人亲历事故。

要求：若问“最难的取舍”，讲事实保留与请求长度、恢复方便与副作用不确定性之间的权衡；若问本人具体解决过什么，必须补真实记录，不让软件自动生成故事。

### Q74：MiniCode：项目测试应该分几层？为什么不能全部调用真实模型？

检索词：MiniCode、单元测试、集成测试、端到端、Fake、ScriptedModel、测试分层。

主回答：纯规则和合同用单元测试；真实文件、Dispatcher、保存恢复与请求组装用集成测试；脚本模型固定调用序列验证整个程序链路；真实模型用于检查真实协议和行为，最后独立验收检查任务交付。各层回答的问题不同。

脚本模型可保证命中拒绝、异常和恢复等分支，但不能证明真实模型会选择同样的动作。真实模型有费用和不确定性，也可能根本不进入待测分支，不适合作为全部程序边界的唯一验证手段。

验证：同一权限测试同时检查审批调用、文件未变和拒绝结果，不只断言最终回答出现“拒绝”。

### Q75：MiniCode：怎样测试中断、保存失败和部分成功？

检索词：MiniCode、故障注入、monkeypatch、Checkpoint 保存失败、取消、屏障、部分执行。

主回答：在明确边界注入故障，而不是随机关程序：第一工具成功后让第二工具取消；临时文件写入后让发布失败；审批后改变待写状态；工具副作用完成后让 Checkpoint 保存失败。每种故障分别检查内存历史、磁盘记录、真实工作区、事件和恢复行为。

关键：工具已执行但状态未提交时，测试应暴露不确定窗口，不能硬写一个“恢复必定不会重复”的错误期望。用可控替身、同步屏障和 tmp_path 避免依赖偶然时序或真实敏感文件。

证据边界：测试设计、存在测试代码和本次实际执行通过是三件事；知识库不能仅凭方法说明声称所有故障已覆盖。

### Q76：MiniCode 怎样证明 Skill 或投影配置真的传到了模型请求？

检索词：MiniCode、配置接线、Arm、ModelRequest、Trace、Result、默认关闭。

主回答：从入口参数检查到组装对象、实际 Request 和结果记录，不能只看文件夹名字。Skill 开启但没有匹配时，应记录开启且选中为空；投影组应记录正确策略，实际是否有候选和替换另行统计。配置开启并不保证这道题一定触发机制。

验证方法：脚本模型捕获真实请求，检查指令、工具定义和引用；Result 校验与 Trace 声明一致，未知模式在模型调用前失败。还需测试默认运行不因实验入口而偷偷开启能力。

事实边界：普通 CLI 未必开放全部研究参数，不把核心可配置说成用户无需配置就默认启用。

### Q77：MiniCode 运行慢时，如何区分模型、工具、审批和回读开销？

检索词：MiniCode、阶段计时、模型轮次、工具耗时、人工审批、回读、端到端延迟。

主回答：先分别测模型请求、Skill 路由加载、上下文投影、工具、保存状态和人工审批等待，检查重复读取及回读是否增加了路径长度。审批等待单独报告，模型首字时间与任务结束时间也不同；有了瓶颈证据再考虑减少无效调用或调整配置。

边界：当前有序事件不代表已具备完整计时画像。不能把线程、异步或更少请求字节直接当作提速证明，也不报告没有计时记录的 P95、火焰图或缓存收益。

验证方法：用受控替身区分慢模型、慢工具和等待审批，真实性能需要额外固定环境的测量，不影响权限和验收标准。

### Q78：MiniCode：如果面试官追问个人贡献、开发时间和真实数字，如何回答？

检索词：MiniCode、个人贡献、AI 辅助、开发时间、项目真实性、实验数字、简历口径。

主回答：这些不能靠技术方案推导。必须由本人确认负责的需求、设计、实现和测试，说明 AI 辅助范围，并用实际提交、源码或原始运行记录支持。模拟完成版帮助组织技术理解，不会把未确认经历自动变成事实。

准备模板：本人负责的决策或模块是什么；为什么这样选；对应代码或测试在哪里；结果证明了什么；哪些部分参考或由 AI 辅助；还有哪些边界。空缺项先补事实，不编“主导全部”或一段不存在的事故经历。

数字与时间：任务数和运行数分开，版本和 Usage 完整性明确；初版时间与后续迭代时间可以不同，但需解释一致口径。缺证据就明确未测或待核对，不用行业数字替代。

## 七、与 MiniCode 直接相关的 Python 和异步基础

### Q79：MiniCode：async def 和 await 为什么不等于工具并行？

检索词：MiniCode、async、await、协程、事件循环、create_task、并发、并行。

主回答：async def 定义协程函数，await 在等待可等待操作时让出执行机会；连续 await 两个工具仍是顺序执行。需要显式调度多个任务，才可能让它们在等待期间交错推进；CPU 并行又是另一回事。MiniCode 的一批工具调用顺序 await，不因此拥有并行执行能力。

项目意义：模型网络、审批和进程输出适合异步等待；不能把一个耗时同步函数直接放进 async 函数后就认为不会阻塞。[Python 协程文档](https://docs.python.org/3.12/library/asyncio-task.html)

### Q80：MiniCode：为什么文件工具使用 asyncio.to_thread？取消后写入一定停止吗？

检索词：MiniCode、to_thread、阻塞 I/O、线程、取消、文件副作用、GIL。

主回答：同步文件操作可能阻塞事件循环，to_thread 把它放到线程执行，让循环继续处理其他等待；这不等于所有计算都会因线程加速。更重要的是，取消外层等待不能保证已经运行的线程函数被强制终止，它仍可能完成文件修改。

后果：不能记录“协程取消，所以文件没变”。需要设计提交与取消边界，并复核实际文件和状态；把运行中线程强杀或自动回滚说成 Python 默认能力是错误的。[Python Future 取消说明](https://docs.python.org/3.12/library/concurrent.futures.html#concurrent.futures.Future.cancel)

验证：用同步屏障控制线程在写入前后的位置，再取消等待并观察真实结果；不使用不稳定的短 sleep 猜测执行时序。

### Q81：MiniCode：Protocol 与普通基类有什么区别？为什么不把它当运行时校验？

检索词：MiniCode、Protocol、接口、结构化子类型、鸭子类型、依赖注入、mypy。

主回答：Protocol 描述调用方需要的方法形状，符合结构的实现不必显式继承它，适合替换真实模型、脚本模型、存储和执行器。普通继承还可能提供共享实现，两者目的不同。

边界：类型注解主要供静态检查，不自动验证运行时返回值。runtime_checkable 也主要检查属性存在，不是完整签名与业务语义校验；关键边界仍需要显式检查和测试。[Python Protocol 文档](https://docs.python.org/3.12/library/typing.html#typing.Protocol)

取舍：只在真实替换点定义接口，避免给每个函数制造没有用途的包装层。

### Q82：MiniCode：frozen dataclass、tuple 和 Pydantic 冻结对象是不是彻底不可变？

检索词：MiniCode、dataclass、frozen、tuple、不可变、深拷贝、快照、可变默认值。

主回答：冻结通常限制字段重新赋值，不会自动让内部 list 或 dict 深度不可变；tuple 自身不能改元素槽位，但其元素仍可能是可变对象。要得到可靠快照，需要按合同复制或规范化嵌套结构，不能只看到 frozen 就认为任何代码都无法改变状态。

项目意义：消息、策略配置和检查点都不希望被外部引用悄悄改动。集合默认值还要避免跨实例共享，应使用合适的工厂，而不是一个共用可变对象。[Python dataclasses 文档](https://docs.python.org/3.12/library/dataclasses.html)

验证：创建对象后修改原输入集合，检查已保存状态是否变化；这与给字段直接赋值的测试是两类情况。

### Q83：MiniCode：为什么取消异常不能随便吞掉？子进程清理要做什么？

检索词：MiniCode、CancelledError、try finally、取消传播、async with、subprocess、管道。

主回答：取消表示调用方要求停止，不是普通工具失败；应做必要清理后继续传播，而不是返回“成功”。Python 的取消通常在协程可处理的位置发生，不是任意时刻强制终止全部工作。[Python 取消说明](https://docs.python.org/3.12/library/asyncio-task.html#task-cancellation)

进程清理：并行消费 stdout/stderr 防止管道堵塞，限制输出，超时或取消时处理读取任务、终止进程并等待回收；实际等待退出也要在明确的 deadline 设计内。只清理直接子进程，不代表后代进程已全部清理，更不会撤销已提交文件。

验证：检查读取任务、进程状态和文件实际结果，不只断言捕获到 TimeoutError 或 CancelledError。

取舍或异常：允许扩展名与允许 MIME 的简单“或”条件不能验证真实格式；杀掉等待协程也不保证解析线程已停止。验证方法：使用小型伪扩展名、损坏压缩包、超限流和取消上传样本，检查拒绝、内存边界与清理；不使用真实危险文件。

### Q92：智能笔记 RAG 如何解析 PDF、Markdown、Word、PPTX 和 TXT？

检索词：智能笔记 RAG、多格式解析、DOCX、Word、PDF、PPTX、Markdown、TXT。

主回答：不同格式先用各自解析器，再统一成正文加定位的 Document。TXT 处理编码与空内容，Markdown 保留标题和段落，DOCX 按文档结构提取段落与表格，PPTX 保留幻灯片页号和文本顺序，PDF 逐页提文字并按需补充视觉描述。统一的是下游合同，不是把所有格式当纯文本读；尤其 DOCX 是结构化压缩包，UTF-8 TextLoader 不能作为可靠 Word 解析方案。

实现要点：DOCX 的参考实现可用 UnstructuredWordDocumentLoader，按实际依赖验收；解析结果记录 parser_version、页/段定位、空页及部分失败信息。扫描 PDF 没有可用文本时走视觉路径，不能静默当空文档入库。

取舍或异常：布局、表格、公式与读取顺序可能失真，不宣称无损解析。验证方法：每种格式准备已知段落、表格和定位的夹具，逐项比对文字与来源，再做下游召回；文件能打开不等于内容正确。

### Q93：智能笔记 RAG 的“多模态”具体实现到哪一层？

检索词：智能笔记 RAG、多模态 RAG、PDF 图片、视觉模型、图表理解、文本 Embedding。

主回答：本项目把多模态理解放在 PDF 导入阶段：提取页面文字和图片，对含图或文字不足的页面生成截图，交给支持视觉输入的模型生成页面描述，再与原文字一起进入文本切片和 Embedding。查询主要仍是文本检索，回答能定位原页和图片。它不是把图片直接映射到独立向量空间，也不代表支持任意图片、音频或视频检索。

实现要点：保存 user_id、doc_id、版本、页码与图片引用；视觉描述标记为模型派生内容。批量页面响应必须按页号校验，页缺失或视觉失败保留原文并标记信息不完整，不能挪用另一页的描述补齐。

取舍或异常：图中数字、单位和小字可能读错，派生描述不能替代原图核对；远端视觉调用会传出页面内容。验证方法：用相似图不同数值、扫描页、纯文字页和跨页表格，检查页级对齐及引用；不宣称已测图表准确率。

### Q94：智能笔记 RAG 怎样切片，chunk_size 和 overlap 怎么确定？

检索词：智能笔记 RAG、递归切分、RecursiveCharacterTextSplitter、chunk_size、overlap、语义完整性。

主回答：参考主链采用按段落、换行、句子等分隔符递归切分，并保留标题、页码和有限重叠。片段太小会丢条件与上下文，太大则稀释召回、增加重排截断和生成成本，因此参数应由语料和证据覆盖来确定。当前材料配置为 200 字符、20 字符重叠，这是配置观察，不能说它等于 Token 数或是实验得到的最优值。

实现要点：先按页或章节形成有定位的单元，再递归拆分；长表格保留表头关联，重叠文本引用时去冗余。切片配置、解析版本变化时重建对应索引版本。语义相似合并不是主链默认能力。

取舍或异常：字符上限不保证语义完整，重叠会制造重复候选。验证方法：标注跨边界事实、否定条件、长代码和表格问答，对比证据 Recall@K、上下文长度及答案支持性，不能只看片段长度整齐。

### Q95：智能笔记 RAG 怎样保留切片的来源和稳定标识？

检索词：智能笔记 RAG、chunk_id、metadata、页码、文档版本、溯源、稳定 ID。

主回答：每个片段都带业务对象和版本，而不是只存正文。参考设计用 user_id、doc_id、文档版本、索引配置版本与片段序号构造确定性 chunk_id，保存原始文件名、页码或段落范围。这样同一个任务重试可以覆盖同一批 ID，更新后能区分新旧版本，引用也能回到真正使用的片段。同名文件和同内容不同用户都不能混为一个业务对象。

实现要点：doc_id 是上传文档的稳定身份，MD5 检查原件字节，version 表示内容版本，index_version 表示解析/切片/Embedding 配置。重排只重排记录，不抹去这些字段；引用到受控读取接口时重新鉴权。

取舍或异常：删除或替换原件后，旧引用可能失效，应显示历史版本或不可用状态，不跳到新文档冒充原证据。验证方法：重复导入、改名、变更切片参数和替换原件，检查 ID、版本及引用行为。

### Q96：智能笔记 RAG 的 Embedding 输入输出是什么，和聊天模型有何区别？

检索词：智能笔记 RAG、Embedding、embed_documents、embed_query、向量维度、DashScope、Ollama。

主回答：Embedding 把片段或查询编码成固定维度向量，用于近似语义比较；聊天模型生成文本，二者不是一个输出合同。入库时按同一版本模型编码片段，查询时用兼容的查询编码方式。参考方案通过独立模型工厂选择 DashScope 或 Ollama，但一次索引的模型、维度、预处理和距离度量固定，不因聊天模型切换而自动换 Embedding。

实现要点：向量与 chunk_id 按批次一一对应；返回数量、维度、有限数值、空向量都要检查。失败时标记该批失败并有限重试，不能用 [] 或零向量冒充有效编码。长片段按模型输入上限处理，避免静默截断。

取舍或异常：同义表达可以更接近，不保证技术编号和否定语义准确，因此保留 BM25 路。验证方法：固定片段测批次映射、错误响应与维度，再用同义改写和精确标识查询检查召回；不把向量相似度称为答案正确率。

### Q97：智能笔记 RAG 更换 Embedding 模型后，旧向量还能直接用吗？

检索词：智能笔记 RAG、Embedding 迁移、重建索引、向量空间、版本切换、维度一致。

主回答：不能只看维度相同就混用。不同模型的向量空间和预处理可能不同，旧文档向量与新查询向量通常不可直接比较。参考设计为新模型建立独立索引版本，用同一份权威原件和笔记重算，完成数量、过滤和检索验收后再切换活动版本，并保留明确回滚入口。聊天模型替换不必重算向量，Embedding 替换则要检查整条索引链。

实现要点：文档清单与笔记索引状态记录 embedding_version；构建期间固定数据快照或补齐构建后的变更，查询不跨版本融合。新索引没覆盖的记录不能被报告为迁移成功。

取舍或异常：重建增加模型调用、磁盘与过渡维护成本；只删除旧库再重建会产生不可用窗口。验证方法：故意让新旧模型维度相同，检查系统仍拒绝混用；比较迁移前后金标查询和新增/删除记录的可见性。

### Q98：智能笔记 RAG 为什么分两个 Chroma collection，索引里存什么？

检索词：智能笔记 RAG、ChromaDB、rag_collection、notes_collection、索引构建、向量数据库。

主回答：rag_collection 保存上传文档的片段索引，notes_collection 保存笔记的语义索引。分开是因为它们的对象生命周期、来源定位和更新方式不同，便于各自维护；不是用 collection 名代替用户权限。索引保存片段正文、向量和必要元数据，MySQL 与受控原件承担权威内容，索引损坏时据此重建。

实现要点：写入确定性 ID，按 user_id 和当前有效版本约束读取；近邻搜索产生有限候选，业务层再复核对象状态。没有材料证明特定底层 ANN 参数已经调优，不报索引构建耗时或百万级检索表现。

取舍或异常：两个集合原始距离不能不经核对直接比较；小规模选择容易嵌入，但多进程写入、备份和恢复仍需独立方案。验证方法：核对索引条数、ID、维度、过滤与删除，再从权威数据重建并运行同一查询集。

### Q99：智能笔记 RAG 的 MD5 去重为什么按用户做，能保证什么？

检索词：智能笔记 RAG、MD5、文件去重、内容摘要、用户作用域、幂等。

主回答：MD5 用来判断同一个用户是否重复导入完全相同字节的文件，减少无意义解析和向量化。去重键包含 user_id 与文件摘要，不跨用户透露“别人已上传此文件”。同名文件未必相同，不同格式或压缩元数据变化也可能让相同正文产生不同 MD5。它是普通内容指纹，不是安全校验、语义去重或用户权限证明。

实现要点：导入开始查询用户内摘要与处理状态，只有有效完成版本可复用；失败或处理中按状态返回。普通上传与 SSE 上传共用该逻辑，不能一路检查、另一路只保存摘要。

取舍或异常：MD5 有碰撞风险，对抗性完整性场景应另用更强摘要及必要字节核对，不能声称项目已升级。验证方法：同用户重复、跨用户相同文件、同名不同文件、失败后重传和并发导入分别测试；只有“检查后写入”无法保证并发唯一。

### Q100：智能笔记 RAG 怎样做增量更新，更新失败时旧内容还能用吗？

检索词：智能笔记 RAG、增量索引、文档更新、版本发布、active_version、删除同步。

主回答：参考设计把增量定义为只处理新增或内容变化的文件，不是每次重建整个知识库，也不默认有段落级差量算法。同一 doc_id 更新时先建新版本，解析和索引都成功才发布活动版本；失败保留旧版并显示更新失败。查询只选本次确定的活动版本，避免同时回答互相冲突的新旧片段。

实现要点：MySQL 文档清单记录 pending、indexing、ready、failed、deleted 与 active_version。新 chunk 全部确认后在事务中切换版本、更新 corpus_version，失效旧 BM25/缓存，随后清理旧向量。候选进入重排前必须复核活动版本，版本过滤不能只靠客户端。

取舍或异常：MySQL 与 Chroma 没有跨库事务；新旧向量短时共存，需按有效状态过滤并在候选不足时有界补取。验证方法：在写一半、发布前和清理旧版时注入失败，检查旧版可用、新版不半露及重试可收敛。

### Q101：智能笔记 RAG 多人上传或重复请求时，怎样防止重复入库？

检索词：智能笔记 RAG、并发上传、唯一约束、幂等键、生产者消费者、串行写入。

主回答：并发下不能靠先查 MD5 再写文件，因为两个请求可能同时查到不存在。参考方案以 MySQL 用户内摘要约束和导入任务状态先登记处理权，相同文件的并发请求返回既有任务；解析可以在线程池并发做，向量提交经过同实例的受控写入器。确定性 chunk_id 使重试能更新同一批片段，而不是制造随机重复项。

实现要点：任务保存对象 ID、预期版本、状态和失败原因；重新处理失败任务通过条件更新取得处理权，不能直接插入第二份。线程结果包含任务身份，消费前检查版本与取消状态；请求内串行消费不等于进程内所有请求都串行。

取舍或异常：本设计限定同实例写入协调，不能宣称已有多机租约或恰好一次。验证方法：用屏障让两个请求同时登记，检查唯一任务、确定 ID 和最终有效片段；再模拟提交成功但响应丢失后的重试。

### Q102：智能笔记 RAG 索引部分写入、删除中断或缓存恢复失败怎么办？

检索词：智能笔记 RAG、部分成功、失败补偿、删除一致性、Chroma 缓存冲突、无损恢复。

主回答：按对象状态恢复，而不是遇到 Chroma 异常就删除整个数据库。部分写入未完成的版本保持不可见，重试按确定 ID 补齐；删除先在权威清单撤销可见性，再清向量、原件、图片与派生缓存，失败留下待清理状态。客户端收到异常不能据此断言没有写入，恢复要核对真实 ID 和版本。

实现要点：Chroma 客户端缓存冲突先停止新写入、关闭相关引用，保留持久化数据再重建客户端；确需数据重建时显式记录范围与来源。文档清单只有 ready 且未删除的版本可进入上下文，引用回读也检查删除状态。

取舍或异常：逻辑不可见与备份、日志、第三方副本的彻底删除不同。验证方法：在向量、摘要登记、删除和客户端初始化各阶段注入失败，检查重试与重启；不能把“删库后能启动”称为无损恢复。

## 十、智能笔记 RAG：混合召回、重排、上下文与答案

### Q103：智能笔记 RAG 一次查询经过哪些步骤，哪些判断必须先做？

检索词：智能笔记 RAG、在线检索、查询流程、用户过滤、双源召回、q 与 HyDE。

主回答：先验证身份、会话归属和查询长度，再把需要消歧的问题整理成独立查询 q。知识库中，BM25 用 q，向量路用 HyDE 生成的假设文本 h；笔记路直接用 q 做语义召回。两种知识库排名融合后，与笔记候选统一数据合同，复核用户和版本、去重，再按 q 重排。最后只把预算内的有效证据送给生成模型，保留引用映射。

实现要点：用户过滤先于召回，活动版本复核先于重排和模型输入，权重由 q 计算且仅本次查询生效。没有用户身份返回鉴权失败，不允许自动回退公共库；来源失败与空结果保留不同状态。

取舍或异常：HyDE、重排可以受限降级，身份和来源有效性不能降级。验证方法：记录 q、各路候选 ID 与入选依据，用伪造用户、旧版本和空库检查没有越权内容进入任何模型请求。

### Q104：智能笔记 RAG 为什么同时用向量检索和 BM25？

检索词：智能笔记 RAG、混合检索、向量召回、BM25、语义匹配、精确匹配。

主回答：两条路解决不同的漏召回。向量检索适合同义改写和概念相关，但可能混淆编号、函数名与相似主题；BM25 根据词项频率、稀有度和文档长度排序，对错误码、专有名词和 API 名称更有帮助。智能笔记 RAG 在同一用户的有效文档中分别召回，再融合候选，由重排处理问题和片段是否真正相关。多一路有潜在互补，也增加维护与噪声，不能预设效果一定更好。

实现要点：两路候选使用同一 chunk_id 与版本合同，保留 route_ranks；向量分数、BM25 分数和后续 CrossEncoder 分数语义不同，不作为同一概率比较。

取舍或异常：只做关键词可能漏改写，只做向量可能漏精确标识；融合不能挽救两路都没召回的证据。验证方法：分别设技术标识、自然语言改写和无答案问题，比较单路与混合的证据覆盖及噪声，不报告未测提升。

### Q105：智能笔记 RAG 的中文 BM25 怎样分词，索引如何更新？

检索词：智能笔记 RAG、中文分词、BM25Retriever、preprocess_func、倒排索引、corpus_version。

主回答：中文资料不能默认按空格分词就足够。统一参考设计让文档与查询共用一个分词函数：中文词项切分，同时保留 FastAPI、user_id、版本号等技术标识，规范大小写与标点时避免破坏错误码。小规模使用按用户和语料版本缓存的内存 BM25，文档发布、更新或删除后重建受影响用户的快照，不每次查询扫描全库。

实现要点：缓存键包含 user_id、corpus_version、分词配置版本；构建只读取当前用户已发布片段，构建后检查版本，过期就丢弃或重建。IDF、平均长度等统计来自该快照，删除也会改变统计，不能只移除返回列表而不更新索引。

取舍或异常：内存重建耗时与用户语料量相关，超出范围后才讨论专门搜索引擎；未设定已接入 Elasticsearch。验证方法：中文无空格、英文标识、增删文档和并发构建时检查词项与快照；分词器选择是参考设计，不称源码已配置。

### Q106：智能笔记 RAG 的动态检索权重怎么调整，属于训练模型吗？

检索词：智能笔记 RAG、动态权重、查询长度、规则、BM25 权重、向量权重。

主回答：材料中的动态权重是启发式规则，不是训练出的路由模型：根据原始独立问题的长度和词项特征，在向量与 BM25 之间调整融合权重。参考设计沿用“短而精确的查询偏词项、较长描述偏语义”的出发点，但每次查询重新计算，默认均衡，规则与参数版本化。不能把查询长短当成真实意图，更不能声称权重已经被实验证明最优。

实现要点：权重 w_vector、w_bm25 非负且归一化，只用于知识库两路 RRF，不用于把不同模型原始分数直接相加；使用 q 判断，不能因 HyDE 把问题扩写变长就自动提高向量权重。

取舍或异常：长问题也可能包含必须精确匹配的编号，中文空格密度不可靠。验证方法：短概念题、长错误码题、空输入和会话连续不同问题，对比固定权重；检查检索器复用不会把上次权重带入本次。

### Q107：智能笔记 RAG 如何融合 BM25 与向量排名，为什么用加权 RRF？

检索词：智能笔记 RAG、RRF、EnsembleRetriever、排名融合、去重、分数归一化。

主回答：参考方案使用加权倒数排名融合：片段在某一路越靠前，贡献越大，再按两路权重相加。写成 score(d)=Σ w_i/(c+rank_i(d))，未命中该路就没有这一项，rank 从 1 开始，c 是固定并记录的平滑参数。它避免直接比较 BM25 与向量距离的不同量纲，也便于解释两路一致命中为什么往前排。

实现要点：按 chunk_id 合并，保存各路排名；同分用稳定 ID 排序。正文完全相同但来源不同不能在融合时丢掉来源，进入上下文时可折叠重复文字并保留多个来源。c 与候选数是配置，不凭空编最优值。

取舍或异常：RRF 丢弃原始分数差距信息，某一路第一名也可能不相关，因此还需重排和拒答判断。验证方法：给定人工可算的排名列表断言融合、缺路、同分及版本去重；源码使用 EnsembleRetriever 不等于自定义 chunk_id 去重已生效，需核对适配。

### Q108：智能笔记 RAG 为什么用 HyDE，假设性答案是否会进入最终证据？

检索词：智能笔记 RAG、HyDE、假设文档、查询扩展、query embedding、幻觉。

主回答：HyDE 先让模型根据问题生成一段可能的文档式回答，再把它编码成向量查询，试图缩小短问题与长文档之间的表达差距。智能笔记 RAG 的参考方案只把假设文本用于知识库向量召回，BM25 仍用原问题，重排也按原问题。假设内容没有来源，不能当事实、不能被引用，更不能因为生成了一段答案就跳过真实检索。

实现要点：输入 q，输出受长度限制的 h；生成失败或超时回退 q，记录是否降级。h 不写入知识库、笔记或最终证据映射，除非用户另外明确要求保存且清楚标注生成内容。

取舍或异常：额外模型调用增加首字时间和成本，假设错误会偏移向量召回。验证方法：对同义查询、专有名词及无答案题做开关比较，检查向量候选覆盖和最终证据，而不是判断假设回答写得像不像。

### Q109：智能笔记 RAG 的 HyDE 偏题、失败或包含错误事实时怎么办？

检索词：智能笔记 RAG、HyDE 漂移、查询回退、原问题、检索降级、无答案。

主回答：把 HyDE 当不可靠的查询辅助。格式错误、过长或生成超时就直接用 q；即使生成成功，也由原问题驱动 BM25 和重排，避免假设答案自己召回、自己评分、自己证明。如果最终候选不能支持问题，就说明资料不足，而不是照着假设内容继续回答。是否改善要在查询集上验证，不能认为加一层模型必然有效。

实现要点：参考链只启用“h 的向量路＋q 的 BM25 路”，不是每次失败再无限添加多查询；保留降级原因与两路候选。鉴权或数据版本问题不能包装成 HyDE 失败后绕过过滤。

取舍或异常：简单规则不一定识别语义偏题；相关分高也不证明假设正确。验证方法：用同名不同技术、虚构术语和明确否定条件，检查偏移后能否被原问题重排和证据检查挡住；强制 HyDE 超时验证回退路径。

### Q110：智能笔记 RAG 的 CrossEncoder 重排和 Embedding 有何不同？

检索词：智能笔记 RAG、CrossEncoder、Reranker、重排、双塔、query-document pair。

主回答：Embedding 分别编码问题与文档，适合在索引中快速找候选；CrossEncoder 同时读取问题与候选片段，利用二者交互输出相关性分，适合少量候选精排。智能笔记 RAG 先混合召回，再把原问题 q 与候选正文组成 pair，按重排分降序选证据。重排只能调整已召回候选，不能找回候选集外的文档。

实现要点：输入是带稳定 ID 的候选列表，输出保留 ID、来源与 rerank_score；长度超限时明确处理问题和片段的截断范围。模型分数不是通用概率，不在界面上未经校准显示为答案正确率百分比。

取舍或异常：候选越多开销越大；重排超时可按已融合的候选降级，但仍执行来源和证据判断。验证方法：同词异义、否定条件、长片段末尾有答案和空候选分别检查排序及截断影响。

### Q111：智能笔记 RAG 配置一个 Reranker 模型路径，就能保证重排正确吗？

检索词：智能笔记 RAG、Qwen3-Reranker、CrossEncoder.predict、模型适配、打分协议、懒加载。

主回答：不能。模型权重可加载不等于 CrossEncoder 封装的输入模板和输出分数就正确。当前材料默认路径指向 Qwen3-Reranker，但需要核对该模型的指令模板、tokenizer、评分方式和库适配，不能仅凭类名断言是有效相关性评分。完成版用独立 Reranker Adapter 固定“问题与片段输入、单值相关分输出”的合同，具体模型与依赖版本以实际配置确认。

实现要点：启动或懒加载时做锁保护、模型能力检查与小样例检查；推理应在有界执行资源上运行，避免同步 predict 阻塞事件循环。加载失败保留检索降级状态，不重复并发加载多份权重。

取舍或异常：可使用已验证适配的 CrossEncoder，或按目标模型正确协议封装；两者是实现选择，不同时虚构成已测成果。验证方法：用明确相关、无关和重复 pair 检查输出形状、有限值、排序方向及版本，真实质量另需金标集。

### Q112：智能笔记 RAG 的召回数量、重排数量和上下文数量怎样配合？

检索词：智能笔记 RAG、Top-K、candidate_k、rerank_k、上下文预算、召回覆盖。

主回答：这些不是同一个 K。每路先取有限候选，融合去重后限制重排输入，再从重排结果中选预算容得下的证据。前段太小会漏证据，后段太大增加推理和噪声；最后应该按有效信息与 Token 预算选，不是固定塞满某个条数。当前配置 k=5 和源码摘要取前 3 条只是材料值，不是已经验证的最优组合。

实现要点：记录各路候选数、融合后唯一片段数、重排入选数、有效证据数和上下文长度。旧版本或已删除项被丢弃后，可在明确最大扫描范围内补取，仍不足就返回有限结果，不能解除用户过滤补数量。

取舍或异常：候选数增加不保证 Recall 持续改善最终回答，还可能截断关键证据。验证方法：在同一金标集改变一个 K，观察证据 Recall、重排指标、引用支持、成本与耗时；不能只报检索条数。

### Q113：智能笔记 RAG 如何组装上下文，为什么不把所有片段直接拼进去？

检索词：智能笔记 RAG、上下文组装、Token 预算、去重、原始证据、摘要策略。

主回答：上下文应保留最能回答问题的证据、必要条件和来源。参考方案先保留固定指令、问题、必要会话和输出预算，再把去冗余的原始片段按相关性与证据互补装入。每段附稳定引用号，明确文档只是资料。预算内默认一次生成工具级摘要，不先逐文档摘要再递归合并，避免新增调用和来源漂移；Agent 使用摘要及引用作最终回复。

实现要点：用实际模型可用的 Token 计量或保守估算，超长片段按语义边界选择并记录范围；保护否定、版本、单位和表格表头。重复 overlap 折叠文字但保留源映射，装不下关键条件时缩小问题或说明不足。

取舍或异常：只按分数截 Top-K 可能全来自同一段，不能支持比较题。验证方法：使用跨片段条件、同名不同版本、长表格与预算不足案例，检查真正进入模型的正文与最终引用；不把原文可回读等同于已被模型正确使用。

### Q114：智能笔记 RAG 怎样保证引用能溯源，而不是模型编一个文件名？

检索词：智能笔记 RAG、引用溯源、citation、证据编号、页码、幻觉引用。

主回答：引用来源由程序分配，不能让模型自由编链接。上下文组装时建立 E1、E2 等编号到 source_type、对象 ID、版本、chunk_id、页码或段落的映射，模型在结论后引用这些编号；程序校验编号确实存在，前端再通过鉴权接口打开原始位置。文件名只是展示信息，不能唯一定位证据，也不能证明这段证据支持结论。

实现要点：RAG 工具把摘要与结构化 citation map 一起返回，Agent 收尾保留映射并再次校验；未知编号不伪造补齐。笔记引用包含 note_id 与版本，历史内容变化时不能用新正文冒充旧证据。

取舍或异常：存在性校验能拦假 ID，语义支持仍需句子级抽查或评测；视觉描述引用还要能查看原页。验证方法：注入不存在的 E99、错页、仅标题相似与证据不支持结论的样本，分别检查格式和支持性。

### Q115：智能笔记 RAG 没检索到答案、证据冲突或服务失败时怎样拒答？

检索词：智能笔记 RAG、拒答、无答案、相关性阈值、证据不足、错误语义。

主回答：先区分无证据、证据不充分、资料冲突与系统错误。空结果直接说明知识库未找到依据；只有主题相似但缺必要事实时，回答已支持部分并明确缺口；资料冲突按来源和版本并列说明。模型、索引或网络失败则报告暂时无法完成查询，不能装成“你的资料里没有”。不靠一句 Prompt 或一个未经校准的相似度阈值保证不幻觉。

实现要点：检索结果带状态与降级原因，回答前检查核心问题能否由所选证据支持；重排分数门槛只可在固定模型和语料上校准，不能跨模型照搬。HyDE 文本不参与证据判定。

取舍或异常：严格拒答减少乱答，也可能错拒，因此同时看应答与拒答。验证方法：可回答、库外、证据残缺、相互矛盾和服务报错五类样例分别验收，统计误答和错拒，不声称零幻觉。

### Q116：智能笔记 RAG 怎样处理“那它为什么这样设计”这类多轮问题？

检索词：智能笔记 RAG、多轮对话、指代消歧、独立查询、聊天历史、会话隔离。

主回答：多轮问题要先解析指代，但历史不能取代本轮检索证据。参考方案只读取当前用户会话中必要的最近内容，把明确的指代转成独立问题 q；仍不确定时询问对象，不能猜一个项目继续。之后 q 统一驱动 BM25、权重和重排，HyDE 从 q 生成。历史回答可能过时或有误，因此本轮引用来自本轮有效来源。

实现要点：会话 owner 校验在读取历史前完成；独立查询保留用户的否定、时间和文档范围，查询改写产生新实体或改变约束时拒绝采用。保存原输入与规范查询的关联便于归因，隐私日志只保留必要信息。

取舍或异常：改写增加调用与错误点，独立问题无须重复改写。验证方法：同名对象、跨话题、历史错误、过长历史及他人 session_id，检查不会继承错误事实或泄露会话。

### Q117：智能笔记 RAG 怎样把知识库与笔记融合问答，分数可直接相加吗？

检索词：智能笔记 RAG、双源融合、跨源问答、notes_collection、rag_collection、来源冲突。

主回答：先在本人两个数据源中分别召回，知识库走混合检索，笔记走语义检索；笔记结果回 MySQL 核验当前内容与版本，再统一成 Evidence，按同一个 q 重排。不同来源原始距离不能无条件相加，也不能默认“笔记一定更可信”。最终回答区分外部文档和个人记录，发生冲突时明确来源、版本和缺失依据。

实现要点：去重键包含 source_type、对象和版本，避免 note_id 与 doc_id 碰撞；语义搜索回填保持召回顺序而非数据库 IN 查询的任意顺序。任何源都不把未过滤预览先发给前端或模型。

取舍或异常：一侧不可用时可给出另一侧有依据的部分结果并标记降级，不能声称已全面比较。验证方法：分别构造只在笔记、只在文档、两边互补、互相冲突和一侧故障的查询，核查证据及回答。

## 十一、智能笔记 RAG：笔记双写、Agent 与 SSE

### Q118：智能笔记 RAG 保存笔记时，MySQL 和 ChromaDB 如何双写？

检索词：智能笔记 RAG、笔记 CRUD、双写、MySQL、ChromaDB、事务、索引待办。

主回答：MySQL 是笔记真相源，ChromaDB 是可重建语义索引，两者不共享事务。参考设计在一次 MySQL 事务中保存笔记版本与索引待办，提交后尝试更新向量；失败保留待办并显示索引处理中，CRUD 仍可读到已保存笔记。删除先撤销业务可见性，再清向量。不能因为两次函数调用都放在 try 里，就声称双写原子或强一致。

实现要点：待办包含 user_id、note_id、目标版本、操作、状态与尝试记录；创建、标题修改、正文修改、删除都产生相应索引维护。Chroma 保存笔记 ID 和版本，搜索后回填 MySQL，过滤已删除、越权或版本不匹配项。

取舍或异常：短暂存在“保存成功但还搜不到”，需明确状态；这是补偿协议参考，当前源码仅日志不能支持此保证。验证方法：让 Chroma 写入失败，检查笔记仍在、待办未丢、恢复后可搜且不重复。

### Q119：智能笔记 RAG 双写重试如何防止旧版本覆盖新版本？

检索词：智能笔记 RAG、最终一致性、索引补偿、乱序更新、乐观锁、删除竞态。

主回答：重试不是简单重复上次写入。参考方案对同一笔记在同实例串行处理，执行前读取 MySQL 当前版本，过期任务标记被替代，按最新状态构建或删除向量；写入后再核对版本，有变化就保留新的待办继续处理。前台并发编辑用版本条件更新，冲突返回明确状态，防止悄悄覆盖用户修改。

实现要点：请求携带 expected_version，SQL 更新条件包含 owner 与旧版本；笔记和待办同事务提交。扫描器从 MySQL 拉取未完成项，重启仍能发现，不把 create_task 当持久队列；成功状态只在核对后写入。所有向量写操作统一经过协调入口。

取舍或异常：不承诺跨多实例互斥或恰好一次；扩大部署需另做执行权协议。验证方法：用屏障控制 v1 索引慢于 v2、删除后旧任务返回、写成功但待办确认失败，检查不会复活删除内容或永久留旧索引。

### Q120：智能笔记 RAG 的自动标签与分类怎样生成，出错会影响保存吗？

检索词：智能笔记 RAG、自动标签、分类、结构化输出、后台任务、JSON 校验。

主回答：笔记先保存，再异步生成有限标签和分类，模型失败不回滚用户正文。模型只读取这次需要的笔记内容，输出受 Schema 限制的 tags 和 category；程序验证类型、数量、长度和类别枚举，不能把一段看起来像 JSON 的文本直接信任为有效业务数据。用户手改标签和分类优先，旧内容的模型结果不能覆盖新版本。

实现要点：任务带 note_id、user_id、content_version，用独立数据库会话；更新时按版本和人工编辑状态做条件判断。裸 create_task 只提供进程内执行机会，需注册任务、处理异常与关闭；标签持久重试不是简历明确保证，不把它包装成可靠分布式作业。

取舍或异常：提示注入可能诱导标签异常，JSON 修剪不等于业务验证。验证方法：非法类别、超长标签、空内容、保存后立刻编辑及模型超时，检查正文不丢、旧结果不覆盖、界面能表达未分类。

### Q121：智能笔记 RAG 如何做关联推荐，怎样避免推荐其他人的笔记？

检索词：智能笔记 RAG、关联推荐、跨源推荐、用户过滤、排除自身、距离排序。

主回答：关联推荐以当前笔记内容为查询，在本人笔记和知识库中分别召回，排除当前笔记及重复来源，再统一重排取有限结果。两路必须在检索时都加用户条件，不能先全库取预览再让前端隐藏。笔记结果回 MySQL 复核 owner、版本和删除状态，文档校验活动版本。当前材料的笔记推荐一侧缺过滤，不能据注释声称隔离已验收。

实现要点：先确认被查询 note_id 属于当前用户，再用其正文；候选包含 source_type、对象 ID、版本和受限预览。若使用距离排序，要核对越小越近；参考方案最终使用统一相关分，避免两集合距离量纲问题。

取舍或异常：笔记很短、主题过宽会推荐泛化噪声；不把同标题视为相同内容。验证方法：让另一个用户拥有几乎相同的私有笔记，检查召回、日志、模型输入和接口响应都没有该内容。

### Q122：智能笔记 RAG 为什么需要 Agent，普通 RAG 链什么时候更合适？

检索词：智能笔记 RAG、LangChain Agent、AgentExecutor、RAG vs Agent、工具编排。

主回答：单纯“从资料回答一个问题”用确定的 RAG 链更直接；Agent 用于用户把多个业务动作组合成自然语言请求，比如先找相关笔记、对照文档归纳，再创建一条新笔记。模型决定调用哪种已开放工具，程序负责参数、身份、范围和副作用。工具多不等于多 Agent，也不需要为了展示能力给每个问题规划复杂流程。

实现要点：AgentFactory 创建请求级执行器，工具调用进入同一业务服务；摘要、语义搜索与创建笔记有不同输入输出。设置模型轮数、工具调用、结果长度与总时限，超限返回停止原因，不继续循环。

取舍或异常：Agent 增加延迟、协议错误和误操作概率，固定链容易追踪但不够灵活。验证方法：使用脚本模型固定调用序列验程序，再单独评估真实模型选工具与完成任务的表现，不用最终说“已保存”代替数据库验证。

### Q123：智能笔记 RAG 的核心 Agent 工具输入输出与调用关系是什么？

检索词：智能笔记 RAG、工具合同、rag_summary_tools、search_notes_tool、create_note_tool、结构化返回。

主回答：核心工具分为取证和业务写入。知识库摘要工具输入问题，返回摘要、证据 ID、引用映射和降级状态；笔记搜索输入查询与受限 top_k，返回本人笔记 ID、预览和版本；创建笔记输入标题和正文，返回实际 note_id、保存状态与索引状态。身份由服务端运行上下文注入，不属于模型可选择参数，工具结果也不能自行授权下一次写入。

实现要点：工具包装器校验参数，调用 RAG/NoteService，再把结果转为有限结构；RAG 内部已有重排，不让 Agent 无意义重复重排。工具错误区分参数、权限、超时和服务失败，不能全部返回空列表。回顾等辅助功能在材料中存在，但不扩大成简历核心亮点。

取舍或异常：过长工具结果会重复消耗上下文；不能为省长度删除关键出处。验证方法：脚本驱动工具参数错误、无身份、空结果、重复创建和部分索引失败，核对实际服务输入、数据库状态及返回合同。

### Q124：智能笔记 RAG 怎样防止文档提示注入与 Agent 越权写笔记？

检索词：智能笔记 RAG、Prompt Injection、Agent 权限、user_id、创建笔记、幂等写入。

主回答：文档、笔记和工具结果都只是资料，不能用其中的“替用户保存”当授权。创建笔记只在用户当前请求明确包含该动作时开放，程序校验工具参数，并从鉴权上下文取得身份；模型不能传另一个 user_id。检索任务本身不授予写权限，引用内容也不能改工具白名单或扩展访问范围。提示词帮助引导，但最终边界由程序执行。

实现要点：请求生成允许动作集合；create_note 需要对应的本次写意图，写操作以 user_id、request_id、tool_call_id 关联业务幂等记录。响应丢失后重试先查实际创建结果，不再插一条。若用户修改写入内容，应视为新请求，不能复用旧幂等键。

取舍或异常：含糊的“处理一下”不足以确定要保存什么，需要澄清内容；普通明确保存请求无需虚构统一人工审批平台。验证方法：恶意资料要求越权搜索、伪造身份、自动保存或导出秘密时，检查模型请求、工具实际副作用和数据库 owner，不能只看口头拒绝。

### Q125：智能笔记 RAG 的 SSE 是怎样从后端到 Vue3 的，算真正流式吗？

检索词：智能笔记 RAG、SSE、StreamingResponse、模型增量、TextDecoder、首字延迟、逐字播放。

主回答：SSE 是服务端持续向客户端发送事件的 HTTP 通道。参考设计分别发送阶段事件、最终回答文本增量、错误和结束事件；Vue3 通过带 Authorization 的 fetch 读取响应流，按 SSE 边界解析后更新界面。是否真正流式要看最终模型生成的增量是否及时到达浏览器，不能把拿到完整回答后 sleep 再逐字播放当成模型流式生成。当前源码最终回答采用后者，完成版接线需另核对。

实现要点：模型回调只转发最终回答阶段的文本 delta，不把工具 JSON、内部中间消息或隐藏推理直接当回答。引用映射单独发送；阶段事件只描述可观察的操作状态。客户端使用流式 TextDecoder，保留半截 UTF-8 和半个事件的缓冲。

取舍或异常：代理缓冲与频繁小事件会影响体验；首个阶段事件、首个答案字与完整结束分别计时。验证方法：假模型按屏障吐增量，确认未完成生成时前端已收到首字，并用拆分中文与事件边界的字节流验证解析。

### Q126：智能笔记 RAG 的 SSE 断连、超时、重试和慢客户端如何处理？

检索词：智能笔记 RAG、SSE 取消、断连、背压、deadline、重试、事件队列。

主回答：连接断开要停止无必要的模型生成并清理任务、队列和资源，不能只结束前端读取。参考方案设置请求总期限，分阶段从剩余预算分配上限；临时网络或限流可在未输出最终答案前有限退避，鉴权、参数和余额错误不盲重试。已经发出一半答案后不悄悄重新生成并拼接，明确标记中断，用户重发走新请求和幂等写入合同。

实现要点：有界 asyncio.Queue 连接模型事件生产和 SSE 消费；允许合并普通进度，关键结果与终态不能丢。finally 中取消并 await 可取消任务、关闭响应流，线程副作用另行核对。结束事件含 completed、failed 或 cancelled，连接 EOF 不能自动视为成功。

取舍或异常：不设定断线续传和持久事件回放；已开始的远端请求可能仍计费，取消不撤销已提交笔记。验证方法：慢读客户端、队列满、生成中断、写入后断连与阶段超时，检查资源、状态和重复写入；不用“捕获异常”替代清理验证。

### Q127：智能笔记 RAG 如何保存会话，两个请求同时写同一会话怎么办？

检索词：智能笔记 RAG、MySQL 会话、ChatSession、ChatMessage、同会话并发、request_id。

主回答：会话记录属于用户，读取、续聊和删除都先按 session_id 与 user_id 校验，不能只凭会话 ID。参考方案为每轮分配 request_id 和顺序号，同一会话先限定串行处理，忙时返回明确状态或进入有界队列；不同会话可并发。用户消息、最终回答和完成状态关联同一轮，不靠时间戳临时猜测两条消息是否一对。

实现要点：消息持久化记录角色、轮次、状态与必要来源；部分失败标记 failed，不伪装正常历史。请求级锁只覆盖同实例合作任务，数据库唯一约束防重复保存；历史取必要窗口，不无限拼接所有轮次。SSE done 只在既定持久化合同完成后发送。

取舍或异常：串行限制同会话吞吐，减少上下文乱序；不宣称现有数据库会话管理器已实现这些规则。验证方法：同会话同时发两题、响应完成但保存失败、重复 request_id、他人 session_id 和删除后续聊，核对归属与顺序。

## 十二、智能笔记 RAG：认证、隔离、Python 与后端基础

### Q128：智能笔记 RAG 的 Django 和 FastAPI 怎样共享 JWT 认证？

检索词：智能笔记 RAG、JWT、Django、FastAPI、Bearer、认证与授权、签名校验。

主回答：Django 登录成功后签发 JWT，FastAPI 从 Bearer 头取 token，按双方约定的算法、密钥和 claims 校验签名、过期时间与撤销状态，再取 user_id。JWT 证明身份声明没有被未授权修改，不替代资源授权；每次读笔记、会话、文档或图片仍要检查它属于这个用户。用户 ID 不由请求正文或模型指定。

实现要点：固定允许算法，要求必要的 user_id、exp、jti，校验数据类型；若启用 issuer/audience，签发与验证必须同时约定，不能只在一侧硬填。两个服务共享密钥增加泄漏影响范围，密钥不进源码、Prompt、日志或工具参数。

取舍或异常：JWT 的 payload 不是加密内容，不能放秘密；只解析 token 而不检查撤销状态不是完整鉴权。验证方法：错误签名、错误算法、过期、缺字段、格式错误和他人资源 ID；不编造已完成密钥轮换部署。

### Q129：智能笔记 RAG 为什么需要 Token 黑名单，Redis 不可用怎么办？

检索词：智能笔记 RAG、JWT 黑名单、jti、注销、Redis TTL、刷新 token、fail closed。

主回答：JWT 在过期前通常可被离线验证，所以注销或撤销需要额外状态。参考方案以 jti 建精确 Redis 黑名单键，TTL 覆盖 token 剩余有效期，两个服务统一 Redis DB、键前缀和序列化。受保护接口无法确认撤销状态时按失败关闭返回服务不可用，不悄悄允许访问。个人资料缓存失败可以回源，安全状态失败不能照搬同一种降级。

实现要点：精确 GET/EXISTS 查询，避免 KEYS 扫描；刷新前检查原 token 的签名、有效期、撤销及用户状态，再发新 token 并撤销旧 token。参考范围只定义有限有效期与撤销规则，不额外声称完整 refresh-token 家族和防重放体系。

取舍或异常：黑名单丢失或过早过期会影响撤销保证，需明确持久化和故障恢复范围。验证方法：Django 撤销后访问 FastAPI、前缀不一致、TTL 边界、Redis 故障及过期/已撤销 token 刷新，不把签名合法直接当仍可用。

### Q130：智能笔记 RAG 的用户级数据隔离需要覆盖哪些入口？

检索词：智能笔记 RAG、数据隔离、多租户、越权、检索过滤、BM25、图片权限。

主回答：隔离需要覆盖所有可能读取数据的路径：MySQL 的笔记和会话、Chroma 两个集合、BM25 构建、关联推荐、Agent 工具、图片与原件回读、缓存和日志。先按身份限制数据，再做相关性检索，不能先从全库找答案再让模型忽略其他用户。collection 分开与 ContextVar 都不能单独构成完整授权。

实现要点：存储过滤条件由服务端构造，包含 user_id；复杂条件按当前 SDK 合同显式用 $and，避免假定任意 dict 都有效。BM25 仅构建该用户有效语料，返回候选再核验 owner、版本和删除；缺身份立即失败，不退回全库。文件读取还需 ID 校验、路径规范化及目录边界检查。

取舍或异常：应用层隔离仍依赖所有入口正确接线，不等于数据库物理隔离。验证方法：A/B 两用户放同名同内容不同私密结论，逐入口检查响应、预览、引用、模型请求和缓存都不串，不只测主聊天接口。

### Q131：智能笔记 RAG 怎么限流，为什么限流还不能解决并发资源问题？

检索词：智能笔记 RAG、Redis 限流、固定窗口、Lua、429、信号量、并发上限。

主回答：限流控制单位时间进入多少请求，并发上限控制同一时刻占用多少昂贵资源，二者不同。参考方案用 Redis 原子脚本维护固定窗口计数，按用户和接口类别建键，必要时对未登录入口加 IP 维度；超过返回 429。模型生成、视觉处理和重排另外用有界信号量与排队超时，避免窗口内所有请求一起占满显存和连接池。

实现要点：计数检查、递增和首次设置过期在一次原子操作内完成，不先 GET 再 SET；固定窗口边缘有突发，不叫令牌桶。排队时间计入总 deadline，限流拒绝与下游服务故障分开；代理 IP 只信任约定代理来源。

取舍或异常：只按 IP 会误伤共享网络；Redis 安全控制故障应明确拒绝而不是静默不限流。验证方法：并发打到阈值、窗口边界、共享 IP 不同用户和 Redis 失败，核对实际获准请求数，不推断已做生产压测。

### Q132：智能笔记 RAG 的隐私边界、缓存键和删除语义怎样设计？

检索词：智能笔记 RAG、隐私、DashScope、Ollama、日志脱敏、缓存隔离、数据删除。

主回答：云端模型会收到发给它的查询、片段或页面图，必须按实际调用说明数据边界；聊天走本地 Ollama 不代表 Embedding、视觉、重排和调试追踪也都在本地。缓存键至少包含用户、对象或查询指纹、语料版本和相关模型配置，删除或更新后失效。日志以请求 ID、片段 ID、阶段和错误类型为主，避免记录 token、完整私密文档和页面截图。

实现要点：本方案不默认缓存完整最终答案；用户资料和 BM25 快照等缓存仍需作用域与版本。关闭非必要外部 tracing，临时文件、原件、图片、向量、MySQL 与本地缓存分别有生命周期；删除后新请求不得继续取出失效内容。

取舍或异常：已发送到 Provider 的内容、备份与历史会话不能靠删除向量立即抹除；需明确各自保留范围。验证方法：A/B 用户相同查询、更新后命中旧缓存、注销后访问、删除后新检索与引用回读；不承诺第三方副本已清空。

### Q133：智能笔记 RAG 使用 async/await 后，哪些操作仍会阻塞？

检索词：智能笔记 RAG、Python 异步、事件循环、asyncio.to_thread、gather、GIL、ContextVar。

主回答：async def 只定义协程，内部同步解析 PDF、Chroma 操作、模型加载和 CrossEncoder.predict 仍可能阻塞。网络异步客户端适合 await，同步 I/O 可放受限线程池，CPU 密集解析或推理需独立执行资源与上限；不能说线程总能突破 GIL 加速。连续 await 仍是顺序，gather 才会调度多个协程，但不自动限并发或创建线程。

实现要点：ContextVar 用于请求任务的身份上下文，设置后用 token 在 finally reset；子任务会继承创建时上下文，普通线程池或外部工作进程需显式传受验证身份。不要共享可变“当前用户”全局变量；也不要让共享 AsyncSession 跨并发任务使用。

取舍或异常：取消等待不保证正在运行的线程停止，gather 默认异常也不意味着其他任务已全部取消。验证方法：用可控阻塞替身与事件循环心跳，检查并发用户不串、取消有清理、同步重排不阻塞其他接口；不以 async 关键字证明吞吐。

### Q134：智能笔记 RAG 的线程队列、背压和 Chroma 单例分别解决什么问题？

检索词：智能笔记 RAG、queue.Queue、asyncio.Queue、生产者消费者、单例、threading.Lock、多进程。

主回答：有界线程队列连接并行解析与受控写入，防止解析结果无限堆积；SSE 的 asyncio.Queue 连接协程事件，不是同一个队列。Chroma 单例减少单进程重复创建客户端和缓存冲突，初始化锁保护共享实例建立；它不自动序列化所有业务写入，也不跨 Uvicorn worker 共享。完成版先限定单实例协调，再讨论扩展，不能把局部锁当分布式一致性。

实现要点：协程不能直接长时间调用阻塞 queue.get、join 或 executor.shutdown(wait=True)；需线程桥接并有结束哨兵、错误结果和 finally 清理。每次消费正确 task_done，生产者失败也必须使消费者退出；空队列不是所有工作完成的证明。

取舍或异常：取消消费者后生产者可能堵在满队列，需停止标记及受限投递；默认线程池资源仍有限。验证方法：队列满、解析线程异常、消费者取消和重复初始化，用屏障检查无死等、无资源泄漏，不报告未测性能提升。

### Q135：智能笔记 RAG 中 SQLAlchemy 的事务、Session 和查询排序有什么要点？

检索词：智能笔记 RAG、SQLAlchemy、AsyncSession、commit、flush、事务、分页、索引。

主回答：Session 负责一次业务操作的 ORM 状态和事务，不适合多个并发任务共享。flush 把待写动作同步到数据库但没有最终提交，commit 才提交事务；异常时 rollback 并释放连接。笔记和索引待办要在同一事务保存，模型调用放在事务外，避免长时间占锁。所有资源查询带 owner 条件，数据库 IN 查询不保证检索排名，需要按候选 ID 显式还原顺序。

实现要点：建议按实际查询设计 user_id 与更新时间/ID 等联合索引，分页加稳定同分排序。标签筛选必须在计数和分页之前按同一条件执行；MySQL JSON 可有 JSON 查询能力，不能把“JSON 字段不能查”当事实。是否规范化成标签关联表按实际需求取舍。

取舍或异常：深 offset 分页可能成本高，游标是替代方案，不能说已实现。验证方法：并发编辑版本冲突、事务回滚、跨用户 ID、同时间排序、标签总数与页数，用实际查询计划再判断索引效果，不凭字段名宣称提速。

### Q136：智能笔记 RAG 如何组织 API 校验、模型配置和资源生命周期？

检索词：智能笔记 RAG、Pydantic、依赖注入、配置接线、模型工厂、健康检查、readiness。

主回答：路由用 Pydantic 限制输入形状、文本长度和 top_k 范围，服务层校验身份、对象状态与业务约束，存储层执行带作用域的操作。模型配置集中到工厂，聊天、Embedding、视觉和重排各自核对能力与实际版本；后台初始化未完成时，AI 接口返回明确未就绪，不能一边对外报健康一边让请求随机碰空对象。

实现要点：依赖注入提供请求级数据库会话与身份，共享模型受并发上限管理；启动加载、就绪标志、失败原因和关闭释放形成生命周期。流开始前可返回 HTTP 错误，开始后用 SSE error 加终态，HTTP 200 本身不能当成功。

取舍或异常：类型校验不证明资源属于用户；环境变量有值不证明实际调用用了它。验证方法：假的模型工厂记录真实参数，测试错误配置、视觉能力不匹配、资源未就绪、关闭中请求和非法 JSON，避免导入测试意外联网下载模型。

## 十三、智能笔记 RAG：测试、独立验收、评测与面试证据

### Q137：智能笔记 RAG 单元、集成和端到端测试分别测什么？

检索词：智能笔记 RAG、测试分层、pytest、Fake Embedding、脚本模型、离线测试。

主回答：单元测试验证分词、权重、融合、ID、状态机与参数规则；集成测试使用隔离的文件、数据库和索引验证导入、增量、双写、过滤与恢复；脚本模型固定工具序列和流事件，检查 Agent 与 SSE；真实模型端到端只用于验证真实协议和任务表现。替身能稳定命中异常分支，但不能证明真实语义检索效果，真实模型也不能替代程序边界测试。

实现要点：Fake Embedding 输出可预测向量，Reranker 替身返回已知排序，模型替身支持超时和分段响应；测试不读取真实 .env，不初始化付费客户端或自动下载权重。当前可见 Django tests.py 为占位，没有据此认定整项目已通过验收。

取舍或异常：测试实现可能自证循环，应给错误实现准备反例。验证方法：同一越权测试核对召回参数、模型实际输入和真实数据副作用；业务集成用独立临时存储，不能清空用户数据来验证删除。

### Q138：智能笔记 RAG 怎样做独立验收，为什么演示跑通还不够？

检索词：智能笔记 RAG、独立验收、验收标准、金标证据、业务闭环、反例。

主回答：独立验收从事先约定的需求和样例出发，检查实际数据和回答，不能只听 Agent 说完成。比如上传文档后应命中指定事实并能定位原页；更新后旧版不能再作为当前证据；保存笔记后 MySQL 有正文，索引失败时状态明确且可恢复；A 用户任何入口都不能看到 B 的资料。一次演示只能说明该样例链路，不证明普遍质量和异常覆盖。

实现要点：准备格式与证据已知的夹具、跨用户与无答案反例，验收器读取数据库、索引、原件和实际发给模型的证据 ID。金标片段、预期行为与调参数据分开，不能把待测实现当前输出当正确答案。

取舍或异常：答案可有不同措辞，验收看事实、支持关系与副作用而非单个关键词。验证方法：让解析错页、漏过滤、旧版复活、仅返回文件名等错误实现必然失败；本文只设计验收，不声称这些用例已执行。

### Q139：智能笔记 RAG 的检索和答案分别用什么指标评测？

检索词：智能笔记 RAG、Recall@K、MRR、nDCG、引用支持、拒答、评测口径。

主回答：检索评测看是否找到回答所需证据，答案评测看是否正确、被证据支持并引用准确，不能混成一个“准确率”。证据 Recall@K 可按前 K 个有效片段覆盖的金标证据单元占比计算，再对可回答查询汇总；MRR 关注首个相关结果位置，nDCG 需要预先标注分级相关性。答案另看事实正确、支持充分、引用定位和无答案拒答，越权泄漏作为独立失败项。

实现要点：先定义查询、语料快照、证据粒度、K、聚合和失败分母；无答案查询的 Recall 分母为空，单独评价拒答。报告不同问题类型及导入失败、模型超时，不只挑有答案且成功返回的样本。

取舍或异常：模型裁判有偏差，需固定判定合同并抽样人工复核，不把自评当事实。验证方法：构造答案正确但无支持、引用存在但不支持、检索命中却答错、无答案乱答四种样本，确认指标能分别识别。

### Q140：智能笔记 RAG 怎样证明 HyDE、混合检索和 Rerank 各自有效？

检索词：智能笔记 RAG、消融实验、HyDE 开关、BM25 向量对照、Rerank、公平比较。

主回答：用固定语料、查询集、模型和配置做受控对照。先比较纯向量、纯 BM25 与混合，再在固定混合链路比较 HyDE 开关、固定与动态权重，最后比较重排开关；一次只改变目标模块，分别看候选证据覆盖、排序、答案支持、耗时和费用。多个模块一起改只能解释整体差异，不能给每个模块各报一个收益数字。

实现要点：固定候选总预算与上下文预算，必要时同时提供等预算和常用配置两种比较；HyDE 额外调用与失败都计入。参数用开发集选择，测试集锁定；缓存冷热、模型版本与输入快照保存，重复运行检查稳定性。

取舍或异常：增加候选、换模型或改变问题集都能混淆归因。验证方法：保留每个 query 的候选 ID、排名、证据与终态，分析模块帮助和伤害的查询类型；本项目尚无本人提供的原始实验记录，不输出提升比例。

### Q141：智能笔记 RAG 怎样算成本、首字时间和整体延迟，先优化什么？

检索词：智能笔记 RAG、Token 成本、TTFT、端到端时延、HyDE 开销、性能定位。

主回答：成本分导入和查询。导入包含解析、视觉、Embedding 与本地资源；查询包含消歧、HyDE、查询 Embedding、重排、RAG 摘要、Agent 轮次和最终生成，失败与重试也算。延迟分别测接收到首个阶段事件、首个真实答案字和完成的时间；先按阶段定位瓶颈，再考虑减少无效调用、缓存快照、限并发或调候选量，不用 SSE 动画证明模型更快。

实现要点：单调时钟记录排队、模型、存储和流发送；SSE response headers 的处理时间不一定覆盖整条流。Provider usage 缺失标记不完整，按执行时已核对的计费口径算费用；本地模型也有硬件、显存和运行时间成本。

取舍或异常：提高并发可能降低单次等待，也可能引发 OOM 与长尾；单次 Token 少不等于任务便宜。验证方法：冷/热、短/长查询分别记录完整链路与失败分母，样本不足不报可靠 P95 或成本降幅。

### Q142：智能笔记 RAG 回答错误或很慢时，如何进行失败归因和三层追问？

检索词：智能笔记 RAG、失败归因、漏召回、错序、上下文遗漏、幻觉、超时排查。

主回答：先沿数据链定位证据在哪一步丢失：原件解析错了，切片丢了条件，Embedding/词项召回没找到，融合或重排把它排后，预算没装入，还是生成忽略了已有证据。权限、服务故障和真实无答案另分；不能看到答案错就统称大模型幻觉，也不能看到慢就直接换向量库。先看阶段记录和当次真实输入，再做受控复现。

实现要点：第一层问“正确证据是否在语料中”；第二层核对候选、排名、入选与引用 ID；第三层固定模型和输入，仅替换解析、检索或上下文一个环节，检查结果是否改变。性能同样区分队列等待、HyDE、重排、生成和前端缓冲。

取舍或异常：Trace 提供线索，不自动证明因果。验证方法：人工插入金标候选、强制排序、固定上下文与替身模型分别缩小原因；这些是假设性排查方法，不组织成本人经历过某次生产事故。

### Q143：智能笔记 RAG 的个人贡献、真实数字和项目时间怎样回答？

检索词：智能笔记 RAG、个人职责、项目时间、AI 辅助、真实指标、待确认事实。

主回答：技术方案可以解释能力，但不能推出个人职责和实验成绩。回答贡献时需要本人确认具体负责的需求、模块、设计决策、测试与参考或 AI 辅助范围，并能指向实际提交和运行记录。简历时间是 2026 年 2 月至 6 月，当前材料是否含后续修改需核对。没有真实记录时不说主导全部、生产上线、服务多少用户或把准确率提高多少。

实现要点：准备“负责的模块—关键决策—证据位置—验证范围—未解决边界”的事实链；代码署名、README 介绍和方案写得完整都不能自动成为个人贡献证明。

待本人确认（事实清单，不作为口述经历）：项目时间与迭代范围；本人实际职责和 AI/开源参考边界；实际模型、维度、Reranker 适配及运行硬件；真实语料与查询集规模；测试版本和原始结果；完整用量与计时；是否部署、使用者与真实故障。未确认项不填推测数字。

## 十四、MiniCode 与智能笔记 RAG：跨项目比较

本节保留既有比较的 RAG 口径，本轮仅校准 MiniCode 一侧，不重新核验另一项目；比较不表示两个项目已互相接入。检索回答必须同时保留项目名称及差异。

### Q144：MiniCode 与智能笔记 RAG 分别解决什么问题，为什么简历同时写？

检索词：MiniCode、智能笔记 RAG、项目比较、Coding Agent、个人知识管理、AI 应用。

主回答：MiniCode 面向 Python 仓库中的理解、局部修改与测试，重点是让模型在程序权限、状态和独立验收约束下执行任务；智能笔记 RAG 面向个人文档与笔记，重点是导入、隔离检索、证据回答和受控笔记操作。二者都围绕模型与程序协作，但核心交付分别是代码变更与可追溯知识回答。

实现要点：MiniCode 用自有 QueryLoop、文件工具、预算式引用投影、元数据 Skill 和 Run 检查点；另一项目保留其 FastAPI/LangChain、MySQL、ChromaDB、Redis 与 SSE 口径。不能把 RAG 向量库或笔记服务说成 MiniCode 已有能力。

验证方法：编码项目检查代码行为与允许差异，RAG 项目检查证据、回答和数据状态；两边个人贡献分别确认，不因同时列简历就推定均独立开发。

### Q145：MiniCode 的 Skill 路由与智能笔记 RAG 的检索有什么区别？

检索词：MiniCode、智能笔记 RAG、Skill 路由、RAG 检索、关键词排序、方法与证据。

主回答：Skill 路由选的是任务方法，RAG 检索选的是回答证据。MiniCode 根据任务与名称、描述、标签的共享词召回，按唯一共享词数量排序，同分稳定后截断并加载正文，不设独立意图模型或语义精排。智能笔记 RAG 保留 BM25、HyDE 向量路和 CrossEncoder 重排的参考设计，输出带来源的资料。二者不能因为都有召回排序，就混用具体算法和指标。

实现要点：Skill 指令与真实历史分离，不授予工具权限；RAG 片段作为证据，也不能授权写入。方法选对不代表代码完成，资料相关也不代表回答被支持。

验证方法：MiniCode 测名称序列、漏选、多选和任务验收；RAG 测证据覆盖、排序、引用与拒答，不拿一边的指标证明另一边质量。

### Q146：MiniCode 的 Checkpoint、历史回读与智能笔记 RAG 的文档笔记有什么区别？

检索词：MiniCode、智能笔记 RAG、Checkpoint、历史回读、跨任务、文档、笔记。

主回答：MiniCode Checkpoint 用于继续同一个中断 Run，read_tool_result 用于读取该 Run 当时的工具结果；它们没有把历史自动提炼成跨任务长期记忆。智能笔记 RAG 保存用户导入资料与主动记录的笔记，通过其检索链提供资料。一个服务于运行状态和历史取证，一个服务于业务知识管理。

实现要点：新建 MiniCode Run 不自动继承另一 Run 全历史，恢复不能随便换 Run ID。RAG 的业务存储与索引依照其独立合同；不能把笔记自动保存或向量召回搬成 MiniCode 的 Memory、Skill 生长能力。

验证方法：分别检查恢复身份与历史结果，以及另一项目的资料归属和检索来源。文件已持久化不意味着模型自然知道内容，仍需要显式进入本轮输入。

### Q147：MiniCode 与智能笔记 RAG 如何分别评测，哪些原则相通？

检索词：MiniCode、智能笔记 RAG、Benchmark、RAG evaluation、独立验收、对照、成本。

主回答：MiniCode 用固定编码任务检查代码、允许变更、运行状态、预算和过程合同，模型说完成不算成功。RAG 则保留固定语料与问题集，分别检查证据召回、排序、事实、引用、拒答及业务状态。共同原则是标准预先定义，失败和用量不隐去，收益用可核对对照说明。

实现要点：MiniCode 关注 Skill 开关、上下文投影和恢复故障回归，不把本版未主张的自动记忆或缓存收益加入实验；RAG 保留 HyDE、融合和重排对照。重复同一任务是稳定性检查，不变成新增场景。

验证方法：分别保留数据版本、配置、输出和判定；不合并两边为一个“准确率”，不把检索 Recall 用来证明 Agent 会正确编辑。

### Q148：MiniCode 与智能笔记 RAG 哪些基础设施能复用，哪些不能直接复用？

检索词：MiniCode、智能笔记 RAG、基础设施复用、模型适配、数据合同、权限、测试替身。

主回答：可以复用窄接口与测试思路，例如模型协议和错误归一化、参数校验、关联 ID、用量记录、脚本模型和故障注入；具体接线仍需检查消息、取消和使用范围。MiniCode 的文件权限、Run 恢复和 Skill 快照不是 RAG 用户鉴权；RAG 的用户过滤、笔记双写和 SSE 也不是编码 Agent 已有能力。

实现要点：如果以后抽公共库，应排除项目身份和业务副作用，由各自实现存储、权限和验收，不共享可变用户状态或无作用域缓存。

取舍与验证：过早统一会掩盖约束，当前只讨论复用边界，不声称已经集成或建成公共平台。即使共享适配器，两边仍需各自的合同和越权反例。

取舍或异常：多模块同时启用只能解释组合效果，评测任务泄漏进记忆会污染结论。验证方法：预先固定数据拆分、失败分母和分析方式，保留不适用及回归样本；没有对照与原始产物，不把未来方案写成实验收益。

### Q162：MiniCode 未来设计：如何扩展五类 Coding Case，防止 Benchmark 自证正确？

检索词：MiniCode、未来设计、Coding Case、单文件、跨文件、只读诊断、搜索修复、上下文压力、验收器。

主回答：如果扩展 Benchmark，我会沿用单文件修复、跨文件契约、只读诊断、搜索定位和上下文压力这些任务类型，给每类增加边界和反例，不只增加相似题数量。需求、允许改动和验收先定义，Agent 自测后由独立侧检查最终行为、预算、过程和工作区差异。推荐操作顺序不能随意变成唯一答案，验收器也要证明能拒绝常见错误实现。

实现要点：单文件覆盖空值与边界；跨文件同时验新契约和消费者；只读验证解释及零改动；搜索修复检查共享根因；压力题让最终正确性依赖早期证据，同时允许基线用原文解决。新增错误记忆、恶意 Skill、拒绝后继续调用和部分恢复等变体，记录与原任务的关系，不能把重命名当独立泛化任务。

取舍或异常：隐藏验收放在工作区外不自动获得进程隔离。验证方法：让未改需求、只改一边、删除测试、关键字凑答案和超范围修改等变体失败；归档 Answer、Trace、Result、补丁及配置，不能只保存成功截图。

### Q163：MiniCode 未来设计：面试时怎样区分“现在做了什么”和“下一步会怎么做”？

检索词：MiniCode、未来设计、项目真实性、当前能力、迭代路线、设计追问、个人贡献。

主回答：我会先准确描述当前的工具治理、预算式引用回读、元数据 Skill、检查点和任务评测，再说明图片中的自动记忆、三层语义摘要及 AI 风险辅助是可讨论的扩展。面试官问如何设计时，我可以讲数据合同、接入位置、异常和验证；问已经实现或效果多少时，只用对应代码与实际记录回答，不把完整设计推成经历。实现顺序先补来源、状态和验收，再逐个增加能力，确认收益后决定是否继续。

实现要点：未来迭代以关闭开关能回到旧路径为起点，先做版本化元数据与持久证据，再加路由治理、候选记忆和受控采纳，随后按实际瓶颈引入摘要与风险辅助。每一步有合同、故障反例、迁移和回滚；没有匹配需求不为了图片把全部功能上线。

取舍或异常：阶段排序是参考路线，不是已完成排期或个人职责。验证方法：为每项建立设计、实现、测试代码、实际运行、收益证据的状态表；职责、日期和指标由本人确认，默认不把未来题用于回答“你已完成什么”。
