## 1. 为什么保存了历史，还需要 Memory

现有 `CodingAgent.run(task)` 每次只创建一条新用户任务，再进入 QueryLoop。
它不会把另一个 Run 的 Checkpoint 自动放进请求。
`resume(checkpoint)` 则沿用原 Run 的历史、计数和 Skill 指令，并不是开始一个新的独立任务。

| 机制 | 当前解决的问题 | 不能直接代替 Memory 的原因 |
|---|---|---|
| message_history | 本 Run 已发生的交互 | 新任务不会自动继承旧 Run 全历史 |
| Checkpoint | 中断后继续同一个 Run | 不是经过筛选的跨任务项目事实库；不能拿任务 A 的状态冒充任务 B |
| Artifact | 保存工具输出，并可通过引用定位 | 当前为进程内存储；保存结果本身也没有选择、确认、失效和跨任务读取流程 |
| 上下文压缩 | 当前请求给模型保留哪些历史内容 | 不决定以后独立任务应该记住什么 |
| Skill | 可复用的方法说明 | 不应为每个项目临时事实改写 Skill 正文 |
| Memory（计划） | 同一项目的新任务复用少量已确认事实 | 必须另有来源、作用域、失效、纠错与读取边界 |

例子不是“模型记住了上次对话”，而是：

```text
任务 A：发现某类任务使用 tests/unit，并实际运行该目标
        → 程序记录观察证据 → 用户确认其适用范围 → 保存项目事实
任务 B：新 Run、新历史
        → 显式读取本项目事实 → 检查仍适用 → 作为历史参考提供给模型
        → 本次测试仍需工具执行及审批，不能沿用上次的通过结论
```

Memory 存在磁盘上不等于模型能看到；只有把通过检查的内容放进本次 ModelRequest，才会影响模型。
它不会修改模型权重，不保证节省 Token，也不代表自动学习或递归自我改进。

## 2. 第一版只做什么

目标：**在同一 Workspace 的两个独立 Run 之间，复用一条用户确认、有执行来源、可失效和删除的测试目标事实。**

只支持一种事实：`test_target`，例如相对路径 `tests/unit`。
此路径是假设示例，不是本仓库或所有项目的真实入口。
现有 `RunTestsTool` 接收一个相对测试路径，执行固定参数的 Python pytest，因此保存路径比保存
任意 Shell 命令更符合现有工具能力，也不会因为 Memory 引入新的执行权限。

这条事实的准确含义是：

> 在指定项目与记录的条件下，该目标曾由 run_tests 正常执行；用户确认它适用于某类后续任务。

**不是**“tests/unit 覆盖整个项目”“以后测试都会通过”或“当前任务必须运行该目标”。
一个路径曾成功运行，不足以证明它适用于所有修改；当前任务可能需要别的测试，历史记录只能作为线索。
用户本次指示及重新检查的文件与工具结果不得被旧事实覆盖。

第一版限制：

- 每个项目最多一条已确认目标，先做人工确认，不由模型自动提炼/自动写入。
- 只在同一规范化 Workspace 路径内复用；克隆到另一路径视为另一个项目，不跨仓库分享。
- 显式开启，默认不读、不写；不自动扫描仓库 Memory 文件。
- 不存用户私密偏好、密钥、完整工具输出或整个聊天，不保存可自由执行的命令字符串。
- 不修改 AGENTS.md，不增加向量数据库、Embedding、模型重排、远程服务或多 Agent。
- 没有合法且适用的记忆时，回到原来的观察/测试流程，不凭空补事实。

## 4. 一条记忆需要哪些信息

下表是数据合同草案，**不是已经新增的 Python 类或确定的 JSON schema**。

| 信息 | 例子 | 为什么需要 |
|---|---|---|
| 项目范围 | 宿主根据当前 Workspace 计算的标识 | 防止 A 项目的事实被 B 项目读到，不能由模型随意填写作用域 |
| 事实 | kind=test_target，path=tests/unit | 结构化且受限，不接受任意指令或 Shell 命令 |
| 执行来源 | source_run_id、call_id、实际 run_tests 参数及成功结果的最小证据 | 不能把失败调用或模型最终文字当作执行成功 |
| 用户确认及适用范围 | 例如“仅用于这类模块的单元测试”，实际确认记录 | 候选不自动成为已采纳记忆；一个可伪造的 confirmed=true 字段本身不是授权 |
| 来源文件版本 | 明确列出所依据的测试说明/配置文件及 hash | 发现已监控条件发生变化时降级，不盲信旧入口 |

执行来源不能只保留进程内 Artifact ID：下一进程的 ArtifactStore 不一定能解析它。
保存时需要可跨进程复核的最小来源片段/现有持久状态引用，并明确失效或不可核实时的处理。
不保存整段历史来绕过来源设计，也不把手填 Run ID 当成真实证据。

失效初版采用保守规则：项目不符、目标消失/越界、已记录依赖文件的 hash 改变、
来源不能复核、用户删除或纠正后，旧记录不得再作为有效参考注入。
hash 只监测**列出的文件**；文件未变不保证语义正确，也不证明未监控依赖、环境或测试覆盖没变。
下一步实现数据合同时，要明确夹具中究竟监控哪些说明/配置，不能靠“一个 hash”声称全面检测陈旧。

存储位置计划使用宿主用户状态目录、与 Checkpoint 分开的项目专属文件，而不是自动信任仓库里的 JSON。
项目隔离可借鉴现有 `_checkpoint_root` 的规范化路径标识，但不为 Memory 改写 Checkpoint 目录或混存记录。
磁盘 JSON 负责跨进程保存；运行中的 Python 对象负责校验和传递，不能把所有内部步骤都写成 JSON。

## 5. 记忆以后如何进入模型

存储与模型接入必须分开验证：写入成功不等于模型使用过。

```text
任务 A 的真实 ToolCall/ToolResult
  → 限定事实类型、核对来源 → 候选（不注入、不持久采纳）
  → 用户确认适用范围 → 项目专属存储

任务 B（显式开启）
  → 读取同项目记录 → 核对来源/文件版本/路径 → 至多一条有效参考
  → 请求中的低信任数据块 → 模型决定本次行动
  → 原 Dispatcher/Policy/Approval → 本次工具结果
```

Memory 内容是历史数据，不应与 Skill 正文一起升成 system 方法指令。
计划在 ModelRequest 的请求视图中提供明确标记的参考数据，不改写真实 message_history，
不伪造一个并未执行的 ToolCall/ToolResult。
在接线步骤中必须给出实际请求示例和测试，再确定具体实现；本步不新增通用 MemoryProvider 或请求包装层。
限制数据类型可以减少任意文本注入面，但不能宣称它解决所有提示注入。

只在一个 Run 开始时读取一次；不能每轮读取磁盘导致同一任务悄悄换参考。
正式开放普通 CLI/resume 之前，必须明确并实现原 Run Memory 参考的快照一致性，
否则中断后用户改了记忆，继续任务可能读到另一份事实。不能未经设计就沿用 Skill 指令字段来塞 Memory。
该边界在第 R4 步一起验证，先用内部脚本接线，不提前把未完能力开放给用户。

| R5 | 固定版本的任务级 Memory 开关与污染反例评测 | 同样任务/模型/Skill 设置，仅变 Memory；独立验收、完整 usage；错误/陈旧记录反例可解释 | 不顺便修改 Skill、压缩或模型来凑提升 |

## 7. 这个模块什么时候结束

完成以下闭环即可结束本版，不无限扩展：

1. 一条经过来源校验及用户确认的项目事实，能够跨两个独立 Run 读取。
2. 项目隔离、默认关闭、大小边界成立，不扩大执行权限。
3. 来源/文件变化时降级；纠正、删除后旧事实不再被召回。
4. 注入位置与恢复快照明确，有独立请求与 CLI 测试。
5. 开关对照和错误记忆反例都有可核对结果；如实报告效果，允许“没观察到收益”。
6. 用户能解释为何一次测试通过不是永久事实，并能跟着代码指出写入、读取、失效分别发生在哪里。

这些条件满足后先整理证据与面试表述，再决定是否需要自动提炼、多条检索或更复杂记忆。
简历当前最多如实描述内部候选、人工确认和项目单条持久化；尚不能写“Agent 已具备跨任务长期记忆”、
“自动学习”或记忆带来效果提升，因为请求接入和任务级评测还未完成。

### 9.2 Candidate 的六个字段

Candidate 意为“候选”，不是“已采纳的长期记忆”。

| 字段 | 来源与例子 | 谁使用、能说明什么 |
|---|---|---|
| kind | 固定 test_target | 标识只支持这一种结构化事实；不是任意文字指令 |
| workspace_root | 来自宿主 Workspace.root 的规范化绝对路径 | 标记候选所属项目；字段存在不等于已实现跨项目存储隔离 |
| target_path | 来自所选 run_tests 参数，经 Workspace 解析后的相对路径，如 tests/unit | 表示该调用的规范化测试目标，不是适用于所有任务的命令 |
| source_run_id | 由 checkpoint.run_id 取得 | 定位来源 Run，不需要函数调用者另外手填一个 Run ID |
| source_call_id | 由历史中找到的 ToolCall.call_id 取得 | 指明这个 Run 里的哪次测试调用 |
| source_result_sha256 | 对匹配 ToolResult.output 的 UTF-8 内容计算 SHA-256 | 日后比对原输出是否一致；不是输出摘要、不能还原原文、不证明内容真实 |

候选只保留这六项，没有 output 原文、approved 标志、置信度分数、模型生成的描述。
Run ID 与 call ID 定位来源，hash 帮助比对来源；它们不等于一个可自行解析的持久证据库。
后续 R2 必须核对与保留可访问的来源，不能只写一个 hash 后声称原证据已保存。
用户确认、适用范围、依赖文件 hash 都尚未实现，不能把这个候选直接当完整 MemoryRecord。

### 9.3 为什么数据类和构建函数分开

数据类负责**字段合同**；构建函数负责**历史与当前 Workspace 的关系**，不是两层执行流程。

`ConfigDict(extra="forbid", frozen=True, strict=True)` 的含义：

- extra=forbid：不能塞入未定义字段，比如 approved=true 或自定义 command。
- frozen=True：构造后不能用普通属性赋值把 tests/unit 改成另一个目标。
- strict=True：不把数值 Run ID 等不符合类型的数据悄悄转成字符串。

`Literal["test_target"]` 只允许这一种 kind，不能传 shell_command。
`Field(pattern=...)` 要求输出 hash 为 64 位小写十六进制。
三个 `@field_validator` 分别检查根目录绝对路径、目标规范化相对路径、来源 ID 非空。
它们会在构造 TestTargetCandidate 时由 Pydantic 自动调用，不需要用户手动逐项调用。

这些是结构检查，不是来源认证：Python 代码仍可以手动构造格式合法但内容虚假的 Candidate。
所以“能创建一个类实例”不是用户授权、真实执行证据或记忆准入。

### 9.4 函数输入和校验顺序

调用形式：

```python
candidate = build_test_target_candidate(
    workspace=workspace,
    checkpoint=completed_checkpoint,
    call_id="tests_1",
)
```

这段是用法示例，不是自动执行的 CLI 命令。
三个输入是当前 Workspace、宿主提供的完成态 Checkpoint、希望提取的调用 ID。
读取完成态历史不等于 resume：已完成任务不能恢复执行，但它的记录仍可作为候选来源供程序核对。

函数执行顺序：

1. 确认 Workspace/RunCheckpoint 类型，并要求 checkpoint.is_completed。
   这是第一版保守门槛，不从未结束 Run 提取；completed 仍不等于独立任务验收通过。
2. 复用 `get_tool_result(history, call_id)` 查找匹配结果。
   再从同一历史取得 ToolCall；找不到 ID 就拒绝，不拿另一个测试结果顶替。
   RunCheckpoint 本身已拒绝重复调用 ID、结果与调用不匹配等结构错误，故不复制这些底层校验。
3. 要求工具名恰为 run_tests，并要求 ToolResult.is_error=False。
   其他工具返回“1 passed”不算测试来源；失败结果含“passed”也不能挽救失败。
4. 复用 `RunTestsArguments` 校验参数。缺 path 时沿用工具默认 tests；拒绝空路径、错误类型、
   pytest 选项和未知参数，不自己写另一套工具参数规则。
5. 本候选接口额外只允许原始相对路径，即使绝对路径指向 Workspace 内也拒绝。
   用 Workspace.resolve_path 处理规范化及符号链接，拒绝逃逸，并要求当前目标是存在的文件或目录。
6. 由解析后的路径、历史来源 ID、输出 hash 构造 Candidate；数据类再校验字段形状。

相对路径规则比现有 RunTestsTool 更窄，但没有修改工具的行为。
`./tests/unit` 会规范化为 tests/unit；内部符号链接存其实际相对目标，外部链接拒绝。
当前目标检查不是事发时文件版本检查，也不能防止它在函数返回之后变化；失效和文件版本规则仍属 R2/R3。

### 9.5 这次数据怎样传导

```text
宿主传入完成态 Checkpoint（保存的真实历史） + 当前 Workspace + 指定 call_id
    → 同一历史中的 ToolCall 与 ToolResult
    → 校验 run_tests、结果状态、参数、当前路径
    → TestTargetCandidate（Python 对象，只有六个字段）
    → 返回调用者；到此结束
```

函数不运行 pytest，不创建模型请求，不改历史，不写 Memory，不将候选附加到 Checkpoint。
真实 pytest 只在集成测试里由现有 RunTestsTool 执行，用来证明真实工具输出也能进入该合同。

### 9.6 成功状态不是日志关键词判断

现有真实 RunTestsTool 在子进程退出码非零时抛工具错误，Dispatcher 据此生成 is_error=True。
本函数消费该结构化状态，不靠正则搜索输出中的 passed。

例如“1 passed, 1 failed”且 is_error=True 必须拒绝；空输出、全 skipped 或一般日志且 is_error=False
不会被本函数重新判定为覆盖充分。候选仅表达所供应记录中的工具正常结束。
这也说明伪造的 is_error=False 记录可能骗过一致性检查，宿主提供真实来源是调用前提。

重要未完成边界：RunCheckpoint 没有 Workspace 身份字段。本函数不能单凭一份 Checkpoint
鉴别它是否来自另一个项目；workspace_root 只是根据传入的 Workspace 标记。
本步尚不读 Store、不检查磁盘来源真实性，所以不能声称跨项目来源绑定或防伪造已经实现。
R2 采纳前必须从宿主的项目专属状态来源重新核对，不能直接接受模型/JSON 提交的 Candidate。

针对性测试 45 项通过，覆盖：默认目标、目录/文件、路径规范化、多个调用中的准确选择、
未知/无效 call_id、错误工具、失败状态、未完成 Run、参数错误、绝对路径、父目录逃逸、
内外符号链接、目标不存在、非法候选字段、不可变对象、Checkpoint 的错配结果拒绝。
另实际在 pytest 临时工作区运行了一次真实 RunTestsTool，并核对候选的输出 hash；没有模型请求。
手动构造伪来源的测试刻意保留，说明字段校验不是认证，后续写入不能据此放行。

本步最重要的设计取舍：不能为方便生成候选而信任“passed”字样，也不能靠一个 hash 冒充持久证据。
因此保留来源定位与真实性边界，不提前实现 Store/自动学习来掩盖尚未贯通的验证链。

## 10. R2a：先从本项目的已保存来源读取候选（2026-10-09）

### 10.1 为什么先做来源入口

R1 的 build_test_target_candidate 接受调用者提供的 Checkpoint，因此不能自行判断该快照来自哪个项目。
本步增加 load_test_target_candidate：它不接受现成 Candidate 或任意 Checkpoint，而是由宿主提供
Workspace、用户状态根目录 state_home、run_id 和 call_id，从当前项目专属目录读取快照，再复用 R1。

这仍然是候选读取，不是用户采纳、记忆保存、resume 或模型接入。

### 10.2 修改了哪里，为什么

| 文件 | 本步改动 | 原因 |
|---|---|---|
| core/file_checkpoint_store.py | 新增 workspace_checkpoint_root 函数 | 提取原 CLI 的项目目录计算，要求绝对根路径；双方共用同一布局，避免各算一套 |

| memory/test_target.py | 新增 load_test_target_candidate 函数，原六字段与构建规则不变 | 从本项目状态来源重新构建，而非信任手填候选 |
| tests/memory/test_test_target_source.py | 新增 15 项测试 | 验证项目隔离、磁盘读取、缺失/损坏拒绝、CLI 布局一致及已有候选门槛 |

### 10.3 调用和数据流

```python
candidate = load_test_target_candidate(
    workspace=workspace,
    state_home=state_home,  # 宿主选择的绝对用户状态目录，不是模型传来的路径
    run_id="run_001",
    call_id="tests_1",
)
```

这是内部 Python 用法示例，不是已经开放的 CLI 命令。

```text
Workspace.root（已规范化） + state_home
    → state_home/minicode/checkpoints/SHA256(项目根目录字符串)
    → FileCheckpointStore.latest(run_id)
    → 读取既有 JSON，由原 checkpoint codec 校验并还原 RunCheckpoint
    → build_test_target_candidate(workspace, checkpoint, call_id)
    → 核对调用/结果、状态、参数、当前路径
    → 返回未确认 Candidate；到此结束
```

目录中的项目哈希与 Candidate 中的输出哈希不同：前者用于定位项目分区，后者用于比对输出文本。
run_id 的文件名哈希由现有 FileCheckpointStore 管理，本步不另写路径拼接或 JSON 解析器。

读取前先要求项目目录存在，因为 FileCheckpointStore 的构造函数本来会创建目录。
因此普通缺失来源不创建目录、不搜索其他项目；存在目录时沿用原有权限检查。
缺失 Run 报错；损坏 JSON、存储 key 与 Run ID 不一致、未结束运行、错误工具/结果等均不返回候选。
读取不会调用 save，不修改原快照，也不会生成新的 Memory 文件。

### 10.4 已解决与尚未解决的信任边界

两个项目即使拥有相同 Run ID、Call ID 和 tests 路径，也只从各自目录读取；无本项目来源时拒绝，
不以其他项目记录兜底。指向同一个项目根目录的 Workspace 符号链接经规范化后共享原分区。
项目复制到另一根路径仍视为另一个项目。

这解决的是正常宿主读取链路的项目分区与来源定位，不是密码学认证。
state_home 必须由可信宿主决定，不能开放给模型任意选择。
拥有宿主状态写权限的人仍能伪造快照，甚至把别的项目快照复制到当前分区；
Checkpoint 本身仍无 Workspace 身份字段，因此不能声称复制篡改或同一用户写入攻击已被防住。
该假设与当前 CLI 信任宿主状态的边界一致，本步不增加签名或数据库来掩盖它。

本函数没有输入一个旧 Candidate 去比对，只是从目前保存的来源重新构建新 Candidate。
用户预览后、实际采纳前若来源发生变化，后续确认步骤必须重新核对并拒绝静默采纳另一份候选。
目录检查也不是锁或文件系统沙箱，不保证并发写入期间的快照不变。

### 11.2 新数据类是什么

```python
class TestTargetConfirmation(BaseModel):
    candidate: TestTargetCandidate
    applies_to: str
```

candidate 指明用户刚刚看到的六字段候选；applies_to 是用户填写的范围，例如“仅用于库存模块的单元测试”。
它不是适用性的自动证明，不保证该入口覆盖当前修改，也不能当作工具权限或 system 指令。
Pydantic 配置要求严格类型、不允许额外字段、不可用普通赋值修改。
范围要求非空、首尾无空白、至多 500 个字符。500 是首版单条备注的有界输入约定，
不是模型上下文、Token 或 Skill 上限；不声称它是最佳阈值。

可在 Python 中手动构造这个对象，故它不是不可伪造的“人工批准令牌”。
后续宿主保存流程必须自己调用确认入口，不能接受模型或仓库 JSON 声称已确认的对象作为授权。
类校验字段合同，函数才实现交互流程；一个类实例的存在不证明人类真的回答过 yes。

### 11.3 函数如何运行

```python
confirmation = confirm_test_target(
    workspace=workspace,
    state_home=state_home,
    run_id="run_001",
    call_id="tests_1",
)
```

这是内部宿主 Python 调用示例，不是当前 minicode 命令。返回类型是 TestTargetConfirmation | None。

1. 默认使用 Python input，先要求 stdin 是交互终端；普通管道/非交互输入拒绝，不默认同意。
   input_reader 可供可信测试/宿主替换，不开放给模型调用。终端存在本身也不是身份认证。
2. 调用 load_test_target_candidate，从本项目状态读取并校验候选。
   非法/未结束来源在展示前报错，不先向用户询问“是否忽略错误”。
3. 将六字段候选显示到 stderr，提醒历史正常结束不代表覆盖完整或以后通过。
   model_dump(mode="json") 将 Path 转成可显示字符串；json.dumps 只负责展示和转义，未写磁盘。
4. 读取用户填写的适用范围，去首尾空白；空白、超 500 字符或非字符串报错，不进入确认问题。
5. 显示转义后的确切范围，询问 [y/N]。仅 y/yes（忽略大小写与首尾空白）同意；
   空输入、n、其他词均返回 None。两次输入中的 EOFError/KeyboardInterrupt 也返回 None。
6. 用户同意后再次从同项目、同 Run、同 Call 读取候选，再走一遍原校验。
   来源丢失/无效或目标不存在会报错；六字段与展示时不同则拒绝，要求重新查看。
7. 两份候选相同才构建确认结果并返回。没有 save、模型调用、测试执行或历史修改。

```text
本项目保存的来源
    → 第一次 load：取得待展示 Candidate
    → 用户查看 → 填写范围 → 明确 yes
    → 第二次 load：取得当前 Candidate
    → 比较展示时/当前的六字段
    → 一致：TestTargetConfirmation(candidate, applies_to)
       不一致/无效：报错，不返回确认结果
       用户拒绝/中断：None
```

### 11.4 为什么需要重新读，以及没有保证什么

如果展示时输出是“1 passed”，用户思考时来源变成“2 passed”，或者 tests 被改为 other_tests，
不能把用户对旧候选的 yes 静默用于新候选。因此第二次读取比较输出指纹和规范化目标等六字段。
这次不是拿两份对象的内存地址比较，Pydantic 的相等比较会核对字段值。

比较的是候选事实，不是整个 Checkpoint：与候选无关的最终消息变化可以通过，测试明确覆盖这一点。
目标目录仍存在但文件内容已变，当前尚未检测；R3 才做明确的依赖文件版本和失效规则。
也没有锁，最后复核之后到将来保存之间仍可能变化；持久化入口必须在保存前再次核对来源。
候选来源真实性继续依赖可信宿主状态，目录分区与 hash 不构成签名。

范围是用户提供的低信任描述性数据，不自动决定当前任务与其语义是否匹配，不会授予 edit_file/run_tests 权限。
JSON 展示转义换行与常见控制字符以避免原样输出终端控制序列，不声称因此解决全部终端欺骗或提示注入。
确认函数未被挂到模型工具表，模型输出“approved=true”不进入这个交互入口。

## 12. R2c：人工确认后的单条磁盘存储与读取（2026-10-09）

### 12.1 这次交付与刻意不做的事

新增 memory/store.py、tests/memory/test_store.py，更新包说明与学习索引。
没有更改确认函数、候选合同、Checkpoint schema、CLI、QueryLoop、Skill、模型或工具权限。
store.py 只有两个公开函数、一个私有磁盘合同和三个小辅助函数；没有新增 Store/Service/Provider 类链。

公开函数：

- confirm_and_save_test_target：自己调用宿主确认流程，再创建记录；不接受外部 Confirmation/approved 标志作为参数。
- load_saved_test_target：从宿主状态读取本项目一条记录，核对格式、归属与来源后返回 Python 对象。

函数仅供可信宿主接线；还没有 Memory CLI/模型工具接口，也没有实际采纳用户的真实候选。
所有本步写入都发生在自动测试临时目录；测试中的 yes 是输入替身，不是用户授权。

### 12.2 放在哪里、存什么

```text
state_home/minicode/
    checkpoints/SHA256(规范化项目根目录)/...      ← 既有完整来源
    memory/SHA256(规范化项目根目录)/test_target.json ← 一条确认记录
```

同一个规范化 Workspace 根目录定位同一分区，另一路径项目读不到这里；不自动扫描仓库 memory.json。
文件名固定，所以每项目最多一条。项目目录的哈希是分区标识，不是密码或来源签名。

磁盘格式：

```json
{
  "schema_version": 1,
  "confirmation": {
    "candidate": {
      "kind": "test_target",
      "workspace_root": "/project/demo",
      "target_path": "tests/unit",
      "source_run_id": "run_001",
      "source_call_id": "tests_1",
      "source_result_sha256": "这里实际必须是64位小写十六进制"
    },
    "applies_to": "仅用于库存模块的单元测试"
  }
}
```

这是结构示意，示例 hash 文本不满足实际合同，不能直接作为测试数据。
_StoredTestTarget 是文件内部合同，增加必须存在的整数 schema_version=1；它不是另一个业务执行层。
仍复用 Confirmation/Candidate 的字段校验，不复制一份字段定义。
版本缺失、bool/string 类型、未知版本、未知字段、非法 scope/路径/hash 等拒绝，不静默补齐或修复。

不复制完整 ToolResult、聊天或 Checkpoint；来源通过 Run ID、Call ID 和输出 hash 回到既有快照核对。
因此原来源快照必须保留：删除或改变来源后记录不能作为合法参考返回。
hash 不是原文备份；“记忆 JSON 存在”也不证明最初获得了人工确认，宿主状态仍在信任边界内。

单条 JSON 使用 UTF-8，最多 16384 bytes；写前检查，读时最多读取上限加 1 字节以识别超限，
不先无限读完整文件再检查。16 KiB 是初版记录合同的有界工程值，不是最优 Token 阈值。
运行内仍传递 Python 对象，只有磁盘边界编码/解码 JSON。

### 12.3 保存数据流与原子发布

```text
Workspace + state_home + Run/Call ID
    → 算本项目 memory 路径，拒绝已有记录
    → confirm_test_target（第一次读取、输入范围、yes、第二次读取）
    → None：返回，不创建 Memory 目录
      Confirmation：编码版本化 JSON，检查字节上限
    → 创建私有项目目录和同目录临时文件
    → 完整写入、flush、fsync 文件
    → 第三次核对候选来源
    → os.link 临时文件到正式文件名，原子首次发布
    → finally 删除本次临时文件名，返回确认结果
```

项目目录权限在 POSIX 为 0700，mkstemp 创建的文件为 0600；硬链接后的正式文件保持同一文件权限。
检查已有项目目录与读取文件的模式位，拒绝组/其他用户可访问，不自行 chmod 用户已有数据。
拒绝直接的项目目录/记录文件符号链接；不是检查全部父目录、ACL 或建立操作系统沙箱。

为什么不是 os.replace：它可以覆盖正式文件。初版不支持替换，而且即使开头检查不存在，
另一写入者仍可能随后发布；os.link 在正式名字已存在时原子失败，避免竞态下覆盖别人记录。
hard link 在这里不是拷贝另一份内容，而是为完整临时文件增加正式名字；删临时名字不删除正式内容。
已有 Workspace.create_text 也使用此类首次创建做法，本步借鉴而不扩展通用存储框架。

来源校验放在正式发布前，防止确认函数返回后来源变化还落盘。它比较候选六字段，不锁来源文件。
如果发生可捕获的写入/同步/发布异常，finally 清理临时文件，正式文件不出现半份内容。
这不等于完整断电持久性保证：未 fsync 父目录；SIGKILL/断电可能遗留隐藏临时文件，读取不会使用它们。
发布与来源核对也不是跨文件事务；来源在核对后变化仍可能发布，但随后读取会再次拒绝该记录。
后段失败可能留下空项目目录，不能声称所有失败都没有任何文件系统痕迹。

### 12.4 读取数据流与失败行为

```text
Workspace + state_home
    → 本项目固定文件路径
    → 无目录/无文件：None，不创建状态
    → 目录/文件类型、模式位和直接符号链接检查
    → 有界读取 → Pydantic JSON 合同还原
    → 记录里的 Workspace 根必须匹配当前项目
    → 重新从当前项目 Checkpoint 读来源并比较候选
    → 合格才返回 Confirmation；不注入、不执行工具
```

只有缺失返回 None。损坏、权限不合、源记录不可核对/变化等抛出异常，不返回旧对象当作有效参考。
当前还没有请求接入，后续 R3/R4 会明确怎样把失效报告给宿主并退回正常任务流程。
目标存在但文件内容改变的版本失效仍未实现；范围与当前任务的语义适用性也没有自动判断。
同一宿主状态的写入者能伪造 JSON 和来源，权限与 schema 不构成用户身份认证。

### 12.5 测试、遇到的问题及阶段门槛

新增 33 项存储测试，Memory 共 124 项，全套 923 项；Ruff、Mypy（82 个源文件）、
新增文件格式检查及 git diff --check 通过。独立子进程只读取记录，未调用模型或测试工具。
覆盖确认后重建对象/跨进程读取、拒绝与中断不建目录、缺失读取无写入、项目隔离、
错归属、原记录不覆盖、确认后来源变化、保存后来源变化/丢失、仓库 JSON 不作为来源、
schema/格式/范围/大小错误、私有权限、直接符号链接、同步/发布异常清理和并发首次发布不覆盖。

本步归纳的设计问题：

1. “检查不存在后 replace”仍可能覆盖并发记录，所以用 link 做首次发布，不偷偷实现替换。
2. 版本若设默认值，缺失版本可能被自动补成 1；本版要求磁盘文件显式提供版本整数，连 true/"1" 也拒绝。
3. 磁盘只保存 hash 不是保存原证据，读取必须回到既有来源；来源丢失就不能使用。
4. 原子可见与断电持久性不是同一个保证，不能凭一个 os.fsync 就声称完整崩溃恢复。
5. 临时文件失败清理与“所有失败零痕迹”不同，应明确空目录/不可捕获中断的边界。

R2 工程门槛已满足：项目来源 → 人工确认函数 → 单条原子持久化 → 新进程读取复核；
未确认不写、项目隔离与权限有测试。只是内部 API 工程验收，不是用户已学会或完整 Memory 产品验收。
理解门槛：能指出实际写入/读取的函数、临时与正式文件区别、来源 hash 为什么仍需要 Checkpoint。
下一小步进入 R3：先固定测试说明/配置文件的监控范围并实现一个文件变化失效案例，
再做显式纠正替换与删除；不在本步顺便开放 CLI 或接入模型。
