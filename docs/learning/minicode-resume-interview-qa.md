## 一、项目介绍与执行主链

### Q01【P0】请用一分钟介绍 MiniCode。

**完成版口述：**

MiniCode 是一个面向 Python 仓库编码任务的 Agent 工程原型。我围绕 Query Loop 和结构化 Tool Calling 组织执行：模型根据上下文提出动作，程序负责参数校验、权限判断、审批和工具执行，再把结果反馈给模型。

项目重点不是让模型多调用几个工具，而是让长任务具备可控执行、必要上下文、可恢复状态和独立验收。我主要从 Skill 路由、可纠错项目记忆、分层上下文和安全审计几个方面组织能力，并通过固定编码任务记录结果、轨迹、工作区差异和用量。

**边界：**这是简历完成版的介绍，不自动包含生产部署、任意项目生成、沙盒或多 Agent。个人负责的部分需要补充确认。

### Q02【P0】它解决什么问题？为什么不直接把代码发给模型？

单次对话能给建议，但编码任务需要反复观察文件、定位调用关系、修改和验证。直接聊天缺少稳定的执行协议，也很难回答“修改是否获准、哪一步失败、是否真的通过测试、能否恢复”。

MiniCode 把这些问题交给模型外的运行系统处理。模型负责不确定的探索和建议，程序负责确定性的边界与记录。价值是形成可检查的任务闭环，而不是保证模型永远正确。

**验证：**拿一个跨文件任务展示输入、ToolCall、审批、修改、测试、最终答案及独立验收，不能只展示聊天截图。

### Q03【P0】“参考 Claude Code 架构”具体参考什么？

参考的是公开的设计思想：多轮工具使用、按需发现和加载方法知识、管理有限上下文、把模型决策放进受控执行环境。不是声称读过闭源内部源码，也不是说 MiniCode 复刻了它的全部实现。

公开 Agent Skills 资料展示了元数据、正文及附加资源的渐进披露，可作为分层加载的思想来源。MiniCode 的 Manifest 格式与具体路由则属于自身实现，不能冒充官方格式。[Anthropic Agent Skills 介绍](https://www.anthropic.com/research/equipping-agents-for-the-real-world-with-agent-skills)

**追问：**必须指出“借鉴的原则”和“自己选择的简化”分别是什么，而不是只说参考了某知名产品。

### Q04【P0】一条编码任务从输入到结束怎样流转？

下面包含简历完成版的记忆、摘要扩展，不是当前仓库原封不动的调用链：

```text
CLI 解析任务与配置，建立 Run ID 和工作区
  → 组装模型、QueryLoop、工具、策略、审批、状态记录
  → 按配置选择并加载 Skill；读取通过校验的项目记忆
  → 完整历史 + 固定指令 + Skill + 记忆参考 + 工具定义
  → 上下文组装/投影，生成模型可见 Request
  → 模型返回文本和/或结构化 ToolCall
      ├─ 无 ToolCall 且无其他停止条件：正常结束
      └─ 有 ToolCall：检查执行预算
          → Dispatcher 校验参数 → Policy → 必要审批
          → 执行或返回拒绝/错误 ToolResult
          → 保存调用、结果、事件和 Checkpoint
          → 进入下一轮
  → 返回最终回答与停止原因
  → 评测工作流另行执行验收，归档结果与差异
```

**当前事实：**普通 `minicode run` 不会自动执行隐藏验收；评测是独立工作流。当前一次响应中的多个工具调用按顺序执行，不是已有并行调度。

### Q05【P0】CodingAgent、QueryLoop、模型、Tool 分别负责什么？

CodingAgent 是面向“编码任务”的外层入口，提供 run/resume 等调用方式；组装函数把依赖接好。QueryLoop 是执行引擎，维护历史、请求、轮次、工具结果和停止原因。

模型只提出下一步动作或最终回答；Dispatcher 决定一个具体调用能否进入工具；Tool 执行读文件、编辑和测试等操作。

外层 CodingAgent 可以很薄，直接使用 QueryLoop 在技术上也成立。保留外层是为了稳定产品入口，不应为了显得架构复杂再堆包装。

### Q06【P0】结构化 Tool Calling 是怎样工作的？

程序把工具名称、描述和参数 Schema 提供给模型；模型返回工具名、参数和调用 ID。适配器解析模型协议后，Dispatcher 再按工具自己的参数模型验证。

执行结果使用相同 `call_id` 返回，因此一次响应有多个工具调用，也能区分每个结果属于哪个请求。结构化只解决表达和匹配，不保证参数语义正确、操作获准或任务成功。

**验证：**覆盖未知工具、额外字段、类型错误、越界路径、工具失败与正确 call_id 关联。

### Q07【P0】循环什么时候结束？COMPLETED 就是任务成功吗？

当前先处理已配置的模型用量停止条件；没有工具调用时可返回 COMPLETED。有调用但没有 Runtime、达到轮数限制或本批调用会超过工具预算，也会以不同原因返回。异常、取消和超时另行处理，不能冒充正常完成。

COMPLETED 只表示本轮模型不再要求工具且循环正常收尾，不证明代码正确。评测还需检查任务验收、运行状态、预算及 Trace 契约。

**容易答错：**不能说“只要没有 ToolCall，任何情况下都一定算成功”，也不能把所有停止都当异常崩溃。

### Q08【P1】为什么采用 Agent，而不是固定读文件、修改、测试的 Workflow？

具体读哪个文件、搜索哪个符号、是否继续调查，需要根据观察结果变化，适合模型探索；参数验证、权限、保存状态和验收则应该尽量确定性执行。

这是“局部自主决策 + 外围固定约束”，不是整套系统都交给模型。固定报表计算等步骤清晰的任务，可以采用 Workflow，不需要为了叫 Agent 而引入不确定性。

## 二、Skill 能力体系

本节以简历中的分层能力体系完成为设定。当前代码没有证明全部层级对象和意图路由已经落地。

### Q09【P0】原子 Tool、深层 Skill、Skill 目录分别是什么？

**完成版参考定义：**

- 原子 Tool：有明确参数、结果和执行权限的具体动作，如读文件、搜索、运行测试。
- 深层 Skill：某个专业任务的方法包，包含适用场景、步骤、约束、验证方式和可引用资源，如跨文件契约修改方法。
- Skill 目录：组织能力入口和轻量元数据，用于先判断任务可能需要哪类方法，再缩小专业 Skill 的候选范围；目录本身不是必须执行的另一个模型。

“深层 Skill”不是统一行业标准名词，必须在项目中给出自己的定义。目录、方法和动作的层级表达知识组织，不自动意味着多个独立模型或多 Agent。

### Q10【P0】为什么不能把 Skill 当成大 Tool？

Tool 是可执行接口，Skill 主要是任务知识。把完整多步任务包装成一个不透明 Tool，模型可能只看到最终字符串，程序也难以逐步审批、定位失败和保存进度。

Skill 可以指导模型多次使用原子 Tool；每次动作仍经过统一执行边界。真正需要确定性多步流程时，可以实现 Workflow，但应显式暴露步骤状态与失败语义，而不是把任意操作藏进一个 Tool。

### Q11【P0】“意图识别、标签、适用边界与示例”怎样配合路由？

完成版采用以下参考链路：先把任务归入修复、诊断、重构等类别；用语言、任务类型及仓库条件过滤明确不适用的 Skill；根据名称、描述、标签和适用任务示例召回；对候选的匹配程度、约束覆盖和加载成本进行排序，选取有限正文。

示例用于说明“什么样的请求适合此方法”，也可作为候选匹配特征；它不是已执行证据。应包含容易混淆的正反例，不能把评测答案塞进示例后再声称泛化提升。

意图可以来自可解释规则，不必默认用 LLM。所谓精排必须说明实际算法：共享词计数是规则排序，不应包装成语义模型重排。简历未给出 BM25、Embedding 或 Cross-Encoder，不能擅自补上这些技术栈。

**验证：**给同一个任务记录候选、得分、过滤原因、选中项和版本，能够解释为什么选它。

### Q12【P0】为什么采用二阶段召回与精排，不直接给全部 Skill 打分？

第一阶段用低成本特征尽量覆盖可能相关的能力，控制候选集合；第二阶段只对候选做更细的适用性和冲突检查，决定最终选择。这样可以避免对所有正文进行昂贵比较，也便于分别诊断漏召回与排序错误。

代价是第一阶段漏掉的 Skill，第二阶段无法凭空找回；候选过滤太严会牺牲覆盖。因此既统计第一阶段候选覆盖，也统计最终漏选、多选与任务效果。二阶段是检索结构，不代表每一轮动态切换 Skill，也不意味着第二阶段必定使用 LLM。

### Q13【P0】Skill 正文何时加载？是不是必须每轮动态加载？

先读轻量元数据，选中后才读正文；附加资源可以再按实际需要加载。当前 MiniCode 是任务开始时选一次、加载一次，多轮请求复用指令，恢复使用保存的 Skill 快照。

动态加载是另一项选择：适合中途出现新任务类别，但要增加版本、去重、冲突、预算和恢复规则。简历说按需加载，并不要求任意时刻都能热插拔。

**成本边界：**一次磁盘加载不等于只付一次输入 Token；只要正文仍在每轮请求中，就仍属于输入内容。

### Q14【P0】怎样避免自动化增长后的检索噪声和功能重叠？

完成版不把“多存一些 Skill”当成能力提升。每项能力都有稳定 ID、适用范围、版本和依赖；先按范围过滤，再排相关性，限制选中数量及总正文预算。

近似功能要比较解决的问题和约束，而不只比较名字。同一能力的新版本应明确替换关系，不能把新旧版本同时注入。发现互斥约束时选择或澄清，不直接把两段说明拼起来。

**验证：**同时放入相似、无关、过期和互斥 Skill，检查误选、漏选、重复选及任务结果。

### Q15【P1】选错 Skill、正文损坏、正文要求越权分别怎么办？

选错是路由质量问题，应记录候选和选择原因，用错选与漏选案例修正；不能承诺模型总能自行发现。

选中正文缺失、非法编码或超限，是加载错误，应在模型调用前明确失败或按预先定义规则降级，不能静默宣称加载成功。正文要求“无需审批”时，Dispatcher 仍按程序策略处理，不把方法文本当权限。

**当前测试入口：**`tests/skills/test_coding_agent_integration.py` 覆盖未选中正文不加载、恢复复用原文和 Skill 不能绕过编辑审批。

### Q16【P0】怎样证明 Skill 有用？路由准确率够吗？

不够。路由评测检查选中名称、漏选、多选、顺序和无关任务；任务级评测检查开启后是否真正改善最终交付，以及是否增加调用、上下文和用量。

固定代码版本、模型、任务初始状态、预算和工具策略，先做路由离线测试，再做 Skill 开关对照。不能把“选中预期 Skill”直接等同于“任务完成得更好”，也不能只保留有提升的任务。

## 三、自动化记忆沉淀与能力生长

**本节整体为完成版参考设计。当前仓库只实现了部分候选、人工确认和单条存储，不能把本节全套口述为既有产品经历。**

### Q17【P0】Memory、Skill、Checkpoint 和上下文压缩有什么区别？

Memory 保存可跨任务复用的项目事实、经验或明确偏好；Skill 保存可复用的方法。Checkpoint 用于继续同一个中断 Run；压缩决定当前请求给模型看什么。

例如“这个项目的某类单测入口是某路径”是有条件的项目记忆；“怎样定位 pytest 失败”是 Skill；上轮执行到哪个调用是 Checkpoint。它们可以协同，但不能互相冒充。

### Q18【P0】“执行—反思—提炼—分级存储—索引更新—按需复用”具体怎样闭环？

执行阶段先收集真实事件、工具结果和验收结果；反思只提出可复用候选；提炼把一次性日志转成有限事实或带适用条件的方法；宿主核对来源后，按风险决定自动采纳还是人工确认。

采纳后存入对应作用域并更新索引；新任务读取候选，检查版本和有效性，再作为有来源的参考注入。后续结果反过来提供成功、失败或陈旧证据，触发纠正、降级或删除。

自动化不意味着无人审核，更不意味着模型可以直接改策略、系统提示或生产 Skill。

### Q19【P0】为什么不能直接让模型总结聊天后写入长期记忆？

模型可能把猜测、仓库注入、临时失败或一次成功的条件误写成普遍事实。保存得越久，错误对后续任务的影响可能越大。

因此候选必须区分观察、解释和建议，并绑定可核查来源。例如某个测试目标运行成功，只能支持“该目标当时可运行”，不能推出“这个目标覆盖所有修改”。用户偏好也应来自明确表达，而不是模型揣测。

### Q20【P0】一条记忆需要哪些字段？

参考合同包括：ID、类型、规范化事实或方法、项目/用户作用域、适用条件、source Run/call、来源证据或可解析引用、版本/时间、状态、必要的依赖指纹以及采纳依据。

这些字段回答四件事：记什么、从哪来、什么时候适用、谁允许采纳。哈希只能帮助比较内容是否变化，不能证明内容真实，也不能代替原文来源。

**落地原则：**先支持少量结构化类型；不要一开始允许任意自由文本升级成长期高优先级指令。

### Q21【P1】分级存储和索引怎样设计？一定需要向量数据库吗？

分级可以按临时候选、已确认项目事实、受控用户偏好及审核后的方法知识组织，生命周期和访问范围不同。它是治理分级，不一定是多种数据库。

小规模可以使用带版本的文件记录和词项/元数据索引；数量与语义检索需求增长后再引入 Embedding。检索前先隔离作用域、状态和版本，不能先跨所有用户向量检索，再希望模型自己忽略越权内容。

### Q22【P0】怎样纠错、去重和防止错误记忆污染？

同一事实先按作用域与规范键识别，再判断是补充、重复还是冲突。冲突时保留来源和版本，不能简单以最新一条覆盖真相；必要时降级为待确认。

来源失效、目标消失或已监控依赖变化时，不再默认注入。用户删除后同步移除索引可见性，处理旧版本与缓存；新任务的直接证据和明确用户要求优先于旧参考。污染反例必须进入评测。

**边界：**监控文件 hash 未变，不代表所有环境和未监控依赖都未变。

### Q23【P0】记忆如何进入模型？怎样处理隐私与恢复？

只检索当前任务有权限使用的少量有效记录，标记为历史参考，附作用域、来源和适用条件；不能伪造本次工具结果，也不把旧事实提升成可覆盖用户要求的系统命令。

用户偏好与项目事实分开管理，敏感内容最小化保存，不写入公共 Skill。一次 Run 使用固定记忆快照，resume 沿用原快照，避免中断后悄悄换参考；失效或强制撤回需要显式的恢复处理规则。

**验证：**新 Run 能读取合格参考、其他项目读不到、删除后不再召回、恢复不混用版本、审批权限不变。

### Q24【P0】记忆怎样变成 Skill？这是不是 RL 或递归自我改进？

多次任务中的经验先生成候选方法，再检查适用条件、重复功能、冲突和敏感信息；用未用于提炼的任务评测后，经人工或受控发布流程形成 Skill 新版本，支持回滚。

这是外部知识与方法的演化，不改变基础模型权重，不自动等于 RL。一次任务成功后生成一段文本，也不能称为已经验证的能力增长。未经验证的候选不能直接替换线上方法。

## 四、分层上下文压缩与 Prompt Cache

原文保留、引用投影与回读有源码基础；中间摘要、最终结果分层及缓存收益按简历完成版参考设计展开。

### Q25【P0】一句话说明你的压缩策略。

完整原始证据保留在执行状态或可解析存储中；模型请求根据任务和预算分层组织，近期必要证据保持原文，较旧输出按条件替换为引用或带来源的结构化摘要，完成阶段形成可验收结果。需要细节时仍可回读，不让摘要成为唯一事实来源。

当前源码中最明确的一部分是预算式 ToolResult 引用投影。不要把“原文可恢复”说成“模型视图信息无损”，也不要把引用称为语义摘要。

### Q26【P0】为什么保留完整历史，只修改 Request？

完整历史服务于恢复、原文查找和审计；模型 Request 是本轮输入视图。直接删除历史会破坏后续恢复与精确回读，也让一次筛选错误变成不可逆的信息损失。

每轮从原始历史构造 canonical Request，再投影，不是把上一轮的压缩结果当作原始状态继续追加。代价是内存与持久化占用仍然存在，需要单独治理。

### Q27【P0】“摘要层—中间指导层—最终结果层”具体是什么？

完成版可以定义为：摘要层保存有来源的已知事实和阶段结论；中间指导层保留当前目标、硬约束、已验证变更、待办和下一步所需的关键证据；最终结果层保存修改说明、验证结果、剩余问题及交付物引用。

三层服务于不同决策，不是连续三次缩短文本，也不是只保留一个越来越短的总结。原始工具证据独立保存，最终结果不能替代验收。这里的“最小”应理解为足够完成任务的精简信息，而不是字符数最少。

### Q28【P0】什么时候压缩？哪些内容不能随便删？

预算模式在完整请求严格超过配置字节预算时尝试裁剪，先保护近期结果、错误结果、排除工具和不能完整回读的输出，再从较旧候选开始选择。另有按单条输出大小触发的阈值模式；默认 identity 不压缩，两种模式互斥。

完成版摘要还需显式保护用户硬约束、关键否定条件、路径/版本区分、审批状态和未解决问题。当前 ToolResult 投影本身不裁剪系统指令、Skill 正文或用户消息。

**边界：**“模型看过”不是程序可验证的理解状态；近期窗口只是保护规则。

### Q29【P0】怎样计算压缩收益？bytes 和 Token 有什么区别？

先计算当前完整 Request 的净字节变化，要把引用文本和新增回读工具定义算进去；未达到净节省门槛就不采用。预算是尝试压缩目标，不应靠任意截断关键内容强行达标。

bytes 是稳定的实现侧代理指标，Token 依赖模型分词与真实请求。整任务还要累加摘要、回读和额外模型轮次。局部变短不能证明整体成本下降；费用还要考虑缓存和 Provider 的实际计价。

### Q30【P0】原文回读怎样做？为什么特别大的结果反而可能保留？

引用保留 call_id、原始大小和回读入口；回读工具只从绑定 Run 的 Checkpoint 查找当时的 ToolResult，不重新执行原工具，也不跨 Run 任意读取。

如果当前回读接口有完整输出上限，而没有分页合同，超过上限的结果不能安全换成“可回读”引用，否则承诺无法兑现。应保留或明确报超限；真要分页，需要处理范围、编码边界、截断状态和恢复一致性，不能临时拼一个 offset 就算完成。

### Q31【P0】摘要模型写错怎么办？怎样防止层层摘要失真？

完成版摘要采用固定结构，保留事实、来源和不确定项，禁止把建议写成已执行结论。路径、数量、版本、否定条件和关键调用 ID 通过程序核对；不能程序核对的语义结论保留不确定性与原文入口。

不无限地只对上一份摘要再次摘要；必要时从原始证据重建，减少累计误差。摘要失败可以保留原文、使用确定性引用或明确停止，取决于预算和预定降级规则。

**验证：**跨文件相似名称、历史/当前值不同、错误结果和早期约束都要有反例；不能只测摘要是否为合法 JSON。

### Q32【P0】Prompt Cache 和上下文压缩是什么关系？

压缩改变模型实际看到的信息量；Prompt Cache 复用符合条件的重复输入前缀计算，不是保存上一轮答案，也不是模型获得长期记忆。缓存命中通常仍受上下文窗口约束。

完成版把稳定工具定义、固定指令及运行内固定的方法块尽量稳定组织，把任务新增信息放到后面；但实际命中受 Provider、前缀一致性、长度及有效期等条件影响，不能仅凭“内容一样”保证命中。[Claude Prompt Caching](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)

### Q33【P0】怎样验证缓存收益？压缩会不会破坏缓存？

读取 Provider 返回的真实缓存计量，区分缓存读、缓存写、普通输入和输出；用受控冷/热条件比较，并报告整任务用量、时延和质量。不同 Provider 字段与计价不同，不能统一虚构成同一种字段。

改变靠前的工具定义或历史内容，可能降低后续前缀复用；因此尽量稳定已构建的摘要块，避免每轮无谓改写，但不能为了缓存保留错误或过量上下文。按需添加回读工具也可能改变前缀，需实测权衡。

Qwen 应按其部署渠道与模型支持情况核对缓存能力，隐式缓存并不保证每次命中；不能由“使用 OpenAI-compatible SDK”推导具体缓存行为。[阿里云 Context Cache](https://help.aliyun.com/en/model-studio/context-cache)

**当前事实：**不能把“稳定指令 + 输入 Token 总数”当成缓存命中证据；当前用量结构尚不能证明完整缓存成本分解。

## 五、权限、安全、恢复与审计

### Q34【P0】工具白名单、风险分级和审批怎样形成执行边界？

工具注册表限定可调用接口；严格参数合同排除未知字段和错误类型；Policy 按动作风险返回 ALLOW、ASK 或 DENY；ASK 必须取得可信审批，随后工具还检查实际路径和执行条件。

当前默认读取、搜索和差异查看允许，创建、编辑和测试需要审批，未配置工具策略默认拒绝。当前策略主要按工具名，不是已经实现任意参数的细粒度授权引擎。

提示词只是行为引导，不能替代这些执行检查。审批还不是安全证明：获准执行的测试代码仍可能产生风险。

### Q35【P0】Pydantic 校验能防止什么，不能防止什么？

`extra="forbid"` 拒绝额外字段，`strict=True` 避免宽松类型转换，`frozen=True` 限制普通赋值修改。它们固定数据合同，不能证明路径合法、操作获得授权或内容符合业务要求。

例如字符串路径可以通过类型校验，却指向工作区外；编辑参数格式正确，也可能找不到唯一目标。因此 Schema、权限和工具内部语义检查要分开。

### Q36【P0】怎样防 Prompt Injection？

区分指令来源和任务数据：仓库、工具输出、检索内容和自动记忆不能自称获得授权；文本即使诱导模型提出危险调用，程序仍在工具入口限制可执行动作。

完成版的规则可标记伪造审批、越权请求或可疑指令，并限制其进入高信任位置，但不能声称规则能识别所有语义注入。输出泄漏、日志和模型直接回答中的敏感信息还要另设检查，工具审批不能覆盖所有风险。

**验证：**恶意 README、工具输出伪造批准、Skill 要求跳过审批、污染 Memory；检查实际文件变化和调用结果，不只检查模型是否口头拒绝。

### Q37【P0】用户拒绝工具后，程序怎么办？这次算不算工具预算？

Dispatcher 不执行动作，返回相同 call_id 的拒绝 ToolResult，历史保留调用与拒绝结果，模型可据此调整。它不必立即终止整个任务。

当前 QueryLoop 在 Runtime 正常返回结果后增加计数，所以拒绝、校验失败等也会消耗一次调用额度。这里限制的是调用尝试，不只是成功副作用，可避免模型通过反复失败绕过预算。若 Runtime 抛出异常而没有返回，则另走异常路径。

### Q38【P0】超时、取消、Token 预算是不是硬安全上限？

轮数、调用数在继续执行前检查；模型累计 Token 阈值主要在收到响应后检查，当前响应可能已经越过阈值，因此不是预付费式硬账单上限。输出上限需要传给 Provider，也要核对返回用量。

超时和取消还要明确覆盖范围。当前进程实现主要终止直接子进程，且不是完整进程树沙盒。不能把一个 asyncio timeout 等同于“所有后代进程与外部副作用都撤销”。

### Q39【P0】你的系统有进程级沙盒吗？

按截图列出的能力完成，也不能额外回答“有”：简历写的是权限与安全审查，不必然包含 OS 隔离。当前 Workspace 是工具层路径检查，测试代码直接调用 open() 不经过它；固定 argv 和环境白名单也不等于容器。

可如实解释后续方案：通过 ProcessRunner 接入隔离环境，只暴露任务目录，默认断网、最小权限、资源限制和完整任务清理；控制侧保留 API Key、状态和审批。方案不是已实施经历。

**当前计划：**进程级安全沙盒已列入项目待办，未启动实现。

### Q40【P0】Checkpoint 能否保证工具恰好执行一次？Replay 又是什么？

不能。工具副作用和 Checkpoint 写入是两次操作，存在“工具已成功、状态未保存”的窗口。恢复通过 call_id 匹配待完成调用，但不自动知道外部世界是否已变化。

幂等动作、执行前条件、外部幂等键或事务可缩小风险，但不是都已实现。当前精确替换编辑重复执行时，旧文本可能消失并报错，不是已实现成功去重。

Checkpoint 用于恢复；Event 记录过程；Artifact 存放输出或其引用；Replay 按事件只读复盘，不重新执行工具，也不等于 resume。当前事件账本主要在进程内，导出 Trace 不等于已有跨进程持久审计服务。

## 六、Benchmark、质量与成本

### Q41【P0】怎样证明任务完成，而不是相信模型说完成？

根据任务要求预先定义独立验收，检查功能行为和接口契约；再检查 Agent 是否正常完成、是否遵守预算与 Trace 约束，并通过工作区差异检查改动范围。

例如 quantity 改 stock：不仅验证报表还能输出，还断言库存记录确实返回 stock，防止两个文件继续使用旧字段却一起通过自测。整体通过需要各项同时满足，而不是加权投票。

当前入口是 `evaluation_result.build_evaluation_verdict()`：outcome、operational、budget、trace 四项合取；具体允许修改范围由案例验收及差异检查约定。

### Q42【P0】隐藏验收是什么？为什么不和业务代码放一起？

隐藏的是检查程序和具体样例，不是隐瞒任务要求。它不依赖模型修改后的实现来重新定义标准，并与可修改交付文件分开，减少通过弱化测试获得通过的机会。

但工作区外不等于 OS 级不可访问；验收导入待测代码也可能执行不可信逻辑。隐藏是评测组织方式，不是完整安全保证。验收器本身也需要反例测试，可能误放或误杀。

### Q43【P0】怎样设计有区分度的 Coding Case？

分别覆盖单文件逻辑、跨文件契约、只读诊断和搜索定位共享根因；给出明确任务、允许改动、预期行为、预算和过程约束。预期结果来自需求，而不是复制模型输出。

同一个初始 bug 跑多次只是重复试验，不是新增场景。题目数量、难度和代表性分开描述；自建任务不能直接称为企业真实流量。对自测通过但契约错、越界修改、未改实际问题等建立反例。

### Q44【P0】你统计哪些指标？

首先统计独立任务成功率与安全合规情况，再统计模型轮次、工具尝试/实际执行、失败类型、回读次数、完整输入/输出 Token 和时延。缓存优化还要记录 Provider 的缓存相关计量。

总体成功率用预先定义的全部运行作分母，同时分开报告任务失败、基础设施失败和安全失败；成本分别给全部尝试的消耗与成功任务成本，不能悄悄丢掉失败样本。

如 usage 缺失，保留已知小计并标记不完整；不能用缺失=0，也不能用配额耗尽反推本任务消耗高。

### Q45【P0】怎样证明提升来自 Skill、Memory 或压缩？

采用受控开关对照，固定模型、代码版本、任务初始状态、预算与策略，尽量只改变目标模块；跨任务覆盖和同任务重复分别衡量覆盖与稳定性。

Memory 要把提炼任务与验证任务分开，避免记住题目；Skill 要固定正文版本；缓存要控制冷/热条件；压缩要统计摘要与回读增加的完整成本。多模块一起改只能说明整体差异，不能独立归因。

**边界：**单对 Preflight 验证流程和路径是否命中，不足以证明普遍效果。没有结果就讲实验设计，不编数字。

### Q46【P0】失败后怎么归因？怎样保存可复盘证据？

按模型协议、工具参数、权限拒绝、工具执行、上下文遗漏、状态存储、Provider/配额以及验收规则等层次排查。先找直接失败，再用请求对比和受控实验分析原因；Trace 是线索，不自动证明因果。

保存 case/版本、初始状态指纹、模型配置、预算、运行标识、answer、trace、result 和工作区补丁。新记录支持关联哈希；哈希证明关联内容未变，不证明内容真实或结论正确。原始证据应归档在稳定位置，不能把临时目录当长期成果。

**Trace 契约提醒：**推荐的搜索路径可以作为诊断覆盖，不宜把所有推荐动作硬编码成唯一正确路线；安全约束与过程偏好需要区分。

## 七、Python 基础、个人贡献与岗位迁移

### Q47【P1】为什么项目里有很多 JSON、Protocol、Pydantic？是不是过度封装？

JSON 用在模型协议、磁盘 Checkpoint/记忆、Manifest、Trace/结果文件等跨边界场景；运行中优先使用有类型对象，不要求每一步先转 JSON 再转回来。

Protocol 定义模型、执行器或存储所需的最小行为，便于脚本替身和实现替换；Pydantic 在外部数据进入时验证合同。抽象应对应真实替换点或可信边界；只转发调用且没有策略价值的包装可以合并，不为每个函数造接口。

### Q48【P1】async/await 有什么用？多个 ToolCall 是并行的吗？

await 让当前协程在等待网络、审批或异步进程输出时让出执行机会，不意味着 CPU 代码自动并行。当前 QueryLoop 对一批调用使用顺序 await，因此不是已有工具并行调度。

真正并发需要处理共享文件冲突、调用结果顺序、预算预留、取消传播和并发上限；不要把 async 函数、await 或多个工具定义直接当成多 Agent/并行能力。

**异常边界：**预期工具错误可反馈 ToolResult，程序意外异常不能全部吞掉；取消也不能伪装成成功。

> 核心难点是控制信息量与保留决策依据之间的平衡。直接截断简单，但会失去早期证据；全文保留稳定，却可能不断增长。因此把执行状态与模型视图分离，再通过保护规则、引用回读和任务级评测检查代价，而不是只优化单轮字节数。

### Q52【P1】怎样迁移到营销洞察 Agent？RL × Harness 怎么理解？

这是岗位设计讨论，不是 MiniCode 已有业务经历。可复用的是运行循环、数据合同、权限审批、上下文、记忆和评测基础；工具改成受控数据查询、指标计算和报表生成，明确转化率等指标的定义、口径、时间范围与数据权限。

确定性指标计算适合程序/Workflow，模型负责澄清问题、提出分析路径和解释证据；修改投放或预算等副作用需要另行授权。多 Agent 分工要用实际收益证明，而不是照搬编码工具。

RL × Harness 可以讨论：Harness 限定动作、记录轨迹并提供可核查反馈；RL 根据奖励优化策略。若没有训练数据、奖励定义、训练过程和对照结果，就不能说本项目做过 RL。

## 八、三条完整口述主线

这些是组织方式，不是虚构的项目经历。涉及未接线能力时仍遵守第 0 节的设定标记。

### 8.1 主链：跨文件契约修复

任务要求库存字段由 quantity 改为 stock，同时保持报表行为。模型先发现、读取相关实现，再提出编辑；程序检查参数和权限，批准后执行。工具调用和结果进入历史，随后测试与差异检查提供反馈，模型最终结束。

独立验收同时检查新字段、报表输出和允许修改范围；即使旧报表仍能工作，也不能放过字段未改。运行预算、停止原因和过程契约另行检查。讲述时展示实际归档，而不是声称所有案例都按同一工具顺序执行。

### 8.2 取舍：局部压缩不等于整任务收益

大段旧搜索输出每轮重发会占空间，因此用引用投影；但模型回读、额外轮次和工具定义会增加消耗。先计量完整请求，再看整任务成功率和累计用量。没有净收益或证据不足时，如实报告，不只展示变短的一轮。

真实材料优先看[上下文封板总结](context-compression-final.md)及其指向的原始结果。该文档明确区分了 Preflight 与未形成持久归档的正式批次，不能把后者重新说成完整可复现实验。

### 8.3 完成版设计：可纠错记忆不是永久正确答案

某次 run_tests 成功形成测试目标候选，来源校验与适用范围确认后保存；新任务只有在项目、来源和条件有效时才得到参考。它不能代替本次测试，也不能带来新的执行权限。遇到不适用或错误证据时更新、降级或删除，方法提升到 Skill 还要独立验证和受控发布。

当前源码可展示候选、确认与单条存储；检索注入、纠错闭环和 Skill 自动提升仍属于完成版设计，不要混讲。
