# MiniCode 项目画像与执行主链

资料性质：简历全部完成前提下的模拟面试参考设计；不是个人实绩或当前源码核验结论。
统一技术口径：Python、Pydantic、Pytest，单 Agent QueryLoop，结构化 Tool Calling；不额外假定数据库或部署平台。

## 问题：请介绍 MiniCode，你的项目是做什么的？

检索词：MiniCode、项目介绍、自我介绍、Coding Agent、AI 应用开发、项目亮点。

主回答：MiniCode 是面向 Python 仓库的 Coding Agent 工程原型，围绕 Query Loop 和 Tool Use，把任务理解、代码观察、修改和测试组织成多轮闭环。模型负责提出下一步动作，程序负责参数校验、权限审批、工具执行、状态记录和预算约束。完成版设计重点是 Skill 分层路由、可纠错的项目记忆、分层上下文与安全审计，再通过固定编码任务和独立验收检查结果。

项目价值：让模型从“给出一段代码建议”进入“有边界、有证据、能验证的任务执行”。功能目标是改善复杂任务的可靠性和信息利用，不等于已经证明某个统一成功率或成本降幅。

不要扩写：没有提供个人职责、团队规模、上线流量和收益数字；这些不能由软件从“项目完成”推断。

## 问题：MiniCode 为什么需要 Harness，而不是只写一个 Prompt？

检索词：Harness、Agent Runtime、Prompt Engineering、Context Engineering、运行框架。

主回答：Prompt 只能引导模型，不能替程序执行权限、保存状态和验证结果。MiniCode 的 Harness 是模型外的运行支撑，包括 QueryLoop、工具协议、策略审批、预算、上下文组装、Checkpoint、Event 和评测。模型决策有不确定性，但关键执行边界和状态处理尽量用确定性代码实现。

术语区别：Prompt Engineering 关注指令如何表达；Context Engineering 关注这一轮给模型哪些指令、历史和证据；Harness 则还包括执行、恢复和评测。三者相互配合，不是互相替代。

## 问题：MiniCode 一条任务从输入到结束的完整流程是什么？

检索词：主流程、调用链、CLI、QueryLoop、Request、Response、ToolCall、ToolResult。

主回答：CLI 解析用户任务和配置，组装工作区、模型、工具、权限和状态依赖。任务启动时按配置选择并加载 Skill，读取通过来源和有效性检查的项目记忆。QueryLoop 从完整历史、固定指令、方法说明、记忆参考和工具定义构建请求，再生成预算约束下的模型视图。模型返回工具调用后，Dispatcher 验证参数并执行策略与审批，获准后才进入工具。调用和结果进入历史、事件及检查点，供下一轮决策。没有后续调用或触发停止条件时，程序返回回答和停止原因。

关键边界：普通任务结束不自动代表独立验收通过。Benchmark 在另一条评测流程中检查代码行为、改动范围、运行状态和轨迹。

职责区分：模型提出动作；程序决定能否执行并维护状态；工具产生真实读写或测试效果。Skill 和 Memory 不拥有执行权限。

## 问题：CodingAgent 和 QueryLoop 有什么区别？是否可以去掉外层 Agent？

检索词：CodingAgent、QueryLoop、组装、依赖注入、薄封装。

主回答：QueryLoop 是维护请求、响应、工具反馈和停止条件的核心执行引擎。CodingAgent 提供面向编码任务的 run/resume 入口，组装函数连接具体模型、工具和策略。外层可以很薄，直接调用 QueryLoop 在技术上也成立；保留它是为了稳定产品入口，而不是多造一层自主智能。

取舍：抽象应服务于替换模型、工具或执行器等真实需求；如果一层只转发参数且没有明确边界，就不应为了架构图复杂而保留。

## 问题：为什么选单 Agent，不直接做规划、执行、审查多个 Agent？

检索词：单 Agent、多 Agent、Planner、Executor、Reviewer、Agent Team、架构取舍。

主回答：MiniCode 优先解决单任务的可靠执行。代码定位、编辑、测试之间有较强状态依赖，拆成多个 Agent 会增加通信成本、证据同步和文件冲突。先用单 Agent 配合外部确定性检查，能够减少不必要的协调。只有子任务可独立并行、收益能覆盖通信和恢复成本时，才考虑引入多 Agent。

不要扩写：多工具不等于多 Agent，Skill 分层也不意味着多个独立模型。

## 问题：MiniCode 能从零搭建并部署完整项目吗？工具是不是太少？

检索词：端到端开发、项目搭建、工具数量、能力边界、部署、依赖安装。

主回答：MiniCode 的目标是已有 Python 仓库中的代码理解、局部修复和测试，不把它定义成任意项目搭建与部署平台。现有工具覆盖文件发现、读取、搜索、创建、编辑、差异检查和测试，是否足够应按目标任务评估，而不是按工具数量判断。依赖安装、后台服务、数据库和部署属于额外能力，需要新的权限与生命周期管理。

边界：能创建文件不等于已验证复杂项目搭建；不能因为简历完成，就补写全栈生成、云端部署和生产运行经历。

## 问题：参考 Claude Code 具体参考了什么？

检索词：Claude Code、架构参考、原理借鉴、渐进披露、自研。

主回答：参考的是公开的多轮工具使用、方法知识按需加载和上下文治理思路，再按本地 Python 编码任务实现自身协议与边界。不是声称使用过闭源内部架构或完整复刻产品。具体参考来源、哪些代码由本人或 AI 编写，需要本人确认，不能由知识库推断。

## 问题：最值得讲的三个项目设计是什么？

检索词：亮点、创新点、项目难点、设计取舍、核心贡献。

主回答：第一，把模型提议和程序执行权限分开，让 Skill、仓库和工具输出都不能自行授权。第二，把完整证据与模型视图分开，压缩请求但保留恢复与回读入口。第三，把模型声明完成和任务验收分开，通过程序检查实际交付。Skill 与 Memory 在这个基础上负责复用方法和项目经验，而不是取代执行边界。

表达要求：技术设计亮点不自动等于个人贡献；如果问“你负责什么”，只能使用本人已确认的职责。
