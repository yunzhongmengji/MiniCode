# MiniCode：Benchmark、独立验收、案例与失败归因

资料性质：简历全部完成前提下的模拟面试参考设计；案例用于解释验收机制，不冒充已经由本人完成的特定运行经历。

## 问题：MiniCode 怎样判断任务成功？

检索词：Benchmark、任务成功、completed、验收、四维判断。

主回答：不能只看模型说完成或 QueryLoop 正常退出。评测同时检查任务结果、运行状态、预算和 Trace 契约，允许改动范围通过验收和工作区差异核对。结果正确但超预算或未正常收尾，要分别记录，不混称代码功能错误。

总体通过是约定条件同时满足，不是某项好就抵消另一项失败。不同案例的必要过程可以不同，不能把推荐路径全部当唯一正确路线。

## 问题：隐藏验收和 Agent 自己运行测试有什么区别？

检索词：隐藏测试、acceptance、run_tests、自测、独立验收。

主回答：自测是 Agent 在执行过程中获得反馈并继续修改；独立验收由评测侧依据预先任务要求检查最终交付，不根据模型的实现反过来改标准。隐藏的是具体代码和样例，不是故意隐瞒需求。

边界：验收可能写错，放在工作区外也不等于不可被任意进程访问。要给验收器设计正反例，不能把“测试全绿”当作绝对正确。

## 问题：单文件修复怎样设计验收？

检索词：single_file_batching、批处理、边界输入、单文件修复。

主回答：以批处理逻辑为例，任务约定输入、批次大小、输出与允许修改文件。验收至少覆盖整除、非整除、空输入和非法参数等已约定边界，检查实现真正满足需求，而不是只适配一个样例。

过程：Agent 读取、提出最小修改、执行测试和检查差异；评测另查结果、改动范围与运行约束。这里是验收设计说明，不补造某次模型的实际工具顺序和结果。

## 问题：跨文件 quantity 改 stock 为什么不能只检查报表能输出？

检索词：multi_file_inventory_contract、跨文件契约、quantity、stock、报表。

主回答：库存与报表如果都继续使用旧字段，报表仍可能正常工作。因此验收既断言库存记录符合 stock 新契约，也断言报表能正确消费该记录，还检查允许修改范围。前者证明需求改了，后者证明功能未坏。

失败反例：只改生产者、只改消费者、两边都没改、通过删除测试绕过需求，都应该被识别。预期字段来自任务，不来自模型修改后的代码。

## 问题：只读诊断案例检验什么？

检索词：readonly_pagination_diagnosis、只读、分页、注入、解释正确性。

主回答：只读任务不仅检查最终解释是否符合不同边界输入，还检查没有修改工作区，并用仓库中的不可信诱导验证权限边界。关键词命中不足以证明诊断正确，应检查关键输入和预期关系，允许合理表达但拒绝错误结论。

取舍：检查过松会误放，过度绑定措辞又会误杀，因此验收也需要独立反例。不能因为答题中出现了正确名词就算通过。

## 问题：搜索驱动的共享根因修复和普通修复有什么不同？

检索词：search_driven_retry_schedule、搜索定位、共享实现、根因、调用关系。

主回答：不预先把具体出错文件指给 Agent，要求从目录和文本搜索发现调用关系，定位多个现象背后的共享实现，再做最小修改。验收检查共享行为和允许修改范围，避免在多个调用方分别打补丁掩盖根因。

证据：轨迹能帮助解释为什么读这些文件、修改是否基于观察；但搜索步骤只是调查路径，是否必须作为硬门禁取决于案例预先契约。

## 问题：大工具输出与早期证据回忆案例为什么必要？

检索词：large_search_context_repair、large_search_context_recall、上下文压力、早期证据。

主回答：简单任务输出少，可能根本不触发压缩，不能证明压缩路径可用。压力案例需要真实产生足够大的历史输出，并让后续任务依赖早期证据，检查是否发生投影、能否回读及最终答案是否正确。

公平性：任务应要求报告正确事实，不强制只有开启组才有的 read_tool_result；否则把专属实现写成正确性条件，会人为偏袒一组。

## 问题：成功率和成本怎样统计？

检索词：成功率、样本、重复、Token、成本、缺失 usage、失败分母。

主回答：区分不同任务数与运行次数；重复同一任务检查稳定性，不能当新增场景。预先规定全部尝试和失败分类，报告安全任务成功、模型和工具调用、完整输入输出以及回读开销。成本同时关注全部尝试和成功任务，不只挑成功样本。

用量缺失保留已知小计并标记不完整，不能当作零；配额错误可能是既有余额不足，不能反推当前任务耗费很大。

## 问题：Skill、Memory、压缩怎样做消融和对照？

检索词：消融、ablation、开关对照、Preflight、公平性、归因。

主回答：固定模型、代码、任务初态、预算和权限，一次只改变目标模块；Skill 固定正文版本，Memory 分开经验提炼与验证任务，压缩统计摘要和回读的整体消耗，缓存控制冷/热条件。模块一起改变只能解释整体差异，不能独立归因。

Preflight 是小规模端到端预检查，用于检查数据链和关键路径是否命中，不是最终统计结论。各跑一次不能证明普遍效果，多次运行也不能代替多种场景。

## 问题：失败如何归因？怎么避免只凭直觉怪压缩或模型？

检索词：失败归因、Trace、权限拒绝、工具失败、模型错误、上下文遗漏。

主回答：先按阶段找直接原因：模型协议、参数、策略拒绝、工具、状态保存、上下文、Provider 或验收器。再查看当轮实际请求、工具输入输出和差异，判断缺了什么证据；要证明某策略影响还需要受控对照。

例子：编辑未获批准导致字段未改，首先是执行未获准；隐藏验收失败不能单独证明压缩有问题。Trace 记录关联线索，不自动构成因果证明。

## 问题：Answer、Trace、Result、工作区补丁分别有什么价值？

检索词：answer.txt、trace.txt、result.json、workspace.patch、归档、哈希。

主回答：Answer 保存最终输出；Trace 保存运行事件；Result 保存验收与统计；工作区补丁说明实际改了什么。一起关联版本、模型、配置、案例和 Run ID，才能把结论追溯到过程与交付。

新记录可以保存关联文件哈希，防止无意混用内容；哈希不证明结论真实。归档要在稳定位置，临时目录被清理后不能声称仍有完整可复现实验。

## 问题：最能体现项目价值的失败复盘应该怎样讲？

检索词：失败复盘、最难的问题、设计取舍、真实经历。

主回答结构：先说具体任务和异常，再指出日志或测试中的证据，解释候选原因与排除过程，说明改变了哪项设计，最后交代验证范围和仍未证明的部分。

可讨论的技术问题：工具输出缩短却增加回读轮次、验收关键词误放、工具成功但状态未保存、Skill 选中却不适用。这些是复盘主题，不是本人已亲历事件；软件不能自动加上“我当时遇到并解决了”的叙述。
