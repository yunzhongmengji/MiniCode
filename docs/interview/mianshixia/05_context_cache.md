# MiniCode：分层上下文、历史回读与 Prompt Cache

资料性质：简历全部完成前提下的模拟面试参考设计，分层摘要和缓存细节采用本包统一方案，不是当前源码验收结论。

## 问题：MiniCode 的上下文策略是什么？

检索词：上下文压缩、分层上下文、Context Engineering、原文外置、模型视图。

主回答：完整工具证据保留在执行状态及可解析存储中，模型请求只携带当前需要的内容。近期证据保持原文，较旧的大输出按条件转为可回读引用；完成版再用带来源的结构化摘要、当前行动指导和最终交付组织不同阶段的信息。压缩的是模型视图，不是销毁原始记录。

设计目标：降低无关信息重复进入请求的成本，同时保持任务可解释、可恢复和可验收；不宣称语义无损或必然降低总 Token。

## 问题：完整历史、Request、Checkpoint 分别有什么用？

检索词：message_history、canonical request、projected request、Checkpoint。

主回答：message_history 是程序维护的本次运行交互；Request 是这一轮给模型的信息视图；Checkpoint 保存可恢复状态和原始工具结果。每轮从完整历史构造请求后再投影，不在上一轮压缩文本上继续丢失信息。

代价：完整历史仍占内存和持久化空间，模型上下文变短不等于所有存储也变小。

## 问题：摘要层、中间指导层、最终结果层分别放什么？

检索词：三层上下文、摘要记忆、必要信息、中间指导、最终结果。

主回答：摘要层保留已确认事实、阶段决策及其来源；中间指导层保留当前目标、硬约束、已验证变更、待处理问题和下一步必要证据；最终结果层保留交付说明、验证结论、剩余风险与工件引用。原始证据另存，不让摘要成为唯一事实源。

三个层次对应不同用途，不是把文本连续缩短三遍，也不是给模型保留其隐藏思维链。所谓“最小结果”是足够支撑交付与验收的精简结果，不是长度最短。

## 问题：什么时候触发裁剪？哪些信息优先保留？

检索词：预算、max_request_bytes、保护窗口、recent、error、retention。

主回答：预算模式先测量完整请求，严格超过配置预算才尝试裁剪；工具结果先分类，近期批次、错误、显式排除工具和无法完整回读的内容保留，其余较旧结果作为候选。阈值模式则按单条结果大小触发，默认不开启时原样发送。

完成版摘要还必须显式保护用户约束、否定条件、版本和路径区分、审批状态与未解决问题。不能因为“旧”就认定不重要，也不能说程序知道模型已经理解了什么。

## 问题：旧工具结果的短引用包含什么？怎样回读？

检索词：read_tool_result、call_id、引用、原文、历史查询、恢复。

主回答：引用说明这里曾有历史输出，保留 call_id、原始大小与回读工具名；原 ToolCall 仍让模型知道当时做了什么。read_tool_result 只读取当前绑定 Run 中已保存的原 ToolResult，校验运行身份和大小，不重新执行搜索或读取当前文件。

工具历史和当前文件可能不同：回读回答“当时返回什么”，read_file 回答“现在文件是什么”。结果尚未生成、ID 不存在或 Run 不匹配都必须明确失败。

## 问题：特别大的输出为什么可能不压缩？为什么不直接分页？

检索词：回读上限、分页、过大结果、不可恢复引用。

主回答：若回读只支持固定上限的完整输出，超过上限就不能生成“可完整恢复”的引用。保留原文或明确报告无法满足预算，优先于制造不可兑现的恢复入口。

分页是独立合同，需要定义范围、编码边界、总长度、截断标记、快照一致性与缺失页行为；没有这些约定，不临时声称支持任意大输出。分层摘要能提供导航，也不能代替需要的原始细节。

## 问题：结构化摘要怎么生成，如何避免模型编造？

检索词：摘要、summary、结构化笔记、事实来源、信息遗漏。

主回答：完成版从原始证据生成固定结构：目标和约束、已确认事实及来源、完成动作与验证、未解决问题和可回读入口。区分“提出过”“执行过”“验证通过”，禁止从模型建议推断真实动作。

程序核对路径、调用 ID、枚举状态、数值和来源存在性；语义是否充分支持结论仍要保留不确定性。摘要失败时按规则保留原文、采用确定性引用或停止，不静默编造替代证据。

## 问题：怎样避免层层摘要造成信息漂移？

检索词：摘要漂移、递归压缩、事实丢失、重建、缓存。

主回答：不把上一份摘要当唯一事实继续无限摘要。摘要保留来源与版本，重要节点从原始证据重建，已确认且未变化的块保持稳定，新增内容单独追加或明确更新。

验证：用早期硬约束、跨文件同名字段、历史与当前值不同、否定条件和错误结果做反例；摘要 JSON 合法不代表信息保真。原文可找回也不等于模型必然知道何时回读。

## 问题：如何判断一次压缩值得采用？

检索词：净收益、Tool Spec、请求大小、bytes、Token、回读成本。

主回答：先比较完整请求的净变化，计入引用本身和回读工具定义；只有达到净节省要求才采用。预算模式按旧候选逐步尝试，仍超预算时报告剩余压力，不无条件删掉受保护信息。

任务级还要统计摘要生成、回读和额外模型轮次，因此单轮字节节省不能证明整任务 Token 或费用下降。字节是程序侧代理，真实 Token 和账单依赖 Provider。

## 问题：Prompt Cache 具体缓存什么？和记忆、压缩有什么区别？

检索词：Prompt Cache、前缀缓存、KV Cache、输入缓存、长期记忆。

主回答：Provider 的 Prompt Cache 复用符合条件的重复输入前缀计算，不是缓存最终回答，也不是让模型获得跨任务长期记忆。压缩改变模型输入内容，Memory 选择跨任务参考，缓存则优化重复计算。

缓存前缀仍属于模型上下文，不能用缓存突破窗口。命中受模型、渠道、前缀一致性、长度和有效期等条件影响，OpenAI-compatible SDK 不保证统一缓存行为。

## 问题：MiniCode 如何兼顾压缩与前缀缓存？

检索词：稳定前缀、工具顺序、指令、缓存失效、按需工具加载。

主回答：完成版稳定组织固定指令、工具定义及运行内固定方法块，避免无意义的重排、时间戳或摘要重写；动态任务证据放在合适的后续位置，稳定已确认的摘要块。但不能为命中缓存保留错误信息或过量历史。

冲突：替换早期历史、动态增加工具或更换 Skill 都可能改变可复用前缀；按需工具节省输入和缓存稳定性之间要实测，不声称二者总能同时最优。

## 问题：怎样证明缓存和压缩真的节省成本？

检索词：缓存命中率、cache read、cache write、usage、费用、TTFT、对照。

主回答：记录 Provider 实际返回的普通输入、缓存读写和输出计量，按该模型计费口径计算；控制冷/热条件并检查整任务结果、调用数、完整用量和时延。记录缺失时标记不完整，不用请求字节或文档折扣代替实测。

边界：缓存字段不同于普通 Token 总数，价格和命中条件也因 Provider 而异。没有原始数据时，可以解释优化机制与实验设计，但不报告具体命中率、降本比例或延迟提升。
