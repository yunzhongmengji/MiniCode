# ADR-0002：使用结构化历史与执行前预算

状态：Accepted
日期：2026-08-22

## 背景
1. 只用message传递记录历史，会导致工具调用信息的丢失，不能得到利用
2. 模型可能不断地请求使用工具，甚至一次请求多个工具
3. 工具可能具有破坏性作用，如修改文件，不能执行后再判断。

## 决策
1. 使用 ConversationItem = Message | ToolCall | ToolResult 保存结构化历史。
2. Query Loop 只依赖 Model 和 ToolRuntime Protocol。
3. 使用 max_turns 限制模型调用次数。
4. 使用 max_tool_calls 限制成功执行的工具调用数量，当前默认值为 8。
5. 所有预算检查都发生在工具执行之前。
6. 最后一个模型轮次不执行工具。
7. 一批工具调用整体超过预算时整批拒绝，不部分执行。
8. 使用明确的 StopReason 和 RunResult 表达停止状态。

## 正面后果
1. 工具调用和结果可以通过 call_id 准确关联。
2. Provider Adapter 可以保留结构信息。
3. 能测试并解释每一个停止状态。
4. 预算能在副作用发生前阻止执行。
5. ScriptedModel 与 ScriptedToolRuntime 可以离线复现循环。

## 负面后果
1. 结构化历史比纯文本 Message 更复杂。
2. Provider Adapter 必须负责序列化不同历史项目。
3. 整批拒绝可能浪费剩余工具预算。
4. 默认值 8 是初始工程选择，尚未经过真实 Benchmark 验证。
5. 最后一轮拒绝工具可能使某些任务提前停止。

## 备选方案

1. 把工具调用和结果转成普通文本 Message。
   - 实现简单，但会丢失结构化参数、call_id 和错误标记，Provider Adapter 还需要重新解析文本。

2. 只限制模型轮次，不限制工具数量。
   - 一次模型响应仍可能请求大量工具，无法真正限制副作用数量。

3. 工具执行后再检查预算。
   - 检查时副作用已经发生，预算无法发挥执行前保护作用。

4. 批次超预算时只执行剩余数量允许的部分。
   - 可以利用剩余预算，但会破坏模型提出的完整批次，可能产生部分副作用和难以解释的状态。

## 重新评估条件
1. 真实 Provider 对工具历史顺序有不同要求。
2. Benchmark 证明默认工具预算不合适。
3. 引入 Policy、Approval、Event Ledger 后需要重新划分停止职责。
4. 出现必须支持部分批次执行的业务场景。
